# Server AI Agent — AI-агентный слой

Персональный голосовой/текстовый AI-агент, живущий на рабочем столе Linux.
Один JVM-процесс: GUI, Telegram, голос и агентная логика внутри него.

---

## 1. Архитектура

### 1.1 Единый процесс

Вся система — **один JVM-процесс**. В нём одновременно работают:

* JavaFX-GUI (окно управления),
* Telegram-бридж (long polling),
* голосовые бриджи (STT/TTS),
* агентная логика (цикл «событие → LLM → инструменты → ответ»).

Отдельных демонов, сервисов и IPC между подсистемами **нет**. Подсистемы
общаются прямыми вызовами и разделяемыми объектами в памяти.

### 1.2 ON/OFF — это флаг, а не процесс

Ключевое решение: «выключить агента» означает **снять флаг в памяти**
(`AgentSwitch` в `agent-core`), а не остановить процесс.

Когда агент выключен:

* процесс, окно и Telegram-бридж продолжают жить,
* входящие события просто не обрабатываются,
* включение мгновенно — ничего не нужно поднимать заново.

Флаг потокобезопасен и рассылает события подписчикам, поэтому все интерфейсы
показывают одно и то же состояние. Подробно — раздел
[«Как включить и выключить агента»](#33-как-включить-и-выключить-агента).

К переключению привязаны **хуки жизненного цикла** `onAfterStart` /
`onBeforeStop` — см. [раздел 3.6](#36-хуки-жизненного-цикла).

интерфейс `AgentTextHandler`, в который `SupervisorMain` подставляет
`AgentCore::handle`.

### 1.4 Один вход для всех каналов

Каналов ввода несколько — Telegram, голос, планировщик, в будущем буфер
обмена — но путь обработки **один**. Любой ввод превращается в `UserMessage`
и уходит в `AgentCore.handle`:

```java
public record UserMessage(MessageSource source, String text, Instant receivedAt, String replyTo, String traceId)
public enum MessageSource { TELEGRAM, VOICE, SYSTEM, CLIPBOARD }
```

`SYSTEM` — сообщение не от человека, а от самого агента из прошлого:
сработавшее напоминание приходит в ядро тем же типом, что и текст из чата
(см. [3.13](#313-напоминания)). `CLIPBOARD` — содержимое буфера обмена,
прочитанное по явной просьбе пользователя: оно ложится в лог сессии отдельной
репликой с этим источником, см. [3.16](#316-буфер-обмена).

Канал отвечает только за свой транспорт: поллинг, микрофон, буфер. Агентная
логика про каналы не знает. Иначе каждый новый канал тащил бы за собой копию
этой логики.

`replyTo` — куда вернуть ответ: для Telegram это id чата, для голоса пусто
(ответ пойдёт в TTS, когда тот появится). `source` нужен не для ветвления
логики, а чтобы знать адрес ответа и чтобы это было видно в логах.

### 1.5 Цикл обработки запроса

Модель отвечает не свободным текстом, а **структурированным решением**:
ответить самой или выполнить Python-скрипт. Один запрос пользователя может
стоить нескольких обращений к модели, и все они считаются общим бюджетом.

```
сообщение -> в лог сессии диалога
          -> поиск в каталоге (по словам, бесплатно)
          -> кто упомянут (по именам, бесплатно) -> их факты в системный промпт
          -> решение модели (JSON): лог сессии целиком + кандидаты + память
               type=reply            -> отдать текст                    ✔
               type=tool_call        -> инструмент (без подтверждения)
                                        -> модель формулирует ответ     ✔
               type=use_script       -> взять готовый из каталога ─┐
               type=run_script       -> сохранить новый ───────────┤
               type=fix_last_script  -> новая версия прошлого ─────┤
                                                                   ▼
                                        требует подтверждения? -> спросить кнопкой
                                                                   ▼
                                        запустить
                                          успех  -> модель формулирует ✔
                                          провал -> модель чинит -> заново
```

Три семейства решений: **ответ**, **скрипт** (три варианта: новый, готовый,
починка) и **инструмент**. Инструмент — заранее написанная Java-функция:
быстрая, проверенная, без подтверждения. Скрипт — код, который модель пишет
сама: медленнее и требует разрешения.

Цикл конечен **не по счётчику итераций, а по бюджету** (`RequestBudget`):
каждый круг стоит минимум одного обращения к модели. Подробности —
[протокол](#382-протокол-решения), [бюджет](#383-бюджет-запроса),
[каталог и подтверждения](#39-каталог-скриптов-и-подтверждения),
[память](#311-память).

После ответа реплика агента тоже ложится в лог сессии, и каждые N сообщений
(или при выключении) отдельное обращение к модели извлекает из лога факты
о людях — это и есть долговременная память.

Тем же путём входят и **напоминания**: сработавшее задание планировщика — это
`UserMessage` от системы с промптом «для будущего себя», см. [3.13](#313-напоминания).

### 1.6 Целевая среда

Система пишется под конкретное окружение, переносимость не является целью:

* **ОС** — Arch Linux.
* **Дисплей** — Wayland. Буфер обмена через `wl-copy`/`wl-paste`,
  скриншоты и автоматизация ввода — с учётом ограничений Wayland.
* **Горячая клавиша** — клавиша **Home**, читается напрямую через **evdev**
  (`/dev/input/event*`) нативным хелпером `native/evdev-hotkey`. Глобальных
  хоткеев в Wayland нет принципиально, это модель безопасности протокола,
  а не ограничение композитора. Требует членства пользователя в группе `input`
  — см. [раздел 3.8](#37-голосовой-ввод-push-to-talk).
* **STT** — **whisper.cpp**, локально. Аудио наружу не уходит.
* **TTS** — **Piper**, локально.
* **Скрипты действий** — **только Python 3**. Других рантаймов не будет.
* **LLM** — на выбор: Ollama (облако `https://ollama.com` либо локальный
  демон) или Claude (Anthropic API). Переключается без перезапуска —
  см. [раздел 3.22](#322-провайдеры-модели).

### 1.7 Конфигурация и секреты

Конфиг — **обычный TOML-файл**, никакого хранилища секретов, keyring или
шифрования. Токен Telegram и API-ключи провайдеров лежат в файле открытым текстом.

**Это осознанное упрощение**: система однопользовательская, работает на личной
машине, и цена правильного secret storage тут выше пользы. Компенсация —
файл в `.gitignore` и `chmod 600`.

Файл правится **тремя способами**, и все три работают с одним и тем же файлом:
руками в редакторе, из формы «Настройки» в окне, из раздела «⚙️ Настройки»
в Telegram. Поэтому запись обязана его не портить — см.
[раздел 3.5](#35-где-хранится-конфиг-и-что-применяется-на-лету).

Читает и пишет файл модуль `config-store`:

* `AppConfig` — снимок файла на момент старта. Каждый модуль берёт только свою
  секцию (`OllamaConfig.from(...)`, `TelegramConfig.from(...)`) и сам решает,
  что обязательно, а что имеет дефолт. Общего типизированного объекта настроек
  для чтения нет специально: новая секция не заставляет править `config-store`.
* `AppSettings` — те немногие значения, которые правятся из интерфейсов.
  Единственный источник правды в рантайме: и окно, и Telegram-меню меняют
  этот объект и подписаны на его изменения.
* `SettingsField` — перечисление этих значений: где лежит в TOML, секрет ли,
  и что происходит при смене (`LIVE` / `RECONNECT`). Оба интерфейса берут
  подписи и предупреждения отсюда, поэтому не могут разойтись в том, что
  обещают пользователю.

Порядок поиска конфига (первый существующий):

1. `-Dbebebe.config=/путь/config.toml`
2. `$BEBEBE_CONFIG`
3. `$XDG_CONFIG_HOME/bebebe-agent/config.toml` (обычно `~/.config/bebebe-agent/config.toml`)
4. `./config/agent.toml` — при разработке

Образец со всеми секциями: [`config/agent.example.toml`](config/agent.example.toml).

## 2. Что сделано

### 2.1 Сборка

Gradle 9.7.1 (Kotlin DSL), multi-module, 20 модулей, Java 25 через toolchain.
Версии библиотек — в одном месте: [`gradle/libs.versions.toml`](gradle/libs.versions.toml).

Общая конфигурация (toolchain, кодировка UTF-8, slf4j, JUnit 5) задана один раз
в корневом `build.gradle.kts` через блок `subprojects`.

### 2.2 `ollama-client` — реализован

Модуль исторически назван по первому провайдеру, но теперь в нём живёт
**слой провайдеров модели** (`com.bebebe.agent.llm`) и два его воплощения.
Ядро, консолидация памяти, инструменты и GUI знают только `LlmProvider`;
устройство и решения — [раздел 3.22](#322-провайдеры-модели).

| Класс (`llm`) | Что делает |
|---|---|
| `LlmProvider` | Контракт: `chat(LlmRequest)`, `listModels()`, `ping()`, `setModel`, `setApiKey`, `endpoint()`, `stats()` |
| `LlmRequest` / `LlmResponse` | Системный промпт, история, вопрос, `temperature`, JSON-схема → текст, токены, длительность |
| `LlmException` | Общий предок ошибок провайдеров; `OllamaException` — наследник |
| `OllamaProvider` | `LlmProvider` поверх `OllamaClient`: схема → `format`, `num_ctx`/`temperature` из `[ollama]` |
| `ClaudeProvider` | Anthropic Messages API через официальный Java SDK; схема → structured outputs |
| `ClaudeConfig` | Секция `[claude]`: `max_tokens`, таймаут, `temperature` |
| `SwitchableProvider` | Переключаемая обёртка: `pin()` на запрос, `switchTo(id)` для новых |
| `LlmProviders` | Фабрика из `AppConfig` + `AppSettings`: слоты `[llm.<id>]`, дефолтные endpoint и модель |

Ниже — HTTP-клиент к нативному API Ollama. Построен на `java.net.http.HttpClient`
из JDK — сторонних HTTP-библиотек нет. JSON — Jackson.

Работает и с облаком (`https://ollama.com`, Bearer-ключ), и с локальным
демоном (`http://localhost:11434`, без ключа) — отличается только конфиг.

| Класс (`ollama`) | Что делает |
|---|---|
| `OllamaClient` | `ask()`, `chat()`, `chatStream()`, `listModels()`, `ping()` |
| `OllamaConfig` | Разбор секции `[ollama]` (сам файл читает `config-store`) |
| `ChatRequest` | Билдер тела запроса: сообщения, `options`, `format`, `think` |
| `ChatResponse` | Разбор ответа, включая метрики (`tokensPerSecond()`) |
| `ChatMessage` | Сообщение диалога + `tool_calls` |
| `OllamaException` | Ошибки конфига, сети и HTTP с подсказками по коду |
| `OllamaStats` | Вызовы, токены, сбои за сессию и всего (JSON-файл); последний успех/сбой — «доступность» для статуса. Общий для обоих провайдеров, файл свой у каждого: `llm-stats-<id>.json` |

Детали, которые стоит знать:

* `stream` не хранится в `ChatRequest` — флаг выставляет сам клиент
  в зависимости от того, вызван `chat()` или `chatStream()`.
* Стрим — NDJSON: каждый чанк несёт **только новый кусок** текста,
  метрики приходят в последнем чанке с `done: true`.
* На 401/403/404/429 в сообщение исключения подставляется подсказка,
  что именно чинить.
* `api_key` валидируется на печатный ASCII: иначе JDK бросит невнятное
  `invalid header value` только на первом запросе.
* `OllamaConfig.toString()` не печатает ключ.
* **Имя модели пишется без суффикса `:cloud`.** Суффикс живёт только в CLI
  (`ollama run glm-5.3:cloud`); HTTP-API знает имена из `/api/tags` —
  `gpt-oss:120b`, `glm-5.3`, `qwen3.5:397b`. С `:cloud` запрос вернёт 404.

18 тестов гоняют клиента против локального HTTP-стаба
(`com.sun.net.httpserver`) — наружу тесты не ходят. `ClaudeProviderTest`
(5) точно так же поднимает стаб `/v1/messages` и `/v1/models`: проверяет
заголовки, тело со схемой, склейку истории в чередование ролей, разбор
401 и то, что без ключа сеть не трогается.

### 2.3 `config-store` — реализован

Выделен из `ollama-client`, когда конфиг понадобился второму модулю.

**Чтение.** `ConfigPaths` ищет файл по цепочке приоритетов; `AppConfig` читает
TOML один раз и держит снимок в памяти, `section(name)` отдаёт секцию,
отсутствующая секция — пустая, а не ошибка. `ConfigSection` даёт типизированные
геттеры (`requiredString`, `seconds`, `longSet`, …) и в сообщении об ошибке
всегда называет полный ключ вида `telegram.bot_token`.

**Запись.** `ConfigFileWriter` обновляет отдельные ключи, не переписывая файл
целиком. Файл правят и руками тоже, поэтому запись:

* **сохраняет комментарии** — читаем через `CommentedFileConfig`;
* **сохраняет порядок секций** — `preserveInsertionOrder()`;
* **не переформатирует файл** — `setIndent("")`, иначе night-config
  расставляет табы перед каждым ключом;
* **дописывает новые ключи в свою секцию**, а не в начало файла;
* **атомарна** — пишем во временный файл и переименовываем, чтобы оборванная
  запись не оставила конфиг без токенов;
* **сохраняет права файла** — `chmod 600` не должен потеряться, там секреты.

Два подводных камня, на которые ушло время:

* `FileConfig` по умолчанию пишет **асинхронно**, и `save()` без `.sync()`
  молча ничего не делает, если процесс не дождался записи.
* Блок комментариев привязывается к следующей записи, поэтому пустая строка
  между «шапкой» файла и первой секцией теряется. Сами комментарии целы.

**`AppSettings`** — живые настройки: провайдер модели и его слоты (ключ,
модель, endpoint — отдельно у Ollama и у Claude), токен бота, белый
список, проактивные подсказки. Изменение значения и запись на диск разделены:
`setXxx` меняет значение в памяти и оповещает подписчиков, `save()` сбрасывает
всё в файл. Секреты не попадают ни в логи, ни в `toString()`.

### 2.4 `agent-core` — цикл обработки готов

`AgentSwitch` — потокобезопасный флаг с подпиской и реестром хуков
(`AgentLifecycle`), см. [3.6](#36-хуки-жизненного-цикла).

`AgentCore.handle(UserMessage)` — полный цикл «решение → действие → ответ».
Устройство протокола, бюджета и промптов — [раздел 3.9](#38-как-агент-решает-и-действует).

| Класс | Что делает |
|---|---|
| `AgentCore` | Цикл обработки одного сообщения; скрипты выполняет через `ActionExecutor`, а не `ScriptRuntime` напрямую |
| `AgentDecision` / `DecisionType` | Разбор структурированного решения модели |
| `DecisionProtocol` | JSON-схема ответа и все системные промпты |
| `RequestBudget` | Потолок обращений к модели на один запрос |
| `UserMessage` / `MessageSource` | Общий тип входящего для всех каналов |
| `EntityResolver` | Кто из известных людей упомянут в сообщении |
| `MemoryConsolidator` | Извлечение фактов из лога, сопоставление имён, вопросы «тот же?» |
| `MemoryProtocol` | Схема и промпты извлечения, блок памяти для контекста |
| `ReminderService` | Хук `reminders`: постановка через инструмент, инъекция промпта при срабатывании, догон |
| `AgentWorker` | Единственный поток обработки `agent-worker`; каналы подают запрос и ждут; перезапускаем |

`tool_call` обрабатывается в `AgentCore.runTool`: инструмент получает
`ToolContext` с `LlmCaller`, который списывает **общий** бюджет сообщения.

`handle()` и `confirm()` **не исполняются в потоке вызывающего**: поллинг
Telegram, STT и тик планировщика подают запрос в `AgentWorker` и ждут ответа.
Так у зависания есть один известный поток, который можно прервать, не задев
канал — см. [3.18](#318-watchdog-зависание-против-падения).

### 2.5 `script-runtime` — реализован

Выполняет Python-скрипты, которые пишет модель.

| Класс | Что делает |
|---|---|
| `ScriptRuntime` | Сохраняет код, запускает, при нехватке пакета ставит и повторяет, пишет аудит |
| `PythonEnvironment` | venv (создаёт/переиспользует), `pip install`, список stdlib |
| `ResourceLimits` | Оборачивает запуск в `prlimit`: память, CPU, размер файла |
| `MissingModule` | Распознаёт нехватку зависимости в трассировке |
| `ScriptResult` | Код возврата, stdout, stderr, длительность; `toActionResult()` — общая форма для ядра |
| `LocalActionExecutor` | `ActionExecutor` автономной сборки поверх `ScriptRuntime`; `timeout()` = таймаут скрипта + 90 с на автоустановку |
| `ScriptConfig` | Секция `[scripts]` |

Решения, которые стоит помнить:

* **Отдельный venv, а не системный Python.** Зависимости ставятся
  автоматически, и им незачем попадать в системные пакеты. На Arch системный
  pip к тому же защищён PEP 668 и просто откажется ставить.
* **venv переиспользуется** между запусками: создание — пара секунд, а
  доустановленные пакеты должны копиться, а не теряться после каждого скрипта.
* **Каждый запущенный скрипт сохраняется** в `scripts_dir` и не удаляется:
  когда агент сделал что-то неожиданное, первым делом смотришь, какой именно
  код он выполнил.
* **stdout и stderr читаются раздельно.** stdout — результат скрипта, его
  увидит модель; stderr — трассировка, по ней ищется отсутствующий модуль.
  Слить их — значит подмешать диагностику в данные.
* **Список stdlib спрашивается у самого интерпретатора**
  (`sys.stdlib_module_names`), а не захардкожен: он меняется от версии
  к версии, а ошибка здесь привела бы к установке левого пакета с PyPI
  под именем модуля из stdlib.
* **Лимиты через `prlimit`, а не `ulimit`.** `ulimit` — встроенная команда
  оболочки, ради неё пришлось бы запускать скрипт через `bash -c`, то есть
  собирать командную строку текстом. `prlimit` — обычная программа: аргументы
  списком, `exec` цели, ничего не интерпретирует.
* **`RLIMIT_NPROC` не ставится намеренно.** Он считает процессы всего
  пользователя, а не потомков скрипта; лимит в 64 на машине с двумя сотнями
  процессов запретил бы скрипту делать хоть что-то. От fork-бомбы защищают
  таймаут и CPU-лимит.
* **От root не запускается.** Скрипт от модели с правами root — это уже
  не компромисс, а халатность: `ScriptRuntime` возвращает ошибку запуска
  и пишет `ERROR` при старте.
* **Каждый запуск — событие `script.audit`** в `script-runtime.log`: код,
  stdout, stderr, код возврата, длительность, установленные пакеты — под
  `trace_id` запроса. См. [3.11](#310-логи).

### 2.6 `script-library` — реализован

SQLite-индекс удачных скриптов плюс сами файлы на диске.

| Класс | Что делает |
|---|---|
| `ScriptLibrary` | CRUD по каталогу, версии, статистика, флаг подтверждения |
| `ScriptEntry` | Запись каталога |
| `ScriptSearch` | Поиск кандидатов по словам |
| `LibraryConfig` | Секция `[library]` |

* **Почему SQLite, а не JSON-файл.** Нужны выборки и счётчики, которые
  обновляются из разных потоков (поллинг Telegram, голос). Переписывать весь
  файл на каждый запуск скрипта — плохая идея; SQLite даёт это даром и не
  требует сервера.
* **Код лежит файлами, а не в базе:** его удобно смотреть и править руками,
  база остаётся индексом.
* **Старые версии не удаляются.** По ним видно, что именно чинили, и их
  статистика не смешивается с новой.
* **Имя скрипта приходит от модели и уходит в имя файла**, поэтому всё, кроме
  букв и цифр, превращается в дефис: `../../etc/passwd` → `etc-passwd`.

### 2.11 `telegram-bridge` — реализован

Long polling в одном фоновом потоке-демоне внутри общего процесса. HTTP —
`java.net.http`, сторонних telegram-библиотек нет: нужно шесть методов API,
своя обёртка дешевле зависимости.

| Класс | Что делает |
|---|---|
| `TelegramBridge` | Цикл поллинга, диспетчер сообщений и нажатий |
| `TelegramApi` | `getMe`, `getUpdates`, `sendMessage`, `sendVoice` (multipart), `editMessageText`, `editMessageReplyMarkup`, `answerCallbackQuery` |
| `TelegramConfig` | Секция `[telegram]` |
| `AccessControl` | Белый список |
| `menu/CallbackData` | Кодирование и разбор `callback_data` с проверкой лимита |
| `menu/MenuSection` | Разделы корневого меню |
| `menu/MenuRenderer` | Чистые функции «состояние → экран» |
| `menu/MenuController` | Обработка нажатий, без сети |
| `menu/ReminderScreens` | Экраны раздела «⏰ Напоминания» |
| `menu/NotesScreens` | Экраны раздела «📝 Заметки и списки» |
| `menu/PersonaScreens` | Экраны раздела «🎭 Персоны» |
| `menu/StatusScreens`, `menu/LogScreens`, `menu/ServerStatus` | Headless-режим: «📊 Статус» и «📜 Логи» из снимка сервера и `LogBuffer` |
| `input/PendingInputs` | Режим ожидания текстового ввода |

**Белый список.** Проверка стоит на самом входе — до разбора команд и до
обращения к агенту. Пустой список означает «не отвечать никому»: сломанный
конфиг делает бота немым, а не публичным. Совпадение достаточно по одному из
двух — `allowed_usernames` (без учёта регистра и `@`) или `allowed_chat_ids`.
На каждое отклонённое сообщение пишется `WARN` с id отправителя и чата — это
единственный способ узнать свой `chat_id`.

**Ответ модели уходит без `parse_mode`.** В тексте от LLM легко оказывается
ломаный HTML, и Telegram отверг бы всё сообщение. Текст меню, наоборот, идёт
с `parse_mode=HTML` — он целиком задан в коде, пользовательского ввода там нет.

#### Схема `callback_data`

Telegram отводит под это поле **1–64 байта UTF-8** и при превышении отвергает
**всё сообщение** с `BUTTON_DATA_INVALID` — то есть меню просто не отправится,
а причина будет неочевидна. Поэтому лимит проверяется в `CallbackData` при
сборке кнопки: ошибка вылезает в тестах, а не в рантайме у пользователя.

Формат — сегменты через двоеточие:

```
<namespace>:<part>[:<part>...]
```

| Значение | Что делает |
|---|---|
| `nav:root` | Корневое меню (кнопка «⬅️ Назад») |
| `nav:close` | Закрыть меню |
| `nav:noop` | Кнопка без действия |
| `menu:power` … `menu:personas` | Открыть раздел |
| `pwr:set:on` / `pwr:set:off` | Включить / выключить агента |
| `pwr:window` | Показать окно приложения (крестик его только прячет) |
| `set:prov:<id>` | Переключить провайдера модели (`ollama` / `claude`) |
| `set:model` | Список моделей |
| `set:model:pick:<i>` | Выбрать модель **по индексу** в показанном списке |
| `set:user` | Список разрешённых username |
| `set:user:add` | Попросить username текстом |
| `set:user:rm:<i>` | Удалить username по индексу |
| `set:hints:on` / `set:hints:off` | Проактивные подсказки |
| `set:voice:on` / `set:voice:off` | Голосовые ответы |
| `set:live:on` / `set:live:off` | Несколько коротких сообщений |
| `set:typing:on` / `set:typing:off` | Индикатор «печатает…» |
| `set:scripts:on` / `set:scripts:off` | Разрешить / выключить скрипты |
| `set:backup` | Собрать бэкап и прислать файлом — обрабатывает сам бридж, не контроллер |
| `cfm:run:<tok>` / `cfm:no:<tok>` / `cfm:trust:<id>` | Подтверждение запуска |
| `cfm:list:<p>` / `cfm:tgl:<id>:<p>` | Раздел «Подтверждения» |
| `mem:people:<p>` / `mem:person:<id>:<p>` | Люди и карточка |
| `mem:fdel:<fact>:<id>:<p>` / `mem:pdel:<id>[:ok]` | Удалить факт / человека |
| `mem:forget[:<what>[:ok]]` | Забыть: `session`, `sessions`, `facts`, `all` |
| `mem:res:<tok>:same\|new` | Ответ на «тот же человек или новый?» |
| `rem:active:<p>` / `rem:history:<p>` | Напоминания: активные и история, постранично |
| `rem:view:<id>:<p>` / `rem:cancel:<id>:<p>` | Карточка напоминания и его отмена |
| `rem:clear[:ok]` | Очистить историю (с подтверждением) |
| `nt:new[:list\|note]` | Заметки: «➕ Создать» → выбор вида → ждём название текстом |
| `nt:list:<p>` / `nt:open:<id>:<p>[:<ip>]` | «📂 Загрузить» постранично / карточка документа |
| `nt:tgl:<id>:<i>:<p>:<ip>` | Переключить чекбокс пункта `i` (`ip` — страница пунктов) |
| `nt:rmm:<id>:<p>:<ip>` / `nt:rm:<id>:<i>:<p>:<ip>` | Режим удаления пунктов / удалить пункт |
| `nt:add:<id>:<p>` | Ждём текст: новый пункт или абзац заметки |
| `nt:drop:<id>:<p>[:ok]` | Удалить документ (с подтверждением) |
| `per:act:<id>` / `per:view:<id>` | Персоны: сделать активной (кнопка в списке) / карточка |
| `per:new` / `per:edit:<id>` | Ждём текст: имя новой персоны / текст инструкции |
| `per:del:<id>[:ok]` | Удалить (с подтверждением) |
| `log:<e\|w\|a>:<p>` | Логи (headless): фильтр ERROR / WARN+ / все и страница |

Правила, которых стоит держаться дальше:

* **В кнопку кладут идентификаторы, а не значения.** Длинный текст (имя
  персоны, текст заметки) хранится в процессе, в `callback_data` уходит
  короткий id: `mem:person:42:delete`.
  Живой пример — выбор модели: имена вроде `mistral-large-3:675b` содержат
  двоеточие (разделитель схемы!) и легко съедают бюджет, поэтому в кнопку
  уходит **номер строки**, а сам список кэшируется в `MenuController`.
  Плата за это — список может устареть после перезапуска процесса; тогда
  нажатие отвечает «Список устарел, откройте заново», а не делает что попало.
* Идентификаторы разделов — только строчная латиница, это проверяется тестом.
* Порог `WARN_BYTES = 48` — тест требует, чтобы навигация укладывалась в него
  с запасом, оставляя место под будущие аргументы.
* Кириллица в UTF-8 занимает 2 байта на символ, поэтому лимит считается
  **в байтах, а не в символах** — на это есть отдельный тест.

#### Как работает меню

`/start` и `/menu` присылают **новое** сообщение с корневым меню. Дальше
навигация — это **правка того же сообщения** (`editMessageText`), а не новые
сообщения в чате: переход в раздел и обратно не засоряет историю. На каждом
подменю есть «⬅️ Назад» (`nav:root`) и «✖️ Закрыть»; закрытие — это тоже правка,
текст меняется на «Меню закрыто», клавиатура убирается.

Несколько решений, которые стоит помнить:

* **Кнопка питания несёт желаемое состояние (`pwr:set:on`), а не «переключи».**
  Иначе нажатие на устаревшую кнопку — состояние уже сменили из GUI — дало бы
  результат, обратный нарисованному на кнопке.
* **`answerCallbackQuery` вызывается всегда**, даже с пустым текстом: пока
  ответа нет, Telegram крутит на кнопке часики.
* **Ошибка «message is not modified» — не ошибка.** Пользователь нажал кнопку
  уже открытого раздела; `TelegramApiException.isNotModified()` это отделяет.
* **Меню работает и при выключенном агенте** — иначе включить его обратно из
  чата было бы нечем.
* Бридж помнит, какое сообщение с меню открыто в каждом чате и на каком оно
  экране, и перерисовывает его, когда флаг переключили снаружи (из GUI).

#### Раздел «⚙️ Настройки»

Зеркалит форму настроек в окне, но **без секретов**: токена бота и API key
провайдера в чате нет вовсе, только пометка «задан / не задан». Причина — сообщения
остаются в истории чата и на серверах Telegram, и отправлять туда токен,
которым этот же бот и живёт, незачем.

| Настройка | Как правится в чате |
|---|---|
| 🤖 Провайдер | Кнопка «Переключить на Claude / Ollama»; если у целевого провайдера пустой ключ — подсказка об этом, но переключение проходит |
| Модель (текущего провайдера) | Список кнопок; перечень тянется у провайдера (`/api/tags` у Ollama, `/v1/models` у Claude) |
| Разрешённые username | Список с корзинами + «➕ Добавить» через режим ожидания текста |
| Проактивные подсказки | Кнопка-тумблер |
| Голосовые ответы | Кнопка-тумблер |
| Несколько коротких сообщений | Кнопка-тумблер |
| Индикатор «печатает…» | Кнопка-тумблер (независим от предыдущего) |
| 🐍 Скрипты | Кнопка-тумблер: выключает выполнение скриптов целиком |
| 💾 Бэкап (без секретов) | Кнопка: архив приходит документом в чат |
| Токен бота, API key провайдера, Endpoint URL | **Недоступны** — только в окне |

Каждое изменение сразу пишется в `config.toml`. Если записать не вышло
(например, конфига нет на диске), значение всё равно применяется в памяти,
а подсказка на кнопке договаривает «(не сохранено в файл!)» — нажатие
игнорировать хуже, чем применить без сохранения.

Список моделей за собой тянет сетевой вызов прямо в потоке поллинга. Он
быстрый, но если провайдер недоступен — экран покажет это текстом, а не упадёт.

#### Режим ожидания текстового ввода

Часть настроек кнопками не задать — имя модели, путь к файлу, текст заметки.
Сценарий: бот просит прислать значение и ставит чат в режим ожидания;
**следующее** текстовое сообщение перехватывается как ответ на конкретное поле
и не уходит агенту как обычный вопрос.

```java
bridge.pendingInputs().await(chatId, PendingInput.of(
        "ollama.model",              // что ждём — уходит в логи
        "Пришлите имя модели",       // чем спросили
        menuMessageId,               // какое меню перерисовать после ввода
        value -> InputOutcome.accepted("Принято: " + value,
                CallbackData.section(MenuSection.SETTINGS))));
```

* Ожидание одно на чат, новое вытесняет старое.
* TTL 5 минут: забытый режим не должен съесть обычное сообщение через час.
* `InputOutcome.rejected(...)` оставляет режим включённым и просит ввести заново.
* `/cancel` снимает режим.
* Команды (`/…`) через режим ожидания **не** перехватываются — иначе из него
  нельзя было бы выйти.

Первый живой потребитель — кнопка «➕ Добавить» в разделе «Настройки».
Контроллер меню не знает ни номера чата, ни номера сообщения, поэтому он лишь
возвращает `InputRequest` («жду вот такое значение, вот обработчик»),
а собирает `PendingInput` и регистрирует его уже бридж.

#### Тесты бриджа

93 теста, все офлайн. `TelegramStubServer` поднимает локальный
`com.sun.net.httpserver` и притворяется `api.telegram.org`: отдаёт заранее
положенные обновления и записывает всё, что бридж прислал в ответ. Благодаря
этому проверяется не только логика меню, но и весь путь целиком — длинный
поллинг, белый список, правка сообщения, `answerCallbackQuery` — без единого
обращения в интернет.

### 2.12 `stt-bridge` — реализован

Push-to-talk: держишь клавишу — говоришь, отпустил — агент отвечает.
Всё локально, аудио не покидает машину.

```
evdev-хелпер  DOWN -> arecord пишет WAV (16 кГц моно 16 бит)
              UP   -> arecord останавливается
                   -> whisper.cpp расшифровывает
                   -> UserMessage(VOICE) тем же путём, что и текст из Telegram
```

| Класс | Что делает |
|---|---|
| `SttBridge` | Склейка цепочки, учёт ON/OFF |
| `capture/HotkeyListener` | Запускает нативный хелпер, читает из его stdout `DOWN`/`UP` (переехал в модуль `capture`, конфиг — `HotkeyConfig`) |
| `AudioRecorder` | `arecord` во временный WAV (интерфейс `Recorder`) |
| `WhisperTranscriber` | `whisper-cli`, разбор вывода (интерфейс `Transcriber`) |
| `SttConfig` | Секция `[stt]`, проверка «всё ли на месте» (`whatIsMissingForTranscription` — без evdev, для сервера) |
| `TranscriptionPipeline` | Общий хвост: WAV → whisper → `UserMessage(VOICE)`; отдельный поток, файл удаляется всегда |
| `RemoteVoiceIngest` | Голос от тонкого клиента (байты WAV) — в тот же пайплайн; порог короткой записи и флаг ON/OFF те же |

Решения, которые стоит помнить:

* **Флаг ON/OFF проверяется до записи, а не после.** Писать микрофон и гонять
  whisper, чтобы потом выбросить результат, бессмысленно.
* **Запись останавливается через SIGTERM** (`Process.destroy()`): `arecord`
  при этом корректно дописывает в WAV заголовок с длиной. Проверено —
  файл после SIGTERM валиден и содержит ровно записанное.
* **Расшифровка уходит в отдельный поток.** whisper на длинной записи работает
  секунды, а поток чтения хелпера обязан оставаться свободным, иначе следующее
  нажатие клавиши потеряется.
* **Слишком короткие записи отбрасываются** (< 8000 байт ≈ 0.25 с) — это почти
  наверняка случайное задевание клавиши.
* **Временный WAV удаляется всегда**, в том числе при ошибке: это запись голоса,
  ей незачем копиться на диске.
* **Почему `arecord`, а не `javax.sound.sampled`:** JDK-шный стек звука под
  Linux на системах с PipeWire ведёт себя непредсказуемо — то не видит
  устройств, то держит их эксклюзивно. `arecord` работает поверх PipeWire
  как обычный клиент.

Куда уходит ответ: в **последний активный чат Telegram** — сначала «🎤
распознанный текст», затем ответ текстом и, если включены голосовые ответы,
голосовым сообщением (см. [3.17](#317-голосовые-ответы-tts)). Отдельного
«озвучить в колонки» нет: пользователь может быть не у машины, а чат он
увидит везде.

### 2.13 `tts-bridge` — реализован

Озвучка ответов. Всё локально: Piper синтезирует WAV, ffmpeg перекодирует

| Класс | Что делает |
|---|---|
| `TtsBridge` | `synthesize(text) → Optional<Path ogg>`: piper (stdin) → wav → ffmpeg → ogg |
| `SpeechText` | Чистит текст для голоса: markdown, ссылки, код, эмодзи; режет по предложению |
| `TtsConfig` | Секция `[tts]`, проверка «всё ли на месте» |

Устройство, установка Piper и поведение тумблера — [раздел 3.17](#317-голосовые-ответы-tts).

### 2.15 GUI — каркас

JavaFX 27 + AtlantaFX (тема `PrimerDark`).

* **Верхняя панель** (`AgentToggleBar`) — индикатор состояния, «дышащий»
  маркер активности с подписью, чем занят агент, и анимированный тумблер
  ON/OFF (`PowerSwitch`). Видна из любого раздела.
* **Статус** (`StatusPane`) — ON/OFF, последняя ошибка из буфера логов,
  доступность Ollama по факту последнего вызова, счётчики вызовов/токенов
  за сессию и всего, свободное место на диске, версия сборки, результат
  проверки обновлений, перезапуски watchdog, кнопки «Проверить обновления»
  и «Экспорт/бэкап…». Обновляется раз в 2 секунды. См. [3.19](#319-статус-логи-версия-и-бэкап).
* **Логи** (`LogsPane`) — живая лента из `LogBuffer` с фильтрами по уровню,
  подсистеме, `trace_id` (двойной клик по строке подставляет её `trace_id`)
  и тексту; выпадающий список уровня логирования применяется сразу
  и пишется в `[logging] level`.
* **Настройки** (`SettingsPane`) — форма поверх того же `AppSettings`,
  который правит и Telegram-меню; здесь же тумблеры «Голосовые ответы»,
  «Несколько коротких сообщений» и «Индикатор «печатает…»».
  Секреты — только здесь. Форма не применяет
  значения по мере набора: пока не нажата «Сохранить», это черновик, иначе
  каждая промежуточная буква в поле модели уезжала бы в файл.
* **Персоны** (`PersonasPane`) — список слева (активная с ✅), справа имя
  и текст инструкции; «Сохранить» (создать или править), «Новая», «Сделать
  активной», «Удалить». Тот же `PersonaStore`, что у Telegram-меню: смена
  в чате перерисовывает список здесь через слушатель и `Platform.runLater`.
* **Заметки** (`NotesPane`) — слева документы (недавние первыми), справа
  список с чекбоксами (Enter в поле — новый пункт, ✖ — убрать) или текст
  заметки с кнопкой «Сохранить» (правка целиком, не по буквам: каждая запись —
  коммит). «Новый список / Новая заметка» — диалог названия. Тот же
  `NotesStore`, что у `notes_tool` и Telegram; правка из чата или Obsidian
  перерисовывает окно через слушатель хранилища.
* **Тест агента** (`AgentTestPane`) — поле промпта, кнопка «Отправить»,
  кнопка «Проверить связь» (`ping()` + список моделей **текущего провайдера**:
  в ответе — его имя и endpoint), область ответа и скорость генерации.
  Сеть уходит в отдельный поток, JavaFX-поток не блокируется. Раньше экран
  назывался «Ollama (тест)»; переименован, когда провайдер перестал быть один.

Кнопка ON/OFF уводит переключение в фоновый поток: хуки жизненного цикла
синхронные, и когда в них появится реальная работа, окно не должно на ней
подвисать.

#### Единый стиль экранов

Все разделы собираются из одних кирпичей класса `Ui` (`ui/Ui.java`):
`Ui.page(...)` — вертикальный стек с отступом 24 и промежутком 12;
`Ui.header(title, subtitle)` — заголовок `TITLE_2` и одна приглушённая строка
о том, что здесь; `Ui.section(...)` — подзаголовок блока (`TITLE_4`);
`Ui.caption(...)` — подпись к полю (`TEXT_MUTED`); `Ui.hint(...)` — пояснение
(`TEXT_SUBTLE`, перенос, ширина ≤ 640); `Ui.separator()`, `Ui.spacer()`,
`Ui.status()` — строка результата под кнопками. Цвета — только токены
AtlantaFX (`-color-success-emphasis`, `Styles.DANGER` и т.д.), захардкоженных
hex нет нигде, кроме дорожки тумблера (`PowerSwitch`: Primer `#238636` /
`#da3633`, те же, что у кнопок темы, — `FillTransition` умеет только `Color`).
Заглушка нереализованного раздела («Заметки») строится тем же `Ui.header`,
чтобы не выглядеть чужой.

Новый экран: `extends VBox`/`ScrollPane`/`BorderPane`, первая строка —
`Ui.header(TITLE, "…")`, дальше `Ui.section` для блоков, все кнопки в `HBox(10)`,
итог действия — в `Ui.status()`. Долгие операции (сеть, файлы) — в отдельном
потоке-демоне, результат обратно через `Platform.runLater`.

#### Анимации

Все в `Transitions` (одни длительности на всё окно, чтобы новый экран не
изобретал свои) плюс две специальные в верхней панели:

| Где | Что | Как |
|---|---|---|
| Смена раздела | `Transitions.swap(host, node)` | старый гаснет 120 мс (`EASE_IN`) → новый проявляется 200 мс и подъезжает снизу на 12 px (`EASE_OUT`). Узлы разделов создаются один раз и переиспользуются — иначе анимировать нечего |
| Смена подписи | `Transitions.crossfadeText(label, text)` | гаснет → текст → проявляется; тот же текст — ничего. Используется для «включён/выключен», подсказок, статуса на «Статусе» |
| Появление | `Transitions.fadeIn(node)` | 200 мс из нуля — для элементов, которые только что добавили |
| Тумблер ON/OFF | `PowerSwitch` | бегунок переезжает (`TranslateTransition`, 220 мс, `EASE_BOTH`), дорожка перекрашивается (`FillTransition`) одновременно; первый показ — без анимации. Пока хуки работают в фоне — тумблер полупрозрачен и не принимает клики, подпись «включаю…/выключаю…» |
| Активность | пульс в `AgentToggleBar` | `ScaleTransition` 1→1,45 + `FadeTransition` 1→0,4, 900 мс, автореверс, бесконечно — пока `ActivityMonitor.inFlight()` не пуст (опрос раз в 300 мс). Подпись — из сигнала занятости: «думает…» (ответ модели), «выполняет скрипт «…»…», иначе «обрабатывает запрос…». По завершении — не стоп-кадр с середины цикла, а плавный возврат к масштабу 1 и полной непрозрачности за 200 мс, подпись гаснет |

Правила: коротко (120–220 мс, пульс — 900), без отскоков и `BOUNCE`;
анимируем только `opacity`, `translate`, `scale` и заливку фигур — они не
трогают раскладку и дёшевы; состояние никогда не хранится в анимации
(тумблер показывает флаг, а не «то, что нажали»); индикатор активности читает
`ActivityMonitor` опросом, а не подпиской, — монитор живёт в потоке обработки
и не должен знать про JavaFX.

#### Крестик прячет окно; один процесс на пользователя

`Platform.setImplicitExit(false)` + `setOnCloseRequest → hide()`: закрытие
окна **не** завершает агента — Telegram, напоминания и голос живут дальше.
Завершить — «Завершить агента» на «Статусе» (с подтверждением; exit 0,
systemd не перезапускает), пункт в трее или `systemctl --user stop server-ai-agent`.

Вернуть окно:

| Как | Механика |
|---|---|
| Запустить приложение ещё раз (ярлык GNOME, стартовый скрипт) | `SingleInstance`: Unix-сокет `$XDG_RUNTIME_DIR/bebebe-agent.sock`. Первый процесс слушает; второй подключается, шлёт `show` и выходит за полсекунды. Заодно второй экземпляр невозможен (иначе 409 от Telegram и занятые базы). Протухший сокет после `kill -9` распознаётся по отказу подключения и перезанимается |
| Telegram → ⚡ Питание → «🪟 Показать окно» | `pwr:window` → `UiContext.showWindow()` |
| Иконка в трее | Только если трей есть: `TrayIconSupport` через AWT поверх XWayland, пункты «Показать окно» / «Завершить агента». **На этой машине трея нет**: GNOME без расширения AppIndicator (`gnome-shell-extension-appindicator`) не показывает иконки вовсе, `SystemTray.isSupported()` = false, в логе об этом одна строка. Поставить расширение — иконка появится без правок кода |

Ярлык — [`desktop/server-ai-agent.desktop`](desktop/server-ai-agent.desktop),
установлен в `~/.local/share/applications/` (`Path=` и `Exec=` абсолютные,
шаблон подставляется `sed`, см. комментарий в файле).

Зависимости в окно передаются через `UiContext` — статический холдер,
заполняемый в `SupervisorMain` до `Application.launch`. JavaFX создаёт
`Application` сам, через конструктор без аргументов, поэтому иначе никак;
полноценного DI в проекте нет и не планируется.

подключение того же клиента вытесняет старое, после перезапуска сервера
клиент возвращается сам, паузы растут. Плюс кодек, хранилище токенов
(хэш на диске, права 600), сертификат и backoff.

`AgentDecisionTest` (30) — терпимость разбора: markdown-обёртка, регистр
и пробелы в `type`, теги строкой, мусор вместо номера, вложенная форма,
угадывание типа без `type`, что схема требует `type` и не предлагает
`unknown`. `JobRunnerTest` (24) — догон отдельно: чуть опоздавшее идёт
обычным, просроченное — `MISSED`; тик сразу после догона не стреляет тем же;
обработчик получает «сейчас», а не время срабатывания; отменённое не
догоняется; перенос сохраняет номер; ежедневное после двух дней простоя
догоняется один раз и ставится на завтра. `ScriptRuntimeTest` (17) —
без автоустановки нехватка модуля уходит модели как есть, stdlib-имя
не тянет pip, 600 КБ в оба потока не вешают процесс (раздельное чтение),
скрипт видит `$HOME` пользователя (компромисс 3.8.5 зафиксирован тестом).
`ScriptLibraryTest` (16) — новая версия спрашивает подтверждение заново
даже после «больше не спрашивать», пропавший файл не роняет каталог,
одноимённые скрипты — разные корни. `MemoryStoreTest` (24) — хвост
консолидации после отметки, алиасы без дублей и без имени, каскад при
удалении факта, «забыть факты» считает факты, а не строки связей
(`executeUpdate` у sqlite-jdbc прибавляет каскад — это был баг в ответе меню).

`LiveRepliesTest` — массив `messages` в протоколе (разбор, склейка,
вывод типа), поле в схеме только при тумблере, реплики при включённом стиле
и склейка при выключенном, разрез свободного ответа по `---`; в
`TelegramBridgeTest` — реплики по очереди с `sendChatAction`, паузы
не короче минимума, голосовое одно.

`EndToEndScenariosTest` (`supervisor-app`) — восемь сквозных сценариев
на **том же графе, что поднимает приложение** (`AgentAssembly`): настоящий
Telegram-бридж против локального стаба Telegram, настоящее ядро против стаба
Ollama, настоящий Python, SQLite, файлы заметок; подменены только внешний мир,
часы и озвучка. Список — [3.21](#321-сквозные-сценарии-и-известные-шероховатости).

`WebSearchToolTest` гоняет поиск целиком со скриптованной моделью, поддельным
провайдером и локальным HTTP-сервером вместо страниц; `ToolCallFlowTest`
проверяет, что «болтливый» инструмент упирается в общий бюджет.

`ReminderFlowTest` гоняет напоминания сквозь ядро с подменяемыми часами:
`set_reminder` от стаба модели создаёт задание в том же разговоре, тик подаёт
`SYSTEM`-сообщение и ответ уходит в тот же чат, выключение останавливает тик,
включение после простоя шлёт догоняющий промпт со словами «не сработало»,
ежедневное переставляется на завтра. `JobRunnerTest` проверяет сам тик:
допуск опоздания, скачок времени, повторы, «пометить до вызова обработчика».

`NotesStoreTest` гоняет **настоящий git** во временном каталоге: первый
запуск делает `git init`, каждое изменение — коммит, файл, дописанный
«в Obsidian», подхватывается переиндексацией. `NotesFlowTest` проверяет
сквозь ядро, что «запиши в список задач» создаёт файл без подтверждения,
а при двух похожих списках модель получает варианты и спрашивает.

`UpdateCheckerTest` поднимает локальный сервер вместо GitHub: путь запроса
собирается из коммита сборки и ветки, `Bearer`-токен уходит в заголовок,
уведомление — один раз на коммит, ошибка API — статус с подсказкой, а не
исключение. `BackupServiceTest` собирает настоящий zip: SQLite внутри
читается, секреты из TOML вырезаны, `.git` заметок не попадает.

`WatchdogFlowTest` — на настоящем потоке и настоящем Python: инструмент,
который спит без heartbeat, через 90 «секунд» (время подменяется в `check`)
признаётся зависшим — поток перезапущен, зависший запрос закрыт молча,
уведомление ушло в `TELEGRAM:1`, следующий запрос обслужен новым потоком;
ожидание модели и скрипт под сигналом занятости зависанием не считаются;
выключение ждёт двухсекундный скрипт и отдаёт его ответ, а пятидесятисекундный
прерывает после льготных двух секунд. `WatchdogTest` перебирает сами условия.

`TtsBridgeTest` подменяет Piper и ffmpeg shell-скриптами: текст уходит
в stdin уже очищенным, модель — полным путём, ffmpeg получает `-c:a libopus`.
В `TelegramBridgeTest` `TelegramStubServer` разбирает multipart `sendVoice`:
проверяется, что при включённом тумблере после текста уходит `audio/ogg`,
при выключенном — нет, а ответ на текстовое сообщение озвучивается только
с `tts.reply_to_text`.

`PersonaFlowTest` проверяет сквозь ядро, что активная персона попадает
в системный промпт и решения, и формулировки, что переключение действует на
следующий же ответ, и что буфер обмена ложится в лог сессии источником
`CLIPBOARD` и виден в истории следующего запроса. `ClipboardBridgeTest`
подменяет `wl-paste` shell-скриптом и проверяет флаги (`--no-newline --type text`).

`MemoryIntegrationTest` проверяет главное про память по реальным запросам
к стабу модели: лог сессии уходит предыдущими репликами целиком, факты
упомянутого человека — в системный промпт, чужие — нет, выключение
консолидирует и закрывает сессию, вопрос «тот же?» уходит в тот разговор,
откуда пришёл.

`TraceIdPropagationTest` проверяет главное обещание логов по реальным событиям
logback: один запрос — один `trace_id` в ядре и в скриптах, включая паузу на
подтверждение. `ResourceLimitsTest` гоняет настоящий `prlimit`.

`script-runtime` гоняет **настоящий** Python в настоящем venv — подделывать
там нечего, проверяется именно взаимодействие с интерпретатором. Сеть при этом
не нужна: автоустановка проверяется на детекторе, а не походом в PyPI.
`agent-core` работает против локального стаба `/api/chat`.

В `stt-bridge` нативный хелпер и whisper.cpp подменяются shell-скриптами:
тесты проверяют протокол (`DOWN`/`UP`), флаги запуска и разбор вывода, а не
работу с реальным железом — для неё нужны права на `/dev/input`, микрофон
и модель на гигабайты.

### 2.17 Логирование — реализовано

slf4j везде, logback — только в модуле `logging`. Файлы — JSON-строки одного
формата с общим `trace_id` на запрос, по подсистемам, с ротацией и сжатием.
Уровень — из конфига, с точечными переопределениями. Подробно —
[раздел 3.11](#310-логи).

| Класс | Что делает |
|---|---|
| `TraceContext` | `trace_id` в MDC: открыть область, перенести в другой поток |
| `JsonLayout` | Одна запись — один JSON-объект с фиксированными полями |
| `AppLogging` | `bootstrap()` до конфига, `applyConfig()` после, `setLevel()` на лету |
| `LogBuffer` / `LogBufferAppender` / `LogEntry` | Кольцевой буфер последних 3000 строк в памяти: экран «Логи» и «последняя ошибка» |
| `logback.xml` | Аппендеры по подсистемам, ротация, `.gz`, `BUFFER` на root |

## 3. Как собрать и запустить

### 3.1 Требования

* JDK 25 (в системе — `openjdk 25`)
* Gradle не нужен: в репозитории есть wrapper

### 3.2 Конфиг

Руками ничего копировать не обязательно: если конфига нет ни в одном из мест
поиска, а рядом лежит `config/agent.example.toml`, **первый запуск сам создаст
`config/agent.toml`** (права `600`) и напишет об этом `WARN` в лог. Дальше
ключи, модель, токен и белый список заполняются в окне → «Настройки». Запись
из интерфейсов работает только поверх существующего файла (чтобы не терять
комментарии и незнакомые ключи), поэтому без этого шага форме было бы некуда
сохранять. Пошагово для чистой машины — [`README.md`](README.md).

Вручную то же самое:

```bash
cp config/agent.example.toml config/agent.toml
chmod 600 config/agent.toml
$EDITOR config/agent.toml
```

Заполнить минимум:

```toml
[ollama]
api_key = "..."          # https://ollama.com/settings/keys
model = "gpt-oss:120b"   # имя из /api/tags, БЕЗ суффикса :cloud

[telegram]
bot_token = "..."               # от @BotFather
allowed_usernames = ["ВашНик"]  # пустой список = бот молчит для всех
```

Для работы без облака:

```toml
[ollama]
base_url = "http://localhost:11434"
api_key = ""
model = "llama3.2"
```

### 3.3 Как включить и выключить агента

ON/OFF — **один флаг** `AgentSwitch` в памяти процесса. Два интерфейса
переключают именно его, а не свои копии состояния:

| Откуда | Как |
|---|---|
| Окно | Кнопка «Включить» / «Выключить» в верхней панели |
| Telegram | `/menu` → **⚡ Питание** → кнопка-тумблер |

Синхронизация двусторонняя и наблюдаемая:

* переключили в окне → бридж подписан на флаг и **перерисовывает открытое
  меню** в Telegram, чтобы кнопка там не врала;
* переключили в Telegram → окно подписано на тот же флаг и обновляет панель
  и раздел «Статус» через `Platform.runLater`.

Что делает выключенный агент:

* на любой текст и на голосовое отвечает коротким «агент выключен» и **не
  дёргает модель**;
* меню и все его кнопки продолжают работать — иначе включить агента обратно
  из чата было бы нечем.

Стартовое состояние задаётся в конфиге: `[agent] enabled_on_start`.

### 3.5 Где хранится конфиг и что применяется на лету

Один файл `config.toml` (см. [1.5](#17-конфигурация-и-секреты)) и три способа
его править — редактор, форма в окне, раздел «⚙️ Настройки» в чате. Запись
из интерфейсов сохраняет комментарии и не трогает ключи, которых она не знает.

| Настройка | Где правится | Что происходит при смене |
|---|---|---|
| `llm.provider` | Окно, Telegram | **На лету.** Следующий запрос идёт на новый провайдер; текущий доводится на старом — см. [3.22](#322-провайдеры-модели) |
| `llm.<id>.model` | Окно, Telegram | **На лету.** Правится модель выбранного провайдера; следующий запрос идёт с ней |
| `llm.<id>.api_key` | **Только окно** | **На лету.** У Ollama меняется заголовок, у Claude пересобирается SDK-клиент |
| `llm.<id>.endpoint` | **Только окно**, «Для продвинутых» | **Пересоздание провайдера.** Пусто — стандартный адрес провайдера |
| `telegram.allowed_usernames` | Окно, Telegram | **На лету.** Действует со следующего входящего сообщения |
| `agent.proactive_hints` | Окно, Telegram | **На лету.** Пока только хранится |
| `tts.voice_replies` | Окно, Telegram | **На лету.** Проверяется на каждой доставке ответа |
| `agent.live_replies` | Окно, Telegram | **На лету.** Ядро читает на каждом запросе |
| `telegram.typing_indicator` | Окно, Telegram | **На лету.** Бридж проверяет на каждом входящем и между репликами |
| `agent.scripts_enabled` | Окно, Telegram | **На лету.** Выключено — модель о скриптах не знает вовсе: в схеме и промпте решения нет ни скриптовых типов, ни их полей, каталог не ищется; на просьбу сделать что-то на компьютере модель отвечает текстом, что действия отключены. Ничего не запускается ни локально, ни на клиенте Этапа 2 — см. [3.8.7](#387-скрипты-выключены-протокол-без-действий). Нужно, когда модель принимает обычные сообщения за задания |
| `telegram.bot_token` | **Только окно** | **Переподключение.** Бридж останавливает поллинг, `offset` сбрасывается, соединение поднимается заново — пару секунд бот не отвечает |

Всё остальное в файле (таймауты, `temperature`, `num_ctx`, `claude.max_tokens`, `request_budget`,
**вся секция `[stt]`** — клавиша, устройство, пути к whisper.cpp и модели,
**вся секция `[scripts]`** — venv, таймаут, автоустановка,
**остальное в `[tts]`** — Piper, голос, ffmpeg, `reply_to_text`,
**`[watchdog]`** — интервал проверки и таймаут зависания, `agent.stop_grace_seconds`,
**вся секция `[library]`**, **`[memory]`**, **`[scheduler]`** — база,
интервал тика, допуск опоздания, уведомления, **`[notes]`** — каталог
и git, **`[tools.*]`**, **`[updates]`**, **`[logging]`** — каталог
(уровень — исключение: он меняется на лету с экрана «Логи» и пишется
в конфиг), `enabled_on_start`)
**требует перезапуска процесса**: эти значения читаются один раз на старте
и в `AppSettings` не заведены.

Почему секреты только в окне: сообщения Telegram остаются в истории чата и на
серверах Telegram, и отправлять туда токен, которым живёт этот же бот, незачем.
В чате они видны как «задан / не задан».

Синхронизация между интерфейсами двусторонняя: правка в окне перерисовывает
открытый в чате раздел «Настройки», правка в чате обновляет форму в окне.
Оба работают с одним объектом `AppSettings`.

### 3.6 Хуки жизненного цикла

`onAfterStart()` и `onBeforeStop()` — это работа, привязанная к включению
и выключению агента. От обычных слушателей `AgentSwitch` их отличает **момент
вызова относительно флага**:

```
OFF -> ON:   флаг := ON  ->  слушатели  ->  onAfterStart   (агент уже включён)
ON  -> OFF:  onBeforeStop  ->  флаг := OFF  ->  слушатели   (агент ещё включён)
```

* `onBeforeStop` идёт **до** смены флага, чтобы хук успел доделать и сохранить
  начатое, пока агент ещё работает.
* `onAfterStart` идёт **после**, чтобы хук мог обращаться к тому, что живёт
  только в состоянии ON.
* Слушатели оповещаются раньше `onAfterStart`: кнопка в интерфейсе должна
  перерисоваться мгновенно, не дожидаясь подготовительной работы.

Хуки **синхронные**, и это осознанно: гарантия «`onBeforeStop` доработал до
падения флага» — весь смысл интерфейса, с асинхронным вызовом её не будет.
Отсюда правило: хук обязан быть быстрым, долгую работу надо ставить в очередь.
`AgentLifecycle` логирует длительность каждого вызова и ругается на всё дольше
500 мс. Тот, кто дёргает флаг из UI-потока, уводит вызов в фоновый —
`AgentToggleBar` так и делает.

Упавший хук не отменяет переключение и не мешает остальным: возможность
выключить агента важнее успеха любой подготовительной работы.

Зарегистрированы три хука (в этом порядке — `graceful-stop` первым,
чтобы консолидация видела ответ доработавшего запроса):

| Хук | `onAfterStart` | `onBeforeStop` |
|---|---|---|
| `graceful-stop` | — | **ждёт доработки текущего запроса** до `agent.stop_grace_seconds`, потом прерывает — см. [3.18.4](#3184-мягкая-остановка) |
| `memory-consolidation` | пишет в лог размер памяти | **консолидирует все активные сессии и закрывает их** — см. [3.11.3](#3113-консолидация) |
| `reminders` | **догоняет пропущенные задания** и запускает тик планировщика — см. [3.13.4](#3134-догоняющие-напоминания) | останавливает тик; задания остаются в базе |

`graceful-stop`, `memory-consolidation` и `reminders.onAfterStart` **нарушают
правило «хук быстрый»** сознательно: обращение к модели занимает секунды.
Цель хука ровно в том, чтобы факты были записаны *до* выключения, а не
«когда-нибудь потом»; асинхронность убила бы смысл. `AgentToggleBar` уводит
переключение с потока JavaFX, в Telegram это поток поллинга — пара секунд
задержки там допустима.

Живут хуки в `agent-core`, а не в `memory-store` и `scheduler`: `agent-core`
зависит от этих модулей, и обратная зависимость ради интерфейса замкнула бы цикл.

### 3.7 Голосовой ввод (push-to-talk)

Держишь клавишу — говоришь, отпустил — агент отвечает. Настройка в три шага.

#### Шаг 1. Собрать evdev-хелпер

В Wayland **нет API глобальных горячих клавиш**: композитор отдаёт события
только сфокусированному окну, аналога `XGrabKey` нет принципиально. Поэтому
нажатия читаются напрямую из `/dev/input` маленьким нативным хелпером —
из JVM это недоступно без JNI.

```bash
sudo pacman -S libevdev          # Debian: libevdev-dev, Fedora: libevdev-devel
cd native/evdev-hotkey && make
```

Бинарник появится в `native/evdev-hotkey/build/evdev-hotkey`.
Из Gradle: `./gradlew :capture:buildHotkeyHelper` (отдельная задача, в обычный
`build` не входит — на машине сборки может не быть gcc и libevdev).

#### Шаг 2. Дать доступ к /dev/input

Устройства ввода принадлежат группе `input`, обычный пользователь их не читает:

```bash
sudo usermod -aG input $USER
```

**Обязательно перелогиниться** — членство в группе применяется при входе
в сессию, а не сразу. Проверить:

```bash
groups | grep input
```

Без этого хелпер честно скажет `не найдено ни одного устройства с клавишей
KEY_HOME`, а STT не запустится.

> Группа `input` даёт доступ ко всем устройствам ввода, то есть фактически
> возможность читать любой ввод в системе. Для однопользовательской машины
> это приемлемо и это обычный способ настройки; более узкая альтернатива —
> правило udev на конкретное устройство.

**Какое устройство слушать.** По умолчанию — все сразу, указывать ничего
не нужно: клавиатур в системе обычно несколько (встроенная, USB, виртуальные
устройства композитора). Посмотреть найденные:

```bash
./native/evdev-hotkey/build/evdev-hotkey --list
# /dev/input/event6   Logitech USB Keyboard
```

Либо через ссылки: `ls -l /dev/input/by-path/ | grep kbd`.
Ограничиться одним — `stt.hotkey_device` в конфиге.

Проверить руками, без всего остального:

```bash
./native/evdev-hotkey/build/evdev-hotkey
# нажать и отпустить Home -- в stdout появятся DOWN и UP
```

> Клавиша **не перехватывается**: нажатие дойдёт и до активного окна. Перехват
> потребовал бы `EVIOCGRAB`, а это забрало бы клавишу у всей системы. Поэтому
> под push-to-talk лучше выбрать что-то незанятое — например `KEY_F13`.

#### Шаг 3. Собрать whisper.cpp и скачать модель

```bash
git clone https://github.com/ggml-org/whisper.cpp && cd whisper.cpp
cmake -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j --config Release
sh ./models/download-ggml-model.sh large-v3-turbo
```

Бинарник — `build/bin/whisper-cli`. **Не `main`**: проект его переименовал,
и старые инструкции в интернете уже не работают.

Модель под русский: `large-v3-turbo` (~1.6 ГБ) — разумный компромисс
скорости и качества. `tiny` и `base` для русского практически бесполезны.

#### Шаг 4. Прописать в конфиг

```toml
[stt]
enabled = true
hotkey_helper = "native/evdev-hotkey/build/evdev-hotkey"
hotkey_key = "KEY_HOME"
hotkey_device = ""          # пусто -- все клавиатуры
whisper_binary = "~/src/whisper.cpp/build/bin/whisper-cli"
model_path = "~/src/whisper.cpp/models/ggml-large-v3-turbo.bin"
language = "ru"
threads = 4
max_seconds = 120
```

Тильда в путях разворачивается. Все значения читаются **на старте**, так что
изменения требуют перезапуска процесса.

#### Диагностика

Чего не хватает, видно в логе при запуске — проверка идёт на старте, а не при
первом нажатии, потому что молчащий push-to-talk отлаживать неприятно:

| Строка в логе | Что делать |
|---|---|
| `STT не запущен: не собран evdev-хелпер` | `cd native/evdev-hotkey && make` |
| `STT не запущен: модель не найдена` | Проверить `stt.model_path` |
| `STT выключен в конфиге` | `stt.enabled = true` |
| `[evdev-hotkey] не найдено ни одного устройства` | Нет группы `input` или не перелогинились |
| `Клавиша нажата, но агент выключен` | Включить агента (тумблер в окне или ⚡ Питание) |
| `Речь не распознана` | Тишина, шум или неверный `language` |

### 3.8 Как агент решает и действует

#### 3.8.1 Общая картина

```
UserMessage
   │
   ├─ 1. «Что делать?»  ──> модель ──> AgentDecision (JSON)
   │
   ├─ type = reply        ──> текст пользователю                    ✔
   │
   └─ type = run_script   ──> ScriptRuntime
                                 │
                                 ├─ успех  ─> 2. «Сформулируй ответ» ──> модель ✔
                                 │
                                 └─ провал ─> 3. «Почини скрипт» ──> модель ──┐
                                                                              │
                                              ◄───────────────────────────────┘
```

Каждая стрелка «──> модель» списывает единицу из общего бюджета запроса.

#### 3.8.2 Протокол решения

Ответ модели — не свободный текст, а JSON по схеме, которая уходит в поле
`format` запроса (структурированный вывод Ollama):

```json
{
  "type":        "reply" | "tool_call" | "use_script" | "run_script" | "fix_last_script",
  "reply":       "текст ответа",
  "messages":    ["первая реплика", "вторая"],   // только при включённом «живом стиле», см. 3.8.6
  "tool_name":   "web_search",
  "arguments":   {"query": "курс доллара"},
  "python_code": "код скрипта",
  "explanation": "одна строка: что скрипт сделает — её показывают пользователю
                  в запросе подтверждения",
  "script_id":   7,
  "script_name": "короткое имя нового скрипта",
  "script_tags": ["ключевые", "слова"]
}
```

| Семейство | `type` | Когда | Что заполняет |
|---|---|---|---|
| ответ | `reply` | Ответ из знаний | `reply` либо `messages[]` (живой стиль) |
| инструмент | `tool_call` | Время, поиск — готовая функция | `tool_name`, `arguments` |
| скрипт | `use_script` | Подходит готовый из каталога | `script_id` |
| скрипт | `run_script` | Нужен новый скрипт | `python_code`, `script_name`, `script_tags`, `explanation` |
| скрипт | `fix_last_script` | Жалоба на прошлый результат | `python_code` |

`tool_name` в схеме — `enum` из имён реестра плюс пустая строка; `arguments` —
открытый объект, состав параметров модель узнаёт из описания инструмента
в промпте.

Что проверено на живой модели и важно при правке схемы и промпта:

* **`additionalProperties: false` помогает, но не гарантирует.** Без него
  модель придумывает поля (`script` вместо `python_code`). С ним — обычно
  соблюдает, но при путаном промпте прислала вложенную форму
  `{"tool_call": {"tool_name": ...}}` вопреки схеме. Ollama Cloud применяет
  схему **нестрого**.
* **`required` тоже нестрогий:** `{"reply": "Лиссабон"}` без `type` — реальный ответ.
* Поэтому `AgentDecision.parse` терпим вчетверо: снимает markdown-обёртку
  ```` ```json … ``` ```` (модели без строгого structured output любят её
  добавлять), разворачивает вложенную форму, при отсутствии `type` угадывает
  его по содержимому (`tool_name` → инструмент, `script_id` → готовый,
  `python_code` → скрипт, `reply` → ответ), и только если нечего взять —
  `UNKNOWN`. Сырой текст неразобранного ответа уходит
  в лог `WARN`.
* **Промпт важнее схемы.** Регрессия, стоившая часа: переписал промпт
  красивыми «тремя семействами» без явного списка полей — модель перестала
  ставить `type`. Список полей с пометкой «type — ОБЯЗАТЕЛЬНО» в начале
  промпта обязателен.

Схема дополнительно пересказывается словами в системном промпте — так советует
документация Ollama, и на практике это заметно снижает число бессмысленных
ответов.

**Новый тип решения** — четыре места: константа в `DecisionType`, поля
в `responseSchema` и `AgentDecision`, ветка в `AgentCore.loop`, строка
в промпте. **Новый инструмент — не новый тип**: см. [3.12](#312-инструменты),
там достаточно регистрации.

#### 3.8.6 «Живой стиль»: несколько реплик вместо одной

Тумблер **`agent.live_replies`** (по умолчанию выключен): окно → Настройки →
«Живой стиль сообщений», Telegram → ⚙️ Настройки → «💬 Включить живой стиль».
Живая настройка `AppSettings`, ядро читает её на каждом запросе через
`BooleanSupplier` — без перезапуска.

Что меняется при включении:

* **Схема решения** получает поле `messages: string[]`; без тумблера его
  в схеме **нет вовсе**, чтобы модель не тянулась к нему сама. В системный
  промпт добавляется блок «Живой стиль сообщений ВКЛЮЧЁН» с правилами
  по умолчанию (2–4 реплики, каждая — законченная мысль, короткий ответ —
  одной репликой) и оговоркой: **инструкция персоны о том, как разбивать,
  важнее этих правил**. Блок стоит перед текстом персоны, так что персона
  видит механику и уточняет её.
* **Свободные ответы** (после скрипта или инструмента) идут без схемы;
  для них в промпт формулировки добавляется подсказка разделять сообщения
  строкой `---`, и ядро режет по ней (`replyFromText`).
* **`AgentReply.Text`** несёт `parts` (реплики) и `text` (всё вместе, через
  пустую строку) — второе для памяти, лога и голоса, чтобы остальной код
  ничего не заметил. `isMultipart()` — больше одной.

Обратная совместимость в обе стороны: пришёл `reply` без `messages` — одна
реплика, как раньше; пришли `messages` при **выключенном** тумблере —
склеиваются в одно сообщение (`AgentDecision.reply()` — их склейка).

**Персона задаёт «как».** Тумблер включает механику, персона — манеру:
в её инструкции можно написать «отвечай короткими рывками по одному
предложению, 3–5 сообщений» или «никогда не дроби ответ», и модель следует
этому, потому что текст персоны идёт после блока правил и объявлен
приоритетным. Персона без указаний — правила по умолчанию.

**Доставка в Telegram** (`TelegramBridge.deliverLively`): реплики по очереди
в отдельном потоке (поллинг не ждёт): первая — сразу, дальше 400 мс →
`sendChatAction("typing")` → пауза по длине следующей (30 мс на символ,
от 600 мс до 4 с) → сообщение. Порядок гарантирован одним потоком-исполнителем.

**«Печатает…» — отдельный тумблер** `telegram.typing_indicator` (окно →
Настройки, Telegram → ⚙️ → «⌨️ Включить/Выключить «печатает…»»; по умолчанию
включён). Он и живой стиль независимы, и правило простое:

| | Индикатор выкл | Индикатор вкл |
|---|---|---|
| Между вопросом и первым сообщением ответа | ничего | «печатает…» всё время, пока агент думает — **независимо от живого стиля** |
| Между репликами при живом стиле | только пауза 400 мс, чтобы не слипались | «печатает…» + пауза по длине |

Механика первого случая — `typingWhile(chatId)`: первый `sendChatAction`
уходит синхронно (индикатор должен появиться до ответа, даже если модель
ответит мгновенно), дальше поток `telegram-typing` продлевает его каждые 4 с —
Telegram гасит статус через 5. Обёрнуты `replyAsAgent` и нажатие
«✅ Выполнить»: за кнопкой скрипт и модель, это тот же «думаю». Ответы,
пришедшие из других каналов через `deliver()` (голос, напоминания), индикатора
«до первого сообщения» не получают — их никто не ждал в чате.

**Голос при живом стиле — одно голосовое на весь ответ**, после последней
реплики. Компромисс осознанный: несколько коротких голосовых подряд — это
несколько отдельных плееров, каждый надо нажать; одно голосовое звучит
цельно, а паузы между репликами Piper и так делает на границах предложений.
Плата — голос отстаёт от последней текстовой реплики на время синтеза.

#### 3.8.7 Скрипты выключены: протокол без действий

Тумблер **`agent.scripts_enabled`** (по умолчанию включён): окно → Настройки →
«Скрипты (действия на компьютере)», Telegram → ⚙️ Настройки → «🐍 Выключить /
Разрешить скрипты». Живая настройка `AppSettings`; ядро читает её **один раз
на решение** (`decide()`), чтобы схема, промпт и разбор ответа видели одно
значение, даже если тумблер щёлкнули посреди запроса.

Ключевое решение: при выключенных скриптах агент **не пытается понять, какое
действие нужно, а потом отказывать** — модель о действиях не знает вовсе:

| Что | Скрипты включены | Скрипты выключены |
|---|---|---|
| `enum` поля `type` в схеме | `reply`, `tool_call`, `use_script`, `run_script`, `fix_last_script` | `reply`, `tool_call` |
| Поля схемы | все | без `python_code`, `explanation`, `script_id`, `script_name`, `script_tags`; `required` = `type`, `reply` |
| Промпт решения | `decisionPrompt(tools, true)` — список полей, «когда какой type», «требования к скрипту» | `decisionPrompt(tools, false)` — отдельный текст, слово «скрипт» в нём не встречается; вместо этого блок «выполнение действий на компьютере ОТКЛЮЧЕНО в настройках: скажи об этом обычным текстом, предложи, что можешь без него, не проси переформулировать» |
| Каталог | `library.search` до обращения, кандидаты и «последний скрипт» в промпте | не ищется, ничего не подмешивается — кандидаты только подталкивали бы к действию, которого в протоколе нет |
| Промпт починки | полный | тот же `decisionPrompt(tools, false)` — если тумблер выключили, пока скрипт падал |

Отказ «сейчас выполнение действий на компьютере отключено» формулирует **сама
модель по промпту**, а не код — поэтому он звучит по-человечески и в стиле
персоны. Единственная захардкоженная фраза
(`DecisionProtocol.scriptsDisabledMessage()`) — для гонки: вопрос задали при
включённых скриптах, а кнопку «✅ Выполнить» нажали (или починка дошла до
запуска) уже при выключенных. Тогда `loop()` и `confirm()` не зовут
`ActionExecutor` вовсе — событие `script.disabled` в логе. Это общая точка для
обеих сборок: в headless-сервере `ActionExecutor` — это `RemoteActionExecutor`,
и `RUN_SCRIPT_REQUEST` клиенту не уходит (проверено в
`ClientServerScenariosTest`: каталог `scripts_dir` клиента остаётся пустым).

**Страховка от модели, которая не уложилась в протокол.** Схема и промпт без
скриптов — не гарантия (3.8.2: Ollama Cloud применяет схему нестрого). Если при
выключенных скриптах модель прислала скриптовый тип или неразборчивый JSON,
ядро **не** отвечает «не разобрался»: ответить текстом можно всегда, поэтому
делается одно обращение **без схемы** (`plainReply`, событие
`decision.scripts_disabled`, списывает бюджет как «ответ без схемы») — и его
текст уходит пользователю; при живом стиле режется по `---`, как после
инструмента. Бюджет кончился — обычное «не справился».

**Когда теперь может звучать «Не разобрался, что нужно сделать. Попробуйте
сформулировать иначе.»** Только при **включённых** скриптах: это ответ
`AgentCore.loop` на решение, у которого `isUsable() == false` — модель
прислала `run_script` без `python_code`, `use_script` с `script_id = 0`,
`tool_call` без имени, `reply` без текста или вовсе не-JSON, из которого
`AgentDecision.parse` не смог угадать тип. То есть это отказ разбора,
а не «не понял задачу». При выключенных скриптах эта ветка недостижима:
непригодное решение перехватывается в `decide()` раньше и заменяется
свободным ответом.

#### 3.8.3 Бюджет запроса

`RequestBudget` — потолок обращений к модели на **одно** сообщение
пользователя. По умолчанию **15**, настраивается через `[agent] request_budget`.

Зачем: цикл рекурсивен по природе — модель просит запустить скрипт, скрипт
падает, модель чинит, снова падает. Без общего счётчика это бесконечный круг,
который жжёт деньги и выглядит как зависший агент.

Счётчик **один на весь запрос** и общий для всех видов обращений:

| Обращение | Когда |
|---|---|
| `решение по запросу` | Всегда, один раз |
| `починка скрипта #N` | На каждое падение скрипта |
| `формулировка ответа` | После успешного скрипта |
| `инструмент: обращение к модели` | Изнутри инструмента: формулировка поискового запроса, оценка выдачи, каждая переформулировка |
| `формулировка ответа по инструменту` | После инструмента |
| `ответ без результата инструмента` | Инструмент прерван по бюджету: ответ из знаний модели на зарезервированное обращение |

Переформулировки поиска берут из этого же счётчика: инструмент получает
`ToolContext.LlmCaller`, реализация которого в ядре списывает бюджет и при
исчерпании бросает `BudgetExhausted` — инструмент останавливается. Проверено
тестом с «болтливым» инструментом: потолок держит и обращения изнутри. Именно
поэтому бюджет протаскивается через весь цикл, а не создаётся по месту.

**Инструменту не достаётся последнее обращение** (`RESERVED_FOR_REPLY = 1`
в `AgentCore.budgetedLlm`): `LlmCaller` отказывает, когда в бюджете остаётся
одно. Это обращение — на ответ пользователю, если инструмент оборвался:
`answerWithoutTool` просит модель ответить из своих знаний и контекста
разговора (`DecisionProtocol.withoutToolPrompt`, без схемы, с историей сессии),
одной фразой оговорив, что проверить не удалось, и **не упоминая лимиты и
инструменты**. Событие `tool.budget_exhausted` в логе. Появилось вместе
с поиском в беседе (3.12.2): раньше оборванный поиск отвечал «не справился»,
для фактологического вопроса это терпимо, для реплики в разговоре — нет.
Из бюджета 15 после решения инструменту остаётся 13 обращений, обычный поиск
тратит 2–4, так что упирается в резерв он только при `max_reformulations`
далеко выше дефолта.

При исчерпании в остальных местах агент вежливо сообщает, что не справился,
вместо того чтобы крутиться дальше. Одно исключение: если бюджет кончился ровно
на формулировке ответа, отдаётся **сырой вывод скрипта** — данные полезнее
извинения.

Ожидание подтверждения бюджет **не сбрасывает**: он переезжает
в `PendingExecution` и продолжается после нажатия кнопки.

#### 3.8.4 Автоустановка зависимостей

Если скрипт упал на `ModuleNotFoundError` / `ImportError`, это механическая
проблема, а не ошибка в коде. Гонять её через модель расточительно: лишний
круг по бюджету ради `pip install`. Поэтому:

```
скрипт упал -> нашли имя модуля в stderr
            -> это не модуль stdlib?
            -> имя похоже на имя пакета?
            -> pip install в тот же venv
            -> повторить запуск РОВНО ОДИН РАЗ
            -> всё ещё падает -> это баг скрипта, чинит модель
```

Детали, которые не очевидны:

* **Имя модуля ≠ имя пакета.** `cv2` → `opencv-python`, `PIL` → `Pillow`,
  `bs4` → `beautifulsoup4`, `yaml` → `PyYAML` и ещё два десятка.
  Таблица — в `MissingModule.PACKAGE_ALIASES`.
* **Модули stdlib не ставятся никогда.** Если не нашёлся `sqlite3` — это
  сломанная сборка Python или опечатка, и установка одноимённого пакета
  с PyPI сделает только хуже.
* **Ставится пакет верхнего уровня:** `google.protobuf` → `google`.
* **Повтор ровно один.** Если скрипту не хватает двух пакетов, второй
  обнаружится только после того, как модель «починит» скрипт — это стоит
  одного лишнего обращения. Сознательный размен: так проще рассуждать
  о поведении, чем с вложенным циклом установок.

> **Про риск.** Имя пакета берётся из трассировки, то есть в конечном счёте
> из кода, который написала модель, и ставится без подтверждения. Это
> установка ПО из интернета по решению LLM — с опечаткой в имени можно
> притащить не тот пакет. Ограничители: имя проверяется на формат пакета,
> stdlib исключён, аргументы передаются списком (без шелла), всё ставится
> в изолированный venv и пишется в лог. Выключается через
> `scripts.auto_install_deps = false`.

#### 3.8.5 Безопасность выполнения: осознанный компромисс

Скрипт пишет языковая модель, выполняется он с правами пользователя, **без
песочницы** — и это не недоработка, а решение.

Причина: скрипты по замыслу **управляют GUI-приложениями пользователя**.
Им нужны его дисплей, его файлы, его сессия, его `DBUS_SESSION_BUS_ADDRESS`.
Контейнер, `bubblewrap` или отдельный пользователь отняли бы ровно то, ради
чего скрипты существуют. Для личного однопользовательского агента цена полной
изоляции выше пользы — тот же расчёт, что и с секретами открытым текстом
в конфиге.

Что всё-таки ограничивает — от **случайной прожорливости**, не от злого умысла:

| Ограничитель | Что даёт |
|---|---|
| Таймаут стены (`timeout_seconds`, 15 с) | Зависший скрипт убивается |
| `prlimit --as` (`max_memory_mb`, 2 ГБ) | Скрипт, читающий файл в память целиком, получит `MemoryError`, а не съест всё |
| `prlimit --cpu` (`max_cpu_seconds`, таймаут×2) | Дополняет таймаут, если процесс успел породить потомков |
| `prlimit --fsize` (`max_file_size_mb`, 512 МБ) | Цикл с записью не забьёт диск |
| Отказ работать от root | Ошибка запуска и `ERROR` при старте |
| Отдельный venv | Системные пакеты не трогаются |
| Аудит `script.audit` | Код, stdout, stderr каждого запуска в `script-runtime.log` под `trace_id` |
| Системный промпт | Модель просят ничего не удалять без явной просьбы |

Лимит памяти проверен на живом `prlimit`: скрипт, берущий 1 ГБ при лимите
256 МБ, падает с `MemoryError`. Лимит щедрый по умолчанию не случайно: numpy
и подобные резервируют гигабайты адресного пространства, не трогая их,
и слишком низкий `RLIMIT_AS` ломает их на импорте.

Если проект когда-нибудь выйдет за пределы одного пользователя, здесь нужен
контейнер — и тогда часть сценариев с GUI перестанет работать. Это придётся
решать заново, а не докручивать лимиты.

### 3.9 Каталог скриптов и подтверждения

#### 3.9.1 Зачем каталог

Без него агент пишет скрипт заново на каждый похожий вопрос: лишние обращения
к модели, лишняя задержка и новый шанс ошибиться там, где вчера всё работало.
С каталогом удачный скрипт переиспользуется.

Схема таблицы `scripts`:

| Поле | Смысл |
|---|---|
| `id` | Первичный ключ; он же уезжает в `callback_data` |
| `name`, `description`, `tags` | Что это и по каким словам искать |
| `path` | Файл со скриптом на диске |
| `version`, `root_id` | Версии одного скрипта: `root_id` общий, `version` растёт |
| `success_count`, `failure_count` | Статистика; влияет на порядок в поиске |
| `requires_confirmation` | Спрашивать ли разрешение перед запуском |
| `created_at`, `last_used_at` | Когда добавлен и когда последний раз пригодился |

#### 3.9.2 Поиск: почему по словам, а не запросом к модели

Осознанный выбор для v1:

* **Бесплатно.** Отдельный вызов LLM ради поиска съедал бы единицу из бюджета
  запроса — а их всего 15, и они нужны на починку.
* **Мгновенно.** Иначе +1–2 секунды к *каждому* сообщению, включая «привет».
* **Детерминированно.** Такое покрывается тестами; ответ модели — нет.
* **Каталог маленький.** На десятках записей выигрыш семантического поиска
  не окупает сложности.

Устройство: текст режется на слова, слова обрезаются до 4 первых букв (грубая
замена морфологии — «файл», «файлы», «файлами» дают одну основу), совпадения
взвешиваются: имя ×3, теги ×2, описание ×1. Результат умножается на долю
успешных запусков, так что надёжный скрипт обгоняет одинаково похожий, но
регулярно падающий. Ниже порога — пусто: лучше ничего, чем случайный скрипт.

**Решение всё равно за моделью.** Найденные кандидаты уходят в промпт вместе
с самим вопросом, и она выбирает — взять готовый (`use_script`) или написать
новый. То есть поиск это дешёвый предварительный фильтр, а не подмена решения,
и он не стоит ни одного лишнего обращения.

Что тут не работает: это лексическое совпадение, а не смысл. «покажи занятое
место» и «сколько свободно на диске» — про одно и то же, но общих слов нет.
Когда каталог дорастёт до сотен записей, сюда встанут эмбеддинги.

#### 3.9.3 Сценарий «не сработало»

Скрипт может отработать без ошибок и при этом сделать не то. Тогда пользователь
пишет об этом следующим сообщением, и его надо связать с прошлым запуском.

Как связывается: после каждого успешного запуска ядро запоминает
`root_id` скрипта — **отдельно по каждому разговору**. Ключ разговора это
канал плюс адресат (`TELEGRAM:12345`, `VOICE:-`), поэтому жалоба из чата
не зацепит скрипт, запущенный голосом.

Дальше прошлый скрипт просто дописывается в промпт следующего запроса:

```
Последний выполненный скрипт: [7] Свободно в /tmp — ... [успех 1/1]
Если пользователь жалуется на его результат — верни type="fix_last_script"
с исправленным python_code.
```

Распознаёт жалобу **модель**, а не список ключевых слов: «не то», «неправильно»,
«мне нужно в гигабайтах», «а можно наоборот» — вариантов бесконечно, и
угадывать их регулярками бессмысленно. Стоит это ноль: контекст едет вместе
с обычным запросом.

Исправленный код сохраняется **новой версией** (v2, v3…) с тем же `root_id`
и сразу запускается. Старая версия остаётся в базе.

#### 3.9.4 Подтверждение запуска

Новый скрипт всегда создаётся с `requires_confirmation = true`: разрешение
даёт пользователь, а не модель.

```
скрипт требует подтверждения
   -> ⚠️ Запустить скрипт? <имя> + описание + статистика
      [✅ Выполнить] [❌ Отмена]
   -> ✅  -> запуск -> ответ
          -> отдельным сообщением: [🔕 Больше не спрашивать]
   -> ❌  -> ничего не запускалось
```

Детали, которые важнее, чем кажутся:

* **Бюджет переезжает в отложенный запуск.** Обработка встала на середине;
  после нажатия она продолжается с тем же `RequestBudget`. Иначе кнопка
  обнуляла бы счётчик, и через неё можно было бы крутить цикл починки вечно.
* **Спрашиваем один раз, до первого запуска.** Если скрипт потом упадёт
  и модель его починит, дёргать пользователя на каждой итерации — издевательство.
* **Токен короткий (8 hex).** Он уезжает в `callback_data`, где 64 байта
  на всё; UUID съел бы больше половины.
* **Подтверждение одноразовое.** Повторное нажатие той же кнопки отвечает
  «запрос устарел», а не запускает скрипт второй раз.
* **Протухает через 10 минут** — незакрытый вопрос не должен висеть вечно.
* **Новая версия спрашивает заново**, даже если прошлую пометили доверенной.
  Доверие выдавалось *прочитанному коду*, а после починки код другой; иначе
  «почини скрипт» стало бы способом протащить непросмотренный код мимо
  подтверждения. В сообщении это сказано прямо, чтобы повторный вопрос
  не выглядел сбоем.

#### 3.9.5 Раздел «✅ Подтверждения»

Список скриптов каталога, у каждого тумблер:

* 🔔 — спрашивать перед запуском;
* 🔕 — запускать сразу.

Нажатие переключает и остаётся на той же странице. По 6 скриптов на страницу:
инлайн-клавиатура в Telegram прокручивается плохо, и длинный список
превращается в простыню на весь экран. Показываются только последние версии.

### 3.10 Логи

#### 3.10.1 Где лежат

Каталог — `[logging] dir`, по умолчанию `logs/` от корня репозитория.

| Файл | Что в нём |
|---|---|
| `agent.log` | Всё подряд — любая строка любой подсистемы |
| `agent-core.log` | Ядро: события запроса, решения модели, бюджет, подтверждения |
| `script-runtime.log` | Скрипты и каталог: запуски, **код, stdout, stderr**, установка пакетов |
| `telegram-bridge.log` | Поллинг, меню, доступ, отправка |
| `scheduler.log` | Планировщик: тики, срабатывания, догон |
| `watchdog.log` | Сторож: `watchdog.hang`, `watchdog.restart`, `worker.restart` |
| `transport.log` | Этап 2: `transport.connect` / `.auth` / `.disconnect` / `.reconnect` / `.heartbeat.timeout`, паринг |

Строка попадает **и в свой файл, и в `agent.log`** (additivity). Разбиение —
по префиксу имени логгера; список префиксов в `logback.xml` обязан совпадать
с `JsonLayout.SUBSYSTEMS`, иначе поле `subsystem` и файл разойдутся.

Ротация — по размеру (20 МБ, у `script-runtime.log` 50 МБ: там код и вывод)
и по дню; старые файлы сжимаются в `.gz`, хранятся 14 дней, общий объём
ограничен (500 МБ, у скриптов 1 ГБ). Консоль остаётся человекочитаемой,
с `trace_id` в квадратных скобках.

#### 3.10.2 Формат

Одна строка — один JSON-объект. Поля одинаковы во всех файлах:

```json
{"ts":"2026-09-18T16:33:48.565+05:00",
 "level":"INFO",
 "subsystem":"agent-core",
 "logger":"c.b.agent.core.AgentCore",
 "thread":"telegram-poll",
 "trace_id":"e510c42a22f9",
 "msg":"Обрабатываю сообщение [Telegram] сколько файлов в /etc?",
 "kv":{"event":"request.start","source":"TELEGRAM","reply_to":"1","text":"сколько файлов в /etc?"},
 "error":{"type":"...","message":"...","stack":"...","cause":{...}}}
```

* `trace_id` есть только у строк, относящихся к запросу пользователя.
* `kv` — структурированные поля из slf4j fluent API
  (`log.atInfo().addKeyValue("exit_code", 1).log(...)`). Числа остаются
  числами, а не строками — по ним можно фильтровать точно, а не регуляркой.
* `error` появляется, когда залогировано исключение; стек обрезан до 30 кадров.

Ключевые события (`kv.event`), по которым читается история запроса:

| Событие | Подсистема | Когда |
|---|---|---|
| `request.start` | agent-core | Сообщение вошло в ядро |
| `decision` / `decision.fix` | agent-core | Модель ответила: тип, `script_id`, число кандидатов |
| `confirmation.requested` | agent-core | Ждём кнопку |
| `confirmation.accepted` / `.cancelled` | agent-core | Нажали |
| `script.audit` | script-runtime | Запуск: код, stdout, stderr, exit, длительность |
| `script.result` | agent-core | Ядро получило результат |
| `reply.ready` | agent-core | Ответ сформулирован |
| `request.end` | agent-core | Сегмент обработки закончен (при подтверждении их два) |
| `tool.call` / `tool.result` | agent-core / tools | Вызов инструмента и его исход |
| `decision.scripts_disabled` / `script.disabled` | agent-core | Скрипты выключены: модель не уложилась в протокол без скриптов → свободный ответ / готовый к запуску скрипт не выполнен (тумблер выключили посреди запроса) |
| `web.search` / `web.relevance` | tools | Поисковый запрос и оценка выдачи |
| `tool.budget_exhausted` | agent-core | Инструмент прерван по бюджету, ответ идёт из знаний модели без него |
| `reply.sent` | telegram-bridge | Ушло в чат |
| `voice.press` / `voice.transcribed` | stt-bridge | Клавиша нажата / речь распознана |
| `tts.synthesized` / `voice.sent` | tts-bridge / telegram-bridge | Озвучено (символы, байты, мс) / голосовое ушло в чат |
| `watchdog.hang` / `watchdog.restart` / `worker.restart` | watchdog / agent-core | Подтверждённое зависание / поток перезапущен |
| `stop.waiting` / `stop.interrupt` / `script.interrupted` | agent-core / script-runtime | Мягкая остановка: ждём / прерываем / скрипту послан SIGTERM |
| `job.created` / `job.fire` | scheduler | Задание поставлено / наступило (`late`, `status`) |
| `scheduler.gap` / `scheduler.catchup` | scheduler | Скачок времени между тиками / догон при включении |
| `reminder.inject` / `reminder.desktop` | agent-core | Промпт подан в ядро / показано уведомление |
| `notes.write` / `notes.delete` / `notes.semantic` | notes-store / tools | Файл записан (и закоммичен ли) / удалён / поиск через модель |
| `persona.create` / `persona.activate` / `persona.delete` | memory-store | Персона создана / стала активной / удалена |
| `clipboard.read` | tools | Прочитан буфер: размер, обрезан ли |

#### 3.10.3 Сквозной `trace_id`

Одно сообщение пользователя — один идентификатор (12 hex) во всех подсистемах,
от входа до ответа. Где он рождается:

* **Telegram** — на каждое обновление в `dispatchSafely`; `UserMessage`
  подхватывает его из потока.
* **Голос** — при **нажатии** клавиши: запись, расшифровка и ответ — один запрос.
* **Подтверждение** — не новый запрос: ядро переключается на `trace_id`
  исходного сообщения, и запуск ложится в ту же историю.
* **Напоминание** — новая цепочка `job-<id>-xxxx`: запрос, из которого его
  поставили, давно закончился. Связь с ним — поле `trace_id` в строке `jobs`.

Механика — `TraceContext` поверх MDC. Идентификатор живёт в потоке, поэтому
при переезде в другой поток его переносят руками:
`TraceContext.wrap(traceId, task)` для исполнителей,
`try (var s = TraceContext.open(id)) {...}` для продолжений.

Собрать историю запроса из всех файлов:

```bash
# всё про один запрос, по времени
cat logs/*.log | grep e510c42a22f9 | jq -r '"\(.ts[11:23]) \(.subsystem) \(.kv.event // "") \(.msg)"' | sort

# что именно выполнялось
grep '"script.audit"' logs/script-runtime.log | grep e510c42a22f9 | jq -r '.kv.code'

# все упавшие скрипты за сегодня
grep '"script.audit"' logs/script-runtime.log | jq 'select(.kv.exit_code != 0) | {ts, trace_id, stderr: .kv.stderr}'

# найти trace_id по тексту вопроса
grep '"request.start"' logs/agent-core.log | jq -r 'select(.kv.text | test("файлов")) | .trace_id'
```

#### 3.10.4 Уровень и точечный DEBUG

```toml
[logging]
dir = "logs"
level = "INFO"          # для кода агента; сторонние библиотеки всегда WARN

[logging.levels]        # переопределения -- DEBUG для одного разбора, не для всего
script-runtime = "DEBUG"
"com.bebebe.agent.ollama.OllamaClient" = "TRACE"
```

Ключ в `[logging.levels]` — имя подсистемы (`agent-core`, `script-runtime`,
`telegram-bridge`, `stt-bridge`, `ollama-client`, `scheduler`, `watchdog`)
или полное имя пакета/класса. Значения читаются на старте. Общий уровень
`[logging] level` можно сменить на лету с экрана «Логи» в окне: применяется
через `AppLogging.setLevel()` и сразу пишется в конфиг, точечные
переопределения из `[logging.levels]` при этом остаются.

Как это устроено внутри: курица и яйцо — уровень лежит в конфиге, а чтобы
прочитать конфиг, логирование уже должно работать. Поэтому `AppLogging.bootstrap()`
поднимает logback с дефолтами (`logs/`, `INFO`), а после чтения конфига
`applyConfig()` подставляет свойства `bebebe.log.dir` / `bebebe.log.level`
и заставляет logback перечитать `logback.xml`. Строки, написанные между
шагами, остаются в `logs/`.

Типичный разбор «агент сделал что-то странное»:

1. Найти `trace_id` по тексту вопроса (команда выше).
2. Собрать цепочку — видно решение модели, кандидатов из каталога,
   подтверждение, результат.
3. Из `script.audit` достать код и `stderr`.
4. Если мало — включить `script-runtime = "DEBUG"` (покажет venv, pip)
   или `ollama-client = "DEBUG"` (покажет URL запросов) и повторить.

> Ловушка, стоившая времени дважды: строка `--` внутри XML-комментария ломает
> весь `logback.xml`, logback молча откатывается на дефолты, и об этом узнаёшь
> по пустому каталогу логов. Теперь это ловит тест `LogbackConfigTest`.

### 3.11 Память

#### 3.11.1 Три уровня

```
┌─ сырой лог сессии ─────────────────────────┐   пока сессия активна --
│ user: Саша не ест мясо                     │   целиком в контекст,
│ assistant: Запомнил.                       │   без сжатия
│ user: мы с Сашей идём в поход в субботу    │
└────────────────────────────────────────────┘
                 │  консолидация (модель)
                 ▼
┌─ сущности ─────────┐     ┌─ факты ──────────────────────────────────┐
│ [1] Саша (друг;    │◄────│ • Саша не ест мясо          [предпочтение]│
│     также: Шурик)  │     │ • поход в субботу           [договорённость]│
└────────────────────┘     │ • перед стримом: OBS, свет  [процедура]  │
                           └──────────────────────────────────────────┘
```

**Сессия диалога** — непрерывный разговор в одном канале (`TELEGRAM:123`,
`VOICE:-`). Граница — пауза дольше `session_idle_minutes` (60) или выключение
агента. Пока сессия активна, **весь её лог уходит в модель предыдущими
репликами** — ничего не сжимается и не суммаризируется на лету. Это решение:
сжатие теряет то, о чём модель потом спросят («а что я сказал про вторник?»),
а контекстное окно облачных моделей это выдерживает. Сессия закрылась — лог
остаётся в базе для истории, но в контекст больше не идёт.

**Сущности** — люди (модель может завести и питомца, и проект). Каноническое
имя, алиасы («Саша», «Александр», «Шурик»), отношение к пользователю, заметки.

**Факты** — короткие утверждения в третьем лице, привязанные к одной,
нескольким или ни одной сущности (тогда это факт о самом пользователе).

| Категория | Что | Как используется |
|---|---|---|
| `event` | случилось, с датой | контекст |
| `preference` | нравится / не нравится / привык | контекст |
| `agreement` | договорились, обещано | контекст |
| `trait` | работа, город, семья | контекст |
| `procedure` | «перед стримом → скрипты А, Б, В» | **всегда** в контексте, отдельным блоком «процедуры» |

Схема таблиц:

| Таблица | Поля |
|---|---|
| `sessions` | `id`, `conversation_key`, `started_at`, `last_message_at`, `ended_at`, `consolidated_up_to` |
| `messages` | `id`, `session_id`, `role`, `text`, `at`, `source`, `trace_id` |
| `entities` | `id`, `canonical_name`, `aliases` (через `\|`), `relation`, `notes`, `created_at` |
| `facts` | `id`, `text`, `category`, `fact_date`, `source_message_id`, `created_at` |
| `fact_entities` | `fact_id`, `entity_id` — многие-ко-многим |

`trace_id` у сообщения и `source_message_id` у факта — чтобы от факта можно
было дойти до реплики, а от реплики до логов запроса.

#### 3.11.2 Что попадает в контекст перед ответом

1. **Лог активной сессии целиком** — предыдущими `user`/`assistant`-репликами
   в запросе к модели.
2. **Упомянутые люди и их факты** — в системный промпт. Кто упомянут, решает
   `EntityResolver`: слова сообщения против имён и алиасов, с грубой
   морфологией (имя без последней буквы как основа, слово не длиннее имени
   больше чем на 3 буквы; имена короче 4 букв — только точно). Это узнавание
   *известных*, бесплатное и мгновенное. Найденное идёт как подсказка, а не
   истина: омонимы бывают («Марк» и «марка»), модель сама решает, о том ли
   человеке речь.
3. **Факты о пользователе** и **процедуры** — всегда, они короткие.

Факты людей, которых в сообщении нет, в контекст **не** идут — иначе с ростом
памяти каждый запрос таскал бы всё.

#### 3.11.3 Консолидация

Извлечение фактов — отдельное обращение к модели, **не** часть ответа:

* каждые `consolidate_every` (6) сообщений сессии — после ответа;
* **при выключении агента** — хук `onBeforeStop` консолидирует все активные
  сессии немедленно и закрывает их. Не «при следующем включении»: если процесс
  потом не переживёт перезагрузку, факты уже записаны.

Модель получает хвост лога с последней консолидации и список известных людей
с их id, возвращает JSON по схеме (та же дисциплина: `additionalProperties:
false`, разбор терпимый): сущности с сопоставлением и факты.

**Разрешение сущностей — через модель, без эмбеддингов.** На каждое имя:

| Ответ модели | Что делаем |
|---|---|
| имя совпало с известным буквально | привязываем, модель не спрашиваем |
| `high` + `entity_id` | привязываем, новое написание — в алиасы |
| `none` | заводим нового |
| `low` + `entity_id` | **спрашиваем пользователя** в Telegram: «Александр — это Саша (друг) или другой человек?» с кнопками «Тот же» / «Другой». Факты про это имя **придерживаются** до ответа; остальные факты из того же куска записываются сразу |

Вопрос живёт сутки; ответ «тот же» дописывает алиас и переносит придержанные
факты, «другой» заводит нового человека с ними.

Хвост помечается консолидированным **до** обращения к модели: если извлечение
упадёт, эти сообщения повторно не гоняются — лучше потерять пару фактов, чем
платить за одну и ту же ошибку при каждом запуске.

**Бюджет.** У консолидации свой `RequestBudget(2)` на запуск, не бюджет
пользовательского сообщения: это фоновая работа, и её сбой не должен отнимать
попытки у ответа. Правило «каждое обращение списывает бюджет» соблюдено —
бюджет просто свой.

#### 3.11.4 Раздел «🧠 Память»

* **👥 Люди** — список с пагинацией по 6 → карточка: имя, отношение, алиасы,
  факты с категориями и корзиной у каждого (по 5 на страницу), «Удалить
  человека» с подтверждением. Удаление человека уносит факты **только о нём**;
  общие с другими остаются у других.
* **🗑 Забыть** — точечно, каждое с подтверждением: текущий разговор (лог
  этого чата, факты остаются) / все разговоры / все факты (люди остаются) / всё.

#### 3.11.5 Ограничения — честно

* **Нет эмбеддингов.** Узнавание известных — по именам; сопоставление новых
  написаний — модель. Значит: «тот высокий парень с прошлой встречи» ни с кем
  не свяжется, и это нормально для v1. Когда людей станут сотни, здесь
  понадобится векторный поиск.
* **Резолвер лексический.** «Марк» узнается в «марке», «Лена» в «лентяе»
  не узнается (длина), но подобные ложные срабатывания возможны. Цена ошибки
  невелика: в контекст попадёт лишний блок фактов, модель его проигнорирует.
* **Без сжатия лога.** Очень длинная сессия (сотни реплик) упрётся в контекст
  модели. Пауза в час закрывает сессию, так что на практике это редкость;
  явного потолка пока нет.
* **Факты только добавляются.** Противоречия («Саша переехал в Москву» после
  «живёт в Казани») лягут рядом; слияния и устаревания нет. Модель видит оба
  с датами и обычно разбирается, но это не гарантия.
* **Вопрос «тот же или новой?» уходит только в Telegram.** Голосовой разговор
  своего чата не имеет — вопрос уйдёт в последний активный чат.

### 3.12 Инструменты

#### 3.12.1 Чем инструмент отличается от скрипта

| | Скрипт (`run_script`) | Инструмент (`tool_call`) |
|---|---|---|
| Кто пишет код | Модель, на лету | Мы, заранее, с тестами |
| Подтверждение | Да, для нового | Нет |
| Параметры | Свободные | Объявлены схемой |
| Когда | Действие на этой машине | Данные, которые модель не знает: время, интернет |

Инструмент — это «детерминированная функция, которую модели незачем
изобретать». Раньше «который час» превращался в Python-скрипт с запросом
подтверждения; теперь это `get_current_time` за одно обращение.

#### 3.12.2 Доступные инструменты

**`get_current_time`** — дата, время, день недели, часовой пояс. Аргумент
`timezone` (необязательный, `Europe/Moscow`). Детерминирован, сети нет.

**`web_search`** — поиск с чтением страниц. Аргумент `query` — о чём искать,
своими словами; точный запрос формулируется отдельно.

```
вопрос пользователя
  -> модель: короткий поисковый запрос (3–8 слов)          [бюджет −1]
  -> провайдер: до 6 ссылок со сниппетами
  -> модель: отвечают ли сниппеты на вопрос?               [бюджет −1]
       нет + новая формулировка -> снова поиск             (до max_reformulations раз)
  -> 1–2 лучшие страницы скачиваются, HTML вычищается
  -> результат: запрос + сниппеты + тексты страниц + источники
  -> модель формулирует ответ пользователю                 [бюджет −1]
```

Обычный поиск стоит 4 обращения из 15 (решение, запрос, оценка, ответ).

*Когда модель ищет.* Два режима, оба описаны словами в
`DecisionProtocol.toolRulesBlock()` (общий для промптов со скриптами и без)
и в `description()` инструмента:

| Режим | Когда | Ограничение |
|---|---|---|
| **Обязательный** | курсы, погода, новости, цены, версии, расписания, события, «сейчас / сегодня / последний» — то, что могло измениться или чего модель знать не может | — |
| **По усмотрению, в беседе** | разговор зашёл о конкретном — человеке, событии, продукте, месте, книге, фильме, числах, датах — и модель не уверена в деталях или знания могли устареть; цель — говорить предметно, а не «кажется, что-то такое было» | не болтовня, мнения, эмоции, советы из общих знаний и то, что уже прозвучало в разговоре (включая прошлый поиск); **не больше одного поиска на сообщение** и только когда он меняет ответ |

Найденное вплетается в ответ как собственное знание — промпт формулировки
(`toolSummaryPrompt`) не изменился: коротко, без «я поискал», источник одной
фразой. **Персона может сдвинуть границу в любую сторону** («ищи только когда
попрошу» / «проверяй факты всегда») — в промпте это сказано явно, как и для
живого стиля.

**Отдельного тумблера «поиск во время беседы» нет, и это решение.** Причины:
это не другой механизм, а те же критерии выбора `tool_call(web_search)`,
и тумблер означал бы два промпта с двумя границами «когда искать», которые
надо держать в согласии; стоимость и так ограничена существующими ручками
(`max_reformulations`, `fetch_pages`, бюджет запроса с резервом на ответ,
см. 3.8.3); а «искать реже / только по просьбе» — вопрос манеры, то есть
персоны, а не флага. Если понадобится выключить поиск целиком, это будет
`[tools.web_search] enabled = false` на старте (инструмент не регистрируется),
а не живой переключатель.

Если бюджет кончился посреди поиска в беседе, пользователь **не** видит
служебной ошибки: ядро отвечает из знаний модели на зарезервированное
обращение (3.8.3, `answerWithoutTool`).

**`set_reminder`** — поставить напоминание. Аргументы: `fire_at` (ISO-8601
со смещением), `prompt` (заметка «для будущего себя»), `summary` (2–5 слов
для списка), `repeat` (`""` / `daily` / `weekly:MON,WED`). Инструмент **не
разбирает** «через два часа» и «в следующий вторник» — считает модель, для
этого в системный промпт решения всегда добавлен блок «Сейчас: …» с датой,
временем, днём недели и смещением. Инструмент проверяет только, что момент
в будущем и не дальше года. Про планировщик он не знает — запись делает
`Sink`, который подставляет ядро, поэтому `tools` не зависит от `scheduler`.
Подробнее — [3.13](#313-напоминания).

**`manage_reminders`** — отменить (`cancel`) или перенести (`reschedule`,
`fire_at`) напоминание по `job_id`. Номера модель берёт из блока «Активные
напоминания» в системном промпте решения (до 10 ближайших: id, когда, о чём),
поэтому «отмени напоминание про врача» — один вызов без поиска. Перенос
сохраняет id, так что привязка пункта списка к напоминанию не рвётся.

**`read_clipboard`** — текст из буфера обмена, **только по явной фразе**
(«возьми то, что я скопировал», «из буфера»). Параметров нет. Подробнее —
[3.16](#316-буфер-обмена).

**`notes_tool`** — заметки и списки с чекбоксами. `action` — одно из
`create_list`, `create_note`, `add_item`, `check_item`, `uncheck_item`,
`remove_item`, `append`, `read`, `find`, `list_all`, `delete`; `name` — как
пользователь назвал документ; `text`, `item` (номер или текст пункта),
`tags`, `remind_at`, `query`. Без подтверждения: это правка собственных
заметок пользователя, а не системы. Описание объявляет модели, что про
заметки она знает **только через инструмент**: любой вопрос «есть ли / найди /
что в списке / покажи / какие есть» — сначала `find` / `read` / `list_all`,
а не ответ по памяти диалога. `find` называет качество совпадения (точное,
по названию/тегам, только похожие, ничего) — [3.14.4](#3144-запиши-в-список-задач-x-как-выбирается-список).

*Провайдеры.* Brave Search API: `GET https://api.search.brave.com/res/v1/web/search`,
ключ в заголовке `X-Subscription-Token` — проверено по документации. Но
с февраля 2026 у Brave **нет бесплатного тарифа**: ~$5 за 1000 запросов
и обязательная карта. Поэтому по умолчанию работает DuckDuckGo через
`html.duckduckgo.com` — без ключа, разбором HTML. Хрупко по определению
(сменят вёрстку — сломается), зато из коробки. `provider = "auto"` берёт
Brave, если задан ключ, иначе DDG.

Два условия, без которых DDG отдаёт антибот-заглушку с HTTP 202 вместо
выдачи (проверено): User-Agent настоящего браузера — с Chrome-подобным пришла
заглушка, с Firefox-подобным результаты — и заголовок `Accept-Language`.
Ссылки в выдаче обёрнуты в редирект `//duckduckgo.com/l/?uddg=<url>`.

*Чтение страниц.* Сниппета для ответа обычно мало — курс обрезан, новость
одним предложением — поэтому 1–2 лучшие ссылки открываются по-настоящему.
HTML вычищается своими регулярками (скрипты, стили, навигация, теги, сущности);
jsoup ради этого не тащим. Не-HTML пропускается, JS-приложения без серверного
рендера дадут пустоту — тогда остаёмся со сниппетом.

*Проактивность.* Пользователь не обязан говорить «погугли». Основная работа
на промпте решения: там описаны оба режима — обязательный и по усмотрению
в беседе (таблица выше). Страховка только для обязательного —
`FreshnessHints`: если в вопросе есть временны́е или рыночные слова, к запросу
дописывается подсказка «похоже, нужны актуальные данные — используй
web_search». Регулярки не решают, они подталкивают; для поиска «по
усмотрению» регулярок нет намеренно — «не уверен в деталях» словами не
поймать, это решает модель. Проверено вживую:
«какой сейчас курс доллара к рублю?» → `tool_call(web_search)` без просьбы,
ответ «≈ 84,20 ₽ за 1 USD (данные ЦБ РФ)» из прочитанной страницы.

> `\b` в Java-регулярках по умолчанию считает буквами только ASCII — с кириллицей
> граница слова не находится вовсе, и все триггеры молча не срабатывали. Нужен
> `Pattern.UNICODE_CHARACTER_CLASS`. Теперь это ловит тест.

#### 3.12.3 Как добавить инструмент

1. Реализовать `Tool` в модуле `tools`: `name()` (строчная латиница и `_`),
   `description()` и `parameters()` по-русски — они уходят в промпт,
   `execute(arguments, context)`. Аргументы приходят от модели: типы не
   гарантированы, `null` возможен, проверять самим.
2. Если нужна модель — только через `context.llm().ask(...)`. Это единственный
   способ, и он списывает общий бюджет. При `BudgetExhausted` — пробросить,
   ядро само ответит пользователю.
3. Зарегистрировать в `SupervisorMain.buildTools()`. **Всё.** В `enum` схемы
   и в промпт имя попадёт из реестра; ветки в цикле, новых типов, правки
   `DecisionProtocol` не нужно.
4. Тест без сети: `ToolContext` с скриптованным `LlmCaller`, внешние сервисы —
   локальный `HttpServer`, как в `WebSearchToolTest`.

Что инструмент делать **не должен**: менять файлы или систему без
подтверждения (для этого скрипты), ходить в Ollama напрямую, заводить свой
лимит обращений.

Конфиг — `[tools.web_search]`: `provider`, `brave_api_key`, `max_results`,
`fetch_pages`, `max_page_chars`, `max_reformulations`, `timeout_seconds`.
Читается на старте.

### 3.13 Напоминания

#### 3.13.1 Общая картина

```
«напомни через 2 часа сходить к врачу»
   -> решение модели: tool_call(set_reminder, fire_at=17:00, prompt=«Пора напомнить про врача»)
   -> ядро пишет строку в jobs с ключом разговора (TELEGRAM:123)
   -> модель формулирует ответ: «Напомню в 17:00»                             ✔

... агент включён, тик каждые 30 с ...

17:00  -> JobRunner: задание наступило -> статус FIRED
       -> ReminderService: UserMessage(SYSTEM, «[планировщик] Сейчас 17:00.
          Сработало напоминание. Твоя заметка: Пора напомнить про врача ...»)
       -> AgentCore.handle -- как обычное сообщение, с памятью и бюджетом
       -> ответ -> в тот же чат Telegram + notify-send                        ✔
```

Три решения, из которых всё следует:

* **Целевой момент считает модель, а не парсер дат.** «Через два часа»,
  «завтра в девять», «в следующий вторник после обеда» — вариантов не счесть,
  а у модели есть контекст разговора. Для этого в системный промпт решения
  всегда добавлен блок «Сейчас: суббота, 19 сентября 2026, 15:00 (Europe/Moscow,
  +03:00)». Инструмент получает уже ISO-момент и проверяет только, что он
  в будущем и не дальше года.
* **Задание хранит не текст напоминания, а промпт «для будущего себя».**
  В момент срабатывания модель получает эту заметку и формулирует напоминание
  заново — с учётом того, что она к тому времени знает (память, текущий час).
  Поэтому «напомни позвонить маме» через три часа звучит по-человечески, а не
  как эхо запроса.
* **Срабатывание — это `UserMessage` с `source = SYSTEM`**, поданное в тот же
  `AgentCore.handle`. Не отдельный вызов модели из планировщика: тогда пришлось
  бы дублировать бюджет, память, флаг ON/OFF и доставку. Ответ уходит в чат,
  из которого напоминание ставили, — ключ разговора лежит в строке `jobs`.

#### 3.13.2 Схема `jobs`

Отдельная база `scheduler.db` (`[scheduler] db_path`):

| Поле | Смысл |
|---|---|
| `id` | Первичный ключ; он же уезжает в `callback_data` (`rem:view:<id>`) |
| `fire_at` | Момент срабатывания, ISO-8601 в UTC |
| `prompt` | Промпт-инъекция «для будущего себя» |
| `summary` | 2–5 слов для списка в меню |
| `conversation_key` | Куда вернуть ответ: `TELEGRAM:<chat>` или `VOICE:-` |
| `repeat` | `""` — разово, `daily`, `weekly:MON,WED` |
| `status` | `PENDING` → `FIRED` / `MISSED` / `CANCELLED` |
| `created_at`, `fired_at` | Когда поставлено и когда сработало |
| `trace_id` | Запрос, в котором напоминание поставили |

Индекс `idx_jobs_due (status, fire_at)` — тик каждые полминуты спрашивает
«что уже пора», это единственный горячий запрос.

Повторяющееся задание — цепочка строк: сработавшая уходит в историю, а на
следующий момент (`Repeat.next`, уже прошедшие даты пропускаются — после
недельного отпуска не будет семи «зарядок» подряд) создаётся **новая строка**
с тем же промптом и правилом. Так у каждого срабатывания своя история
и свой статус. Следующая строка появляется только при срабатывании
предыдущей, поэтому отмена активной останавливает всю серию.

#### 3.13.3 Тик планировщика

`JobRunner` — один поток-демон `scheduler-tick`, `scheduleAtFixedRate`
с интервалом **`[scheduler] tick_seconds`** (по умолчанию 30). Точность
срабатывания — плюс-минус этот интервал; меньше 10 секунд ставить незачем,
а больше пары минут делает «напомни через 5 минут» заметно неточным.

Тик работает **только пока агент включён**: хук `reminders.onAfterStart`
запускает, `onBeforeStop` останавливает. При выключенном агенте задания лежат
в базе и ждут — тик их не трогает, а даже если бы тронул, ядро на `SYSTEM`
при OFF отвечает молчанием.

Задание помечается `FIRED` **до** вызова обработчика: если модель зависнет или
упадёт, следующий тик не выстрелит тем же заданием второй раз. Цена — упавшее
срабатывание теряется; это лучше, чем два одинаковых напоминания.

#### 3.13.4 Догоняющие напоминания

Задание может наступить, когда некому его отдать: агент был выключен, процесс
не работал, компьютер спал. Тогда оно всё равно должно дойти — с извинением.

```
onAfterStart (агент включили в 19:00)
   -> JobRunner.catchUp(): все PENDING с fire_at <= сейчас
   -> для каждого: опоздание > late_tolerance_minutes?
        нет -> обычная инъекция, статус FIRED
        да  -> статус MISSED + догоняющая инъекция:
               «Сейчас 19:00. Напоминание должно было сработать в 17:00
                (2 ч назад) и не сработало -- агент был выключен или
                компьютер спал. Извинись и всё равно напомни; если момент
                уже прошёл, скажи об этом честно.»
   -> запустить тик
```

Порядок важен: **сначала догон, потом старт тика**, иначе они могут выстрелить
одним заданием наперегонки.

**Скачок времени между тиками** (компьютер уснул при включённом агенте)
определяется в самом тике: если с прошлого тика прошло больше 4×`tick_seconds`,
пишется `WARN scheduler.gap`. На классификацию это не влияет — «вовремя»
или «пропущено» решает один и тот же допуск **`late_tolerance_minutes`**
(по умолчанию 5), и для тика, и для догона. То, что опоздало на две минуты,
уйдёт обычным напоминанием; то, что на два часа, — догоняющим.

Догоняющая инъекция — та же модель, тот же цикл; модель извиняется сама,
шаблонной фразы в коде нет. Слово «не сработало» в промпте — не для
пользователя, а для модели; проверяется тестом.

#### 3.13.5 Десктопные уведомления

`notify-send` дублирует **именно напоминания и только их**: обычные ответы
на рабочий стол не идут. Показывается текст ответа модели (а не сырой промпт),
заголовок «⏰ Напоминание». Аргументы передаются списком через
`ProcessBuilder` — без шелла; если `notify-send` нет в `PATH`, это одна строка
в логе на старте, а не ошибка. Выключается через
`[scheduler] desktop_notifications = false`.

#### 3.13.6 Отмена и перенос словами

В системный промпт решения ядро дописывает `ReminderService.promptBlock()` —
список активных заданий с номерами. Без него модель не может ни отменить,
ни перенести: искать по тексту она бы гадала, а спрашивать id у пользователя
бессмысленно. Дальше — `manage_reminders(cancel | reschedule, job_id)`;
`JobStore.reschedule` меняет только `fire_at`, статус и id остаются.
Проверено сквозь ядро: промпт содержит `#<id> — 19 сентября 2026, 17:00 — врач`,
отмена переводит задание в `CANCELLED`, перенос сохраняет номер.

#### 3.13.7 Раздел «⏰ Напоминания»

* **📅 Активные** — `PENDING`, по 6 на страницу, ближайшие первыми → карточка:
  когда, повтор, статус, заметка для агента, «❌ Отменить».
* **🗄 История** — `FIRED` ✅ / `MISSED` ⏰ / `CANCELLED` ✖️, свежие первыми,
  «🗑 Очистить историю» с подтверждением — активные не трогает.

Поставить напоминание из меню нельзя, только словами: у постановки слишком
много свободных параметров для кнопок, а модель с ними справляется.

#### 3.13.8 Ограничения — честно

* **Часовой пояс один — системный.** Задание хранится в UTC, показывается
  в поясе машины; «напомни в 9 по Токио» модель посчитает, но покажется оно
  в местном.
* **Активных в промпте не больше десяти.** При большем числе модель видит
  ближайшие; остальное — в меню.
* **Голосовое напоминание** ставится с разговором `VOICE:-`, а ответ на него
  уйдёт в последний активный чат Telegram — как и всё голосовое до `tts-bridge`.
* **Упавшее срабатывание не повторяется** (см. 3.13.3): в истории оно будет
  `FIRED`, хотя пользователь ничего не получил. По `trace_id` `job-<id>` это
  видно в логах.

### 3.14 Заметки и списки

#### 3.14.1 Где лежат и как открыть

Отдельный каталог — `[notes] dir`, по умолчанию `~/.agent-data/notes/`.
Это **свой git-репозиторий**, не тот, где код агента: у заметок своя история,
и `git log` там читается как журнал изменений. Создаётся при первом запуске
(`git init`, ветка `main`, `.gitignore` для индекса).

```
~/.agent-data/notes/
  .git/            история: коммит на каждое изменение
  .gitignore       .index.db*
  .index.db        SQLite-индекс, пересобирается из файлов
  lists/*.md       списки с чекбоксами
  notes/*.md       заметки
```

**Источник правды — файлы.** Каталог открывается как vault в Obsidian
(«Open folder as vault» → `~/.agent-data/notes`): frontmatter и чекбоксы
`- [ ]` — это его родной синтаксис, теги из шапки попадают в панель тегов.
Править можно чем угодно: содержимое известных файлов читается с диска при
каждом обращении, а перед каждым чтением набор `.md` в каталогах сверяется
с индексом — новый или удалённый снаружи файл подхватывается **сразу**, без
перезапуска (это одно `Files.list` на каталог, на десятках файлов бесплатно). Файл без шапки тоже подхватится: заголовок возьмётся
из имени, вид — из каталога (`lists/` или `notes/`).

Посмотреть историю руками:

```bash
cd ~/.agent-data/notes && git log --oneline        # «Покупки»: + молоко / ✓ молоко / − молоко
git show HEAD~3:lists/покупки.md                    # каким список был три правки назад
```

#### 3.14.2 Формат файлов

Список:

```markdown
---
title: Покупки
kind: list
created: 2026-09-19
tags: [дом, еда]
---

- [x] молоко
- [ ] хлеб
- [ ] сдать отчёт <!-- job:12 -->
```

Заметка — та же шапка с `kind: note` и свободный текст под ней. Шапка
разбирается вручную (четыре плоских поля), незнакомые ключи сохраняются
как есть. Между пунктами могут стоять заголовки и абзацы — редактирование
идёт построчно, и текст вокруг пунктов не трогается.

`<!-- job:12 -->` — привязка пункта к напоминанию (см. 3.14.5). HTML-комментарий
Obsidian в режиме чтения не показывает, а файл остаётся самодостаточным.

Имя файла — из заголовка: буквы и цифры любого алфавита остаются
(`покупки.md`), прочее — дефис, второй такой же заголовок получает `-2`.
Заголовок приходит от модели, поэтому `../../etc/passwd` → `etc-passwd.md`.

#### 3.14.3 Схема индекса

`.index.db`, таблица `documents`:

| Поле | Смысл |
|---|---|
| `id` | Стабильный номер; уезжает в `callback_data` (`nt:open:<id>`) — путь с кириллицей в 64 байта не влезает |
| `path` | Относительный путь, `lists/покупки.md`; уникален |
| `title`, `kind`, `tags` | Из шапки; теги через `\|` |
| `updated_at` | Время изменения файла |
| `preview` | Первые пункты или начало текста — для поиска и подсказок модели |

Индекс — кэш, не хранилище: его можно удалить, он пересоберётся. Именно
поэтому он в `.gitignore`.

#### 3.14.4 «Запиши в список задач X»: как выбирается список

Разбор естественного языка делает модель: `notes_tool(action=add_item,
name="задачи", text="X")`. Дальше `NotesStore.resolve(name)`:

1. точное совпадение заголовка без учёта регистра, знаков и дефисов
   (`Quality.EXACT`: «wi-fi» = «wifi») — берём;
2. иначе среди совпадений **по названию/тегам** (`Quality.NAME`: все значимые
   слова запроса есть в заголовке или тегах, либо одно содержит другое —
   «покупки» ↔ «Список покупок», «заметка про борщ» ↔ «Рецепт борща»,
   «еда» ↔ тег `#еда`) — по похожести заголовков; один кандидат или явный
   лидер (в 1,5 раза выше второго) — берём;
3. несколько близких («Задачи по дому», «Задачи по работе») —
   **`Ambiguous`**: инструмент возвращает ошибку с вариантами, и модель
   **спрашивает пользователя**, а не выбирает. Ничего при этом не создаётся
   и не добавляется — проверено тестом;
4. совпадение лишь по отдельному слову (`Quality.WEAK`: «рецепт пирога» при
   наличии только «Рецепта борща») — это **`NotFound`**, а не находка: раньше
   борщ отдавался как найденный и в `read`, и в `add_item`. Для `add_item`
   список создаётся с этим именем, для остальных действий — ошибка с похожими
   по названию и перечнем того, что есть, и просьбой уточнить, а не выбирать.

Значимые слова — без служебных: «список», «заметка», «про», «есть ли у меня»,
предлоги (`NotesSearch.GENERIC`, по 4-буквенным основам). Поэтому запрос
может быть и полной фразой пользователя: «есть ли у меня заметка с именем
рецепт борща» → значимые «рецепт», «борща».

Пункт для `check_item`/`remove_item` — по номеру с единицы или по тексту
(точно → подстрока → основы); несколько подходящих — тоже уточнение.

**`find` отвечает не «найдено / не найдено», а качеством совпадения** —
именно это модель обязана передать пользователю словами:

| Что нашлось | Ответ инструмента | Что скажет агент |
|---|---|---|
| `EXACT` | «Есть, название совпадает точно: «X»» + документ | «да, есть» |
| `NAME` (один или несколько) | «Есть, подходит по названию/тегам: «X», «Y» — несколько, уточни…» + документы | «да, есть» / «есть два похожих — какой?» |
| только `WEAK` (по слову в названии/тегах или по тексту) | «Документа «q» НЕТ. Есть лишь отдалённо похожие: «X» (слово «рецепт»), «Y» (по тексту). Скажи, что такой заметки нет, и назови похожие» | «нет, но есть «Рецепт борща»» |
| ничего по словам | **одно** обращение к модели с каталогом (id, заголовок, теги, превью): «что подходит по смыслу» — единица бюджета, только здесь | «по смыслу могут подходить…» |
| и по смыслу ничего | «Ничего похожего на «q» нет — ни по названию, ни по тегам, ни по тексту. Есть: …» | «нет такой; есть …» |

Слабые совпадения показываются пользователю словами, какими он сам их
написал («слово «рецепт»»), а не обрубками основ. Проверенные формулировки
(тест `NotesToolTest`, вручную — 30 запросов на 6 документах): «есть ли
у меня заметка с именем X», «заметка про X», «X» одним словом, тег, «что
у меня в списке X», `Wi-Fi`/`WIFI` против «wifi», «есть ли у меня список
задач» при двух списках задач, несуществующее имя с общим словом
и без него.

Вторая половина починки — **описание инструмента** (`NotesTool.description()`):
оно говорит модели, что содержимое заметок она знает **только через
инструмент**, и перечисляет формулировки, на которые его надо звать до
ответа: «есть ли у меня заметка/список X», «найди заметку про Y», «что у меня
в списке X», «покажи заметку X», «какие у меня есть списки», «где я записывал
про Z» → `find` / `read` / `list_all`. До этого «есть ли заметка X» модель
отвечала по памяти диалога — и заметку, созданную в прошлой сессии или из
Obsidian, «не находила». В `query` для `find` — название или тема без слов
«заметка / список / есть ли» (служебные всё равно отсеются, но так чище).

#### 3.14.5 Связь с напоминаниями

Пункт списка можно привязать к напоминанию — `add_item` с `remind_at`:
«запиши в дела сдать отчёт и напомни завтра в 9». Отдельного механизма нет:
ставится обычное задание в `jobs` через тот же `ReminderService`, что
и `set_reminder`, с промптом «Пора напомнить о пункте «сдать отчёт» из списка
«Дела»». Его id пишется в строку пункта, в меню пункт помечен ⏰. Отметка
«сделано» или удаление пункта **снимает** напоминание. Это единственное место,
где `tools` знает о планировщике, и знает через интерфейс `ReminderLink`,
который подставляет `SupervisorMain`.

#### 3.14.6 Раздел «📝 Заметки и списки»

Один общий раздел на оба вида:

* **➕ Создать** → «📋 Список» / «📝 Заметку» → бот ждёт название текстом
  (режим ожидания, `/cancel` отменяет) → сразу карточка.
* **📂 Загрузить** → документы постранично по 6, недавние первыми → карточка:
  для списка — пункты **кнопками-чекбоксами** (нажатие переключает ☐/☑),
  «➕ Пункт» (ждёт текст), «🗑 Пункты» (режим удаления: нажатие убирает);
  для заметки — текст и «✏️ Дописать». «🗑 Удалить» — с подтверждением.

Пункты — по 8 на экран с ◀️ ▶️ внутри карточки (`nt:open:<id>:<p>:<ip>`):
инлайн-клавиатура длиннее не читается. Нажатие на второй странице оставляет
на второй странице.

#### 3.14.7 Ограничения — честно

* **Поиск лексический**: точное и частичное совпадение по названию и тегам,
  по словам — в тексте; «по смыслу» — только запасной путь через модель.
  Транслитерация («вайфай» ↔ «wifi») и синонимы найдутся только по смыслу.
* **Нет переименования и перемещения** между списками — удалить и создать.
* **Одна папка, без вложенности.** Obsidian-vault с подпапками агент читать
  не будет: сканируются только `lists/` и `notes/`.

### 3.15 Персоны

#### 3.15.1 Что это

Персона — именованный текст системного промпта: кто агент и как отвечает
(«отвечай как пират», «ты строгий редактор, правь без комплиментов»).
В любой момент **ровно одна активная**, и переключение действует **на
следующий же ответ** — без перезапуска и без «применить».

Таблица `personas` в `personas.db` (рядом с `memory.db`, путь берётся от
`[memory] db_path`):

| Поле | Смысл |
|---|---|
| `id` | Первичный ключ; уезжает в `callback_data` (`per:act:<id>`) |
| `name` | Имя для списков, до 60 символов |
| `prompt` | Текст инструкции; пустой — поведение по умолчанию |
| `created_at` | Когда создана |
| `active` | `1` ровно у одной строки |

Инвариант «ровно одна активная» держится кодом, а не схемой: смена активной —
одна транзакция «`UPDATE personas SET active = 0`, потом `= 1 WHERE id`»;
удалить последнюю нельзя; удаление активной передаёт флаг соседней; на первом
запуске заводится «Стандарт» с базовой инструкцией. Новая персона активной
**не** становится — пользователь включает её сам.

#### 3.15.2 Как подмешивается в промпт

`PersonaStore.promptBlock()` — блок вида

```
Персона «Пират» — следуй этой инструкции во всех ответах:
<текст>
```

Ядро дописывает его в **каждый** системный промпт, который уходит в Ollama:
решение (`decisionPrompt + память + время + напоминания + персона`), починка
скрипта и обе формулировки ответа (после скрипта и после инструмента). Иначе
персона задавала бы стиль решению, а финальный текст шёл бы без неё.
Пустой `prompt` → пустой блок. Активная персона читается из базы **при каждом
обращении**, кэша нет — поэтому переключение из окна или чата действует
на следующий ответ, проверено тестом.

Персона — про стиль и роль, не про права: она не отменяет протокол решения,
подтверждения скриптов и бюджет.

#### 3.15.3 Где правится

| Где | Как |
|---|---|
| Окно → «Персоны» | Список слева, справа имя и текст; «Сохранить», «Новая», «Сделать активной», «Удалить» |
| Telegram → 🎭 Персоны | Список: **кнопка = сделать активной**, ✏️ — карточка; «➕ Создать» → имя текстом; в карточке «✏️ Текст инструкции» → текст следующим сообщением (режим ожидания, `-` очищает, `/cancel` отменяет), «🗑 Удалить» с подтверждением |

Оба интерфейса работают с одним `PersonaStore`; у него есть слушатели, и окно
перерисовывает список, когда активную сменили из чата. В Telegram текст
инструкции присылается **одним сообщением целиком** и заменяет прежний —
построчной правки в чате нет, для длинных инструкций удобнее окно.

### 3.16 Буфер обмена

**Читается только по явной просьбе**, никогда фоново. В буфере бывают пароли
и чужая переписка, и агенту незачем видеть их без слов пользователя. Поэтому
это инструмент `read_clipboard`, который модель зовёт по фразам вроде «возьми
то, что я скопировал», «переведи из буфера» — триггер в описании инструмента,
регулярок нет; `wl-paste --watch` и опроса по таймеру нет намеренно.

```
«переведи то, что я скопировал»
  -> решение: tool_call(read_clipboard)                     [бюджет −1]
  -> ClipboardBridge: wl-paste --no-newline --type text     (таймаут 3 с)
  -> ToolResult.okAsContext(текст, "CLIPBOARD")
  -> ядро: memory.append(session, USER, текст, source=CLIPBOARD)
  -> модель формулирует ответ                               [бюджет −1]
```

Ключевое — `okAsContext`: содержимое буфера кладётся в **лог сессии** отдельной
репликой с источником `CLIPBOARD` (тот самый `MessageSource.CLIPBOARD`).
Так следующее «а теперь на английский» имеет к чему относиться — текст уже
в истории, второй раз читать буфер не нужно. Это единственное место, где
результат инструмента становится репликой; механизм общий (`contextSource`
в `ToolResult`), а не проверка имени инструмента.

Почему `wl-paste`, а не `java.awt.datatransfer`: под Wayland JDK ходит через
XWayland и видит не тот буфер. `--type text` берёт текстовый MIME; картинка
или пустой буфер — код 1, инструмент отвечает «пусто или не текст», а не
падает. Текст обрезается до 20 000 символов. Пакет: `sudo pacman -S
wl-clipboard`; без него бридж пишет `WARN` на старте, а инструмент честно
отвечает, чего не хватает.

Ограничения: только чтение (запись в буфер — `wl-copy` — не заведена, когда
понадобится, это тот же класс); только текст; primary selection (выделение
средней кнопкой) не читается — это другой буфер, и он почти всегда содержит
что-то случайное.

### 3.17 Голосовые ответы (TTS)

#### 3.17.1 Установка Piper

Проект переехал: актуальный репозиторий — `OHF-Voice/piper1-gpl`, ставится
как Python-пакет `piper-tts` (проверено по документации и вживую в этой
сессии), а не бинарником из релизов старого `rhasspy/piper`. Без root,
в venv пользователя:

```bash
python3 -m venv ~/.local/share/bebebe-agent/piper-venv
~/.local/share/bebebe-agent/piper-venv/bin/pip install piper-tts
~/.local/share/bebebe-agent/piper-venv/bin/python -m piper.download_voices \
    --data-dir ~/.local/share/bebebe-agent/piper-voices ru_RU-irina-medium
```

Голоса лежат на HuggingFace в `rhasspy/piper-voices`; каждый — пара файлов
`<голос>.onnx` + `<голос>.onnx.json`. Русских четыре, все `medium`:
`ru_RU-irina-medium` (женский, по умолчанию), `ru_RU-denis-medium`,
`ru_RU-dmitri-medium`, `ru_RU-ruslan-medium`. Сменить — `[tts] voice`
и скачать соответствующий. Нужен ещё `ffmpeg` (`sudo pacman -S ffmpeg`).

Проверить руками:

```bash
echo "Привет, это проверка." | ~/.local/share/bebebe-agent/piper-venv/bin/piper \
    -m ~/.local/share/bebebe-agent/piper-voices/ru_RU-irina-medium.onnx -f /tmp/t.wav
```

Первый запуск — секунды (грузится модель ~60 МБ), короткая фраза — около
5 с на CPU; это цена локальности.

#### 3.17.2 Конфиг и тумблер

Секция `[tts]` (см. `config/agent.example.toml`): `piper_binary`, `voice`,
`voices_dir`, `ffmpeg_binary`, `length_scale`, `max_chars`, `timeout_seconds`,
`reply_to_text` — читаются на старте; чего не хватает, видно в логе при
запуске (`TTS не запущен: не найден голос …` с командой, что сделать).

**Тумблер «Голосовые ответы»** — `tts.voice_replies`, живая настройка
в `AppSettings`: правится в окне (Настройки) и в Telegram (⚙️ Настройки →
«🔊 Включить голосовые ответы»), пишется в конфиг, действует на следующий
же ответ. **По умолчанию выключен.**

#### 3.17.3 Поведение: текст + голосовое, не вместо

При включённом тумблере ответ уходит **текстом и следом голосовым
сообщением** — не голосом вместо текста. Причины: текст можно прочитать
в шумном месте, скопировать, найти поиском по чату; голосовое — удобство,
а не замена. Подпись у voice ограничена 1024 символами, у текста — нет,
поэтому это два сообщения, а не одно с подписью.

Что озвучивается:

| Запрос пришёл | Тумблер выкл | Тумблер вкл |
|---|---|---|
| Голосом (push-to-talk) | «🎤 текст» + ответ текстом | + голосовое |
| Текстом в Telegram | текст | текст; голосовое только при `tts.reply_to_text = true` |
| Напоминание | текст + notify-send | как текст в Telegram (это `SYSTEM`, не голос) |

Логика: спросили голосом — отвечаем и голосом; печатал — читает.
Подтверждения с кнопками и вопросы памяти не озвучиваются — их нужно нажать.

```
deliver(chat, reply, spoken)
   -> sendMessage(текст)                              всегда, первым
   -> spoken && тумблер && TTS готов?
        -> поток telegram-tts (не поллинг): SpeechText.prepare
           -> piper (stdin) -> wav -> ffmpeg -> ogg/opus
           -> sendVoice(multipart audio/ogg) -> удалить файл
```

Синтез идёт в отдельном потоке `telegram-tts`, под тем же `trace_id`; сбой
Piper или ffmpeg — `WARN` в логе, текст уже ушёл. `SpeechText` убирает
markdown, ссылки («ссылка»), блоки кода («фрагмент кода пропущен»), эмодзи;
длиннее `max_chars` (1500) режет по предложению и добавляет «Дальше — в тексте».

#### 3.17.4 Ограничения — честно

* **Только Telegram.** В колонки машины ответ не проигрывается — голосовой
  запрос отвечается в последний активный чат, как и раньше.
* **Голос один на всех.** Персона меняет текст, не тембр; смена голоса —
  конфиг и перезапуск.
* **Секунды задержки.** Piper на CPU — порядка секунды на предложение; текст
  приходит сразу, голосовое догоняет.
* **Русский голос читает латиницу по буквам.** Английские термины в ответе
  звучат плохо; это свойство модели.

### 3.18 Watchdog: зависание против падения

#### 3.18.1 Что именно ловим

Система — один JVM-процесс, поэтому «упал процесс» и «завис агент» — две
разные беды с разными лекарствами:

| | Падение процесса (crash) | Зависание (hang) |
|---|---|---|
| Что случилось | JVM нет: OOM-kill, `System.exit`, segfault в нативном коде | Процесс жив, окно и поллинг работают, а запрос не двигается: дедлок, бесконечный цикл, повисший сокет без таймаута |
| Кто видит | **Только снаружи** — `systemd --user` | Сторож внутри процесса |
| Лечение | `Restart=on-failure` в юните | Перезапуск **потока обработки**, не процесса |
| Где | `systemd/server-ai-agent.service` | модуль `watchdog` + `AgentWorker` |

**Падение процесса программно изнутри не ловится и не лечится** — того, кто
ловил бы, уже нет. Это известное ограничение, а не недоработка: единственный
честный ответ — внешний супервизор. В репозитории лежит
[`systemd/server-ai-agent.service`](systemd/server-ai-agent.service), он
**установлен и включён** на этой машине (`~/.config/systemd/user/`,
`WantedBy=graphical-session.target` — автозапуск при входе в сессию):
`Restart=on-failure`, `RestartSec=5`, `StartLimitBurst=5` за 10 минут в секции
`[Unit]` (в `[Service]` systemd его молча игнорирует — так и было в первой
версии, поймал `systemd-analyze verify`), `KillSignal=SIGTERM` + 30 с на
shutdown-хук. Запускается **стартовый скрипт `installDist`**, а не
`./gradlew run`: старт за секунды и падение JVM видно systemd напрямую, без
Gradle-демона между ними. Флаги `--enable-native-access` заданы в
`applicationDefaultJvmArgs`, поэтому попадают в скрипт. Штатный выход (закрыли
окно, exit 0) юнит не перезапускает.

Проверено вживую: `kill -9` главного процесса → через 5 с
`Scheduled restart job, restart counter is at 1` → окно, бридж и watchdog
поднялись заново. После обновления кода: `./gradlew installDist &&
systemctl --user restart server-ai-agent`; логи процесса —
`journalctl --user -u server-ai-agent -f`, логи агента — по-прежнему `logs/`.

#### 3.18.2 Heartbeat и «занят легитимно»

Вся обработка идёт в одном потоке — `AgentWorker` (`agent-worker-N`).
Каналы (поллинг Telegram, STT, тик планировщика) **подают** запрос
и ждут ответа; до этого `handle()` работал в потоке вызывающего, и зависание
нечем было прервать, не убив канал. Плата — запросы из разных каналов идут
по очереди; для личного агента это приемлемо и даже спокойнее для памяти.

`ActivityMonitor` — то, что читает сторож:

* **heartbeat** (`beat()`) — после каждого шага цикла: получен ответ модели,
  отработал инструмент, отработал скрипт;
* **сигнал «занят легитимно»** (`busy(reason, expected)`) — на время ожиданий
  с известным потолком: ответ модели (HTTP-таймаут `ollama.timeout_seconds`
  + 5 с) и скрипт (`scripts.timeout_seconds` + 90 с запаса на автоустановку
  пакетов). Пока сигнал жив, молчание heartbeat — это ожидание сети или
  дочернего процесса, и сторож его **не** трогает;
* **в работе / простой** — простой не зависание: при выключенном агенте
  или между сообщениями heartbeat не нужен вовсе.

#### 3.18.3 Подтверждённое зависание

`Watchdog` тикает каждые `check_seconds` (10) и объявляет зависание только
при **трёх** условиях сразу:

```
запрос в работе
  И heartbeat молчит дольше hang_timeout_seconds (90)
  И нет живого сигнала «занят легитимно» (истёк или не поднимался)
```

Скрипт на 15 секунд, модель, думающая минуту, `pip install` на две — всё это
под сигналом с известным потолком и зависанием не считается. Зависание — это
когда потолок вышел, а движения нет: сокет без таймаута, дедлок, инструмент
в бесконечном цикле.

Тогда, и только тогда: `AgentWorker.restart()` — прервать текущую задачу
(`InterruptedException` в ожиданиях), бросить старый поток, поднять новый
`agent-worker-N+1`; зависший вызов `handle()` получает `Restarted` и молча
закрывается; в Telegram — в разговор прерванного запроса, а если его нет,
в последний активный чат — уходит «🐶 Агент завис при обработке «…» (нет
активности N с) и был перезапущен. Повторите запрос.» Окно, поллинг, память,
планировщик при этом не трогаются: перезапускается **поток**, не процесс.
Счётчик перезапусков — `Watchdog.restarts()`, события `watchdog.hang`,
`watchdog.restart`, `worker.restart` в `watchdog.log` и `agent-core.log`.

Сторож работает всегда, независимо от ON/OFF.

#### 3.18.4 Мягкая остановка

Хук `graceful-stop` (первый в списке, `onBeforeStop` — то есть **до** смены
флага): если запрос в работе, ждём его до `agent.stop_grace_seconds` (20).
Скрипт дорабатывает при включённом агенте, и его ответ доставляется как
обычно. Не уложился — `interruptCurrent()`: `ScriptRuntime` на прерывание
шлёт процессу **SIGTERM**, даёт 3 секунды выйти и лишь потом **SIGKILL**;
пользователю уходит «Запуск прерван: агент останавливается». Прежде скрипт
убивался мгновенно `destroyForcibly`. Проверено тестами: двухсекундный
скрипт дожидаемся и отдаём ответ, пятидесятисекундный прерываем после
льготных двух.

#### 3.18.5 Где настраивается

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `watchdog.enabled` | `true` | Выключить сторож целиком |
| `watchdog.check_seconds` | `10` | Как часто смотреть |
| `watchdog.hang_timeout_seconds` | `90` | Молчание heartbeat, после которого (без сигнала занятости) — зависание; не меньше `check_seconds` |
| `agent.stop_grace_seconds` | `20` | Сколько ждать доработки при выключении |

Потолки сигналов занятости отдельно не настраиваются — они выводятся из
таймаутов модели и скриптов, чтобы не расходиться с ними.

#### 3.18.6 Ограничения — честно

* **Один поток — одна очередь.** Долгий скрипт задерживает ответ на следующее
  сообщение из другого канала. Параллельные воркеры — когда понадобятся.
* **Сторож ловит только поток обработки.** Зависший поллинг Telegram или
  слушатель клавиши он не видит: у них свои механизмы повтора с нарастающей
  паузой, но контроля их живости нет.
* **`Thread.interrupt` — не гарантия.** Код, который игнорирует прерывание
  (нативный вызов, `while(true)` без проверок), останется висеть в старом
  потоке-демоне; новый поток при этом работает, а старый доживёт до конца
  процесса. Утечка одного потока — цена того, что мы не убиваем процесс.

### 3.19 Статус, логи, версия и бэкап

#### 3.19.1 Экран «Статус» — только в окне

В Telegram раздела «Статус» нет намеренно: главное, что там показывается, —
«есть ли сеть и отвечает ли Ollama», а без сети сообщение об этом в Telegram
и не дойдёт. Окно на локальной машине — единственное место, где статус
честен.

| Строка | Откуда |
|---|---|
| Агент | `AgentSwitch` |
| Последняя ошибка | `LogBuffer.lastError()` — последний `ERROR` из logback, с подсистемой и исключением |
| Ollama | `OllamaStats`: **по факту последнего вызова**, не пинг по таймеру. «Доступна» — последний успешный вызов позже последнего сбоя; иначе «НЕДОСТУПНА» с текстом ошибки |
| За сессию / Всего | Вызовы, токены (`prompt_eval_count + eval_count`), сбои; «всего» — в `~/.local/share/bebebe-agent/ollama-stats.json` |
| Диск | `FileStore.getUsableSpace()` для каталога данных и каталога логов |
| Версия | `BuildInfo`: коммит, ветка, есть ли незакоммиченные правки, дата коммита |
| Обновления | Последний результат `UpdateChecker`; кнопка «Проверить обновления» |
| Watchdog | Сколько раз перезапускался поток обработки |

Обновляется раз в 2 секунды по таймеру JavaFX; ничего не блокирует.

#### 3.19.2 Экран «Логи»

Источник — `LogBuffer`: кольцевой буфер последних 3000 строк, который
наполняет аппендер logback на root. То есть окно показывает ровно тот поток
событий, что уходит в JSON-файлы, с теми же полями (`subsystem`, `trace_id`,
`kv`, `error`), и ничего не пишется в буфер мимо логгера.

Фильтры: минимальный уровень, подсистема, `trace_id`, текст сообщения;
«Следить» прокручивает к новым строкам. **Двойной клик по строке подставляет
её `trace_id`** — вся цепочка запроса в один жест, без `grep`.

**Переключатель уровня** (`TRACE … ERROR`): `AppLogging.setLevel()` меняет
уровень логгера `com.bebebe.agent` сразу и `ConfigFileWriter.update` пишет
`[logging] level` в конфиг — переживёт перезапуск. Комментарии и остальные
ключи файла не трогаются, как и при любой записи из интерфейсов.

#### 3.19.3 Самоосознание версии

При каждой сборке Gradle-таск `generateBuildInfo` в `supervisor-app`
спрашивает git и кладёт в ресурсы `build-info.properties`:

```
commit=5af699bc…      commit.short=5af699b      commit.time=2026-09-19T01:20:47+05:00
branch=master         dirty=true                remote=git@github.com:qateralong/server-ai-agent.git
build.time=…
```

`BuildInfo.load()` читает его с classpath; без файла (запуск из IDE без
Gradle) версия «неизвестна», проверка обновлений пропускается.

`UpdateChecker` — один запрос `GET /repos/{owner}/{repo}/compare/{коммит}...{ветка}`
к GitHub API: `ahead_by` — сколько коммитов в ветке новее сборки, из
`commits` — до трёх заголовков. Репозиторий приватный, поэтому нужен токен;
берётся по порядку: `[updates] github_token` → `$GITHUB_TOKEN` →
`gh auth token`. Последнее — рекомендованный путь: GitHub CLI уже залогинен,
и секрета в конфиге нет вовсе (так и работает на этой машине: проверено
вживую, «сборка актуальна»).

Расписание: через 30 с после старта, если прошлая проверка была раньше чем
`check_hours` (24) назад, дальше по таймеру. Состояние — `update-check.json`
рядом с базами: время проверки и `notified_sha` последнего коммита, о котором
уже говорили. О новых коммитах сообщается **один раз на коммит**: в Telegram
(последний активный чат) и на экране «Статус». **Автообновления нет** —
только информирование; обновление — `git pull` и перезапуск руками.

Ограничение: сравнение идёт с коммитом, **с которого собрано**, а не с рабочим
деревом; `dirty=true` в версии напоминает, что локально есть незакоммиченное.
Если коммит сборки не запушен, API вернёт 404 — подсказка об этом есть в ошибке.

#### 3.19.4 Экспорт/бэкап

`BackupService` собирает один zip:

| В архиве | Что это |
|---|---|
| `memory.db` | Лог сессий, сущности, факты |
| `personas.db` | Персоны |
| `scheduler.db` | Напоминания: активные и история |
| `notes/lists/*.md`, `notes/notes/*.md` | Снимок заметок; **полная история — отдельный git-репозиторий** `~/.agent-data/notes`, на это указывает `README.txt` |
| `config.toml` | Конфиг **без секретов** |
| `README.txt` | Что внутри, что вырезано, как восстанавливать |

**Секреты исключаются всегда**: значения ключей, в имени которых есть `token`,
`api_key`, `secret` или `password` (ключ Ollama, токен бота, Brave, GitHub),
заменяются на `"<исключено из бэкапа>"`; сами ключи остаются, чтобы файл
читался как шаблон. Список вырезанного пишется в `README.txt` и показывается
в интерфейсе с предупреждением — после восстановления их придётся вписать
заново. Это следствие решения хранить секреты открытым текстом (1.7):
раз файл не защищён, копировать его целиком в архив, который поедет
в облако или в чат, нельзя.

SQLite копируется через `VACUUM INTO`, а не копированием файла: базы открыты
в WAL, и файл без `-wal` был бы неполным.

| Где | Как |
|---|---|
| Окно → «Статус» → «Экспорт/бэкап…» | Выбор каталога → архив → итог с предупреждением о секретах |
| Telegram → ⚙️ Настройки → «💾 Бэкап (без секретов)» | Архив собирается в `~/.local/share/bebebe-agent/backups/` и приходит **документом** в чат с тем же итогом подписью |

Помнить: файл в Telegram остаётся на серверах Telegram. Секретов в нём нет,
но факты о людях и заметки — есть; это личные данные, и решение отправлять
их туда — за пользователем, кнопка об этом не спрашивает.

| Симптом | Причина |
|---|---|
| `Telegram-бридж не запущен: не задан telegram.bot_token` | Пустой токен или `enabled = false` |

| Переключил провайдера, а ответ пришёл от старого | Так и задумано: запрос уже шёл — доводится на прежнем, следующий пойдёт на новый |

### 3.21 Сквозные сценарии и известные шероховатости

#### 3.21.1 Что проверено сквозь весь процесс

Каждый сценарий — тест в `EndToEndScenariosTest`, поднимающий полный граф
через `AgentAssembly` (тот же класс, что и `main`). Вход — как в жизни:
JSON-обновление в стаб Telegram, «распознанный» голос в `handleVoice`, тик
планировщика; выход — сообщение в чат, голосовое, файл, факт в базе.

| Сценарий | Что подтверждено |
|---|---|
| **Голос → скрипт → починка → текст + голос.** «Открой Spotify» голосом: скрипт падает, после подтверждения кнопкой модель чинит, версия 2 запускается | «🎤 текст» в чат, кнопки подтверждения, ответ текстом и `sendVoice`; оба запуска (`script.audit`) под **одним `trace_id`**; в каталоге один скрипт версии 2, а не два |
| **Текст → `web_search` с переформулировкой.** Первая выдача не о том, модель переформулирует, вторая подходит, страница читается | 2 обращения к «DDG», ровно 5 вызовов модели из бюджета 15 (решение, запрос, две оценки, ответ); один `trace_id` на `request.start`, `tool.call`, `web.search`, `reply.ready`, `reply.sent`; в промпт формулировки попал текст страницы, не сниппет |
| **«Запиши в список задач…» → `notes_tool` → меню.** | Файл `lists/задачи.md` создан, карточка `nt:open` показывает «☐ купить хлеб»; без подтверждения, 2 вызова модели |
| **Напоминание вовремя и догоняющее.** «Напомни в 17:00»; тик после 17:00; второе напоминание, агент выключен в момент срабатывания, включён через 3 часа | Задание в разговоре `TELEGRAM:<chat>`; ответ на `SYSTEM`-сообщение в тот же чат, статус `FIRED`; после включения — догон, статус `MISSED`, в промпте «не сработало», в чате извинение |
| **Новый человек → сущность → факт → вспомнил.** «Мой друг Саша не ест мясо», выключение (консолидация), «что приготовить Саше?» | Сущность «Саша» создана, факт в системном промпте следующего запроса, вопроса «тот же?» не было |
| **Рискованный скрипт → отказ.** «Удали все мои файлы» → `cfm:no` | Ни одного `script.audit`, статистика скрипта нулевая, после отказа модель не дёргается, в чате «Отменено» |
| **Смена персоны.** `per:act` в меню между двумя «привет» | Первый промпт с «Стандарт», второй — с «Пират» и его текстом |
| **Выключение во время скрипта.** Трёхсекундный скрипт, `turnOff()` посреди | Выключение ждёт ≥ 1 с, ответ скрипта доставлен, `stop.waiting` есть, `stop.interrupt` нет, сессия закрыта консолидацией |

Стыки, которые вскрылись и починены по ходу:

* **Ответ на голосовой запрос после подтверждения не озвучивался.** Подтверждение
  приходит кнопкой, и результат шёл правкой сообщения с кнопками — путь, где
  бридж не знает, что запрос был голосовым. Теперь `ConfirmationActions.confirm`
  смотрит на источник исходного сообщения: для `VOICE` ответ доставляется как
  ответ на голос (отдельным сообщением, с голосовым при включённом тумблере),
  а кнопки закрываются пометкой «✅ Выполнено — ответ ниже».
* **Починка плодила дубли в каталоге.** Промпт починки просит `run_script`
  с исправленным кодом, и `resolveScript` заводил новую запись с тем же именем.
  Теперь в цикле починки исправленный код — **новая версия упавшего скрипта**
  (`loop(…, failed)`), как и обещает 3.9.3.
* `wireSettings` не перечислял `VOICE_REPLIES` — работало случайно (тумблер
  читается на доставке), теперь явно.
* Провайдер DDG получил `tools.web_search.ddg_endpoint`: адрес HTML-версии
  теперь конфиг, а не константа, — и его можно подменить локальным стабом.
* Юнит systemd: `StartLimit*` были в `[Service]` и молча игнорировались;
  запуск через `./gradlew run` заменён на скрипт `installDist`.

#### 3.21.2 Известные шероховатости

* **Ответ на голос идёт в последний активный чат Telegram**, в том числе
  подтверждения и голосовые. Пока агентом пользуется один человек из одного
  чата — незаметно; появится второй чат — ответы поедут не туда.
* **Сборка сравнивается с коммитом, а не с рабочим деревом.** `UpdateChecker`
  берёт `commit` из `build-info.properties`; локальные незакоммиченные правки
  видны только как `dirty=true` на «Статусе».
* **Один поток обработки.** Долгий скрипт задерживает и голос, и чат,
  и напоминание (3.18.6).
* **Трея на этой машине нет** (GNOME без AppIndicator); окно возвращается
  повторным запуском, ярлыком или из Telegram. Расширение `gnome-shell-extension-appindicator`
  включит иконку без правок кода.
* **Проверка обновлений и бэкап в Telegram молчат при отсутствии сети** —
  по замыслу, но об этом легко забыть: смотреть «Статус» в окне.
* **`LogBuffer` один на JVM.** В сквозных тестах строки разных сценариев лежат
  в одном буфере; тесты фильтруют по `seq`, новый тест обязан делать так же.
* **Первый запуск скриптов создаёт venv** — секунды; в сквозных тестах venv
  общий на класс, в приложении — один на всё время (`scripts.venv_dir`).
* В `~/.config/systemd/user/` лежит **чужой старый `ai-agent.service`**
  (путь `~/AI`, задача `:supervisor-ui:run`, которых нет) — выключен
  и неактивен; удалить: `systemctl --user disable ai-agent; rm
  ~/.config/systemd/user/ai-agent.service`.
* **Секреты в бэкапе вырезаются по имени ключа.** Ключ, названный иначе
  (`pass`, `credential`), уедет в архив открытым — правило именования
  в разделе 5.

### 3.22 Провайдеры модели

#### 3.22.1 Какие есть и где переключать

| Провайдер | `id` | Стандартный endpoint | Модель по умолчанию | Ключ |
|---|---|---|---|---|
| Ollama | `ollama` | `https://ollama.com` | `gpt-oss:120b` | `https://ollama.com/settings/keys`; для локального демона пусто |
| Claude | `claude` | `https://api.anthropic.com` | `claude-opus-5` | `sk-ant-…` из консоли Anthropic |

Провайдер — **один на весь агент**, а не на канал или на персону: ядро,
консолидация памяти, инструменты (через `ToolContext.LlmCaller`) и «Тест
агента» ходят в один и тот же объект.

| Где | Как |
|---|---|
| Окно → **Настройки** | Выпадающий список «Провайдер», под ним поля выбранного: «API key», «Модель» (редактируемый список с кнопкой «Загрузить список»), и свёрнутый блок **«Для продвинутых»** с полем «Endpoint URL». Применяется по «Сохранить» |
| Telegram → **⚙️ Настройки** | Кнопка «🤖 Переключить на Claude / Ollama»; модель — кнопками из списка провайдера. Ключа и endpoint в чате нет — секреты только в окне |
| Файл | `[llm] provider = "…"` и слоты `[llm.ollama]` / `[llm.claude]` — см. ниже |

У каждого провайдера **свой слот**: ключ, модель, endpoint. Переключение
туда-обратно ничего не теряет — вернулся на Ollama, а там прежняя модель.
В форме окна слоты тоже держатся отдельно как черновики: можно поправить
ключ Claude, переключиться на Ollama, поправить модель и сохранить всё разом.

#### 3.22.2 Endpoint URL

Поле спрятано в «Для продвинутых» намеренно: в обычной жизни его не трогают.

* **Пусто** — стандартный адрес провайдера из таблицы выше. Именно так
  значение и хранится (`endpoint = ""`), поэтому смена стандартного адреса
  в коде подхватится сама.
* **Заполнено** — запросы идут туда. Зачем: локальный демон Ollama
  (`http://localhost:11434`, ключ пустой), прокси перед Anthropic API,
  self-hosted сервис с совместимым протоколом. Путь `/api/...` или `/v1/...`
  дописывает провайдер; указывать нужно только схему, хост и порт.
* Смена endpoint **пересоздаёт провайдера** (`SettingsField.LLM_ENDPOINT`
  помечен как `RECONNECT`), но процесс не перезапускается. Сквозные тесты
  подставляют стаб именно сюда — `AgentAssembly.Options.ollamaBaseUrl`
  пишет endpoint в слот Ollama.

#### 3.22.3 Как Claude ложится на протокол решения

Протокол ядра (`reply | tool_call | use_script | …`, [3.8.2](#382-протокол-решения))
провайдеро-независим: `LlmRequest` несёт системный промпт, историю, вопрос и
**JSON-схему**, а провайдер сам решает, как заставить модель её соблюдать.

* **Ollama** кладёт схему в `format` — как и раньше.
* **Claude** кладёт её в `output_config.format` (structured outputs Messages
  API, `JsonOutputFormat` в SDK). Схема та же самая, включая
  `additionalProperties: false`. Собственный tool-use Anthropic **не
  используется**: наши инструменты выбираются тем же `tool_call` в JSON, что
  и у Ollama, иначе `AgentDecision`, бюджет и логи пришлось бы раздваивать.
* История сессии у Anthropic обязана **чередовать роли**, а наш лог этого не
  гарантирует (два подряд сообщения пользователя, ответ инструмента и т. п.).
  `ClaudeProvider.alternate()` склеивает соседей одной роли и отбрасывает
  ведущую реплику ассистента. Проверено тестом.
* Ошибки Anthropic (`AnthropicServiceException`) переводятся в `LlmException`
  с подсказкой по коду — 401 ключ, 404 модель или endpoint, 429 лимит,
  529 перегрузка — тем же способом, что и у `OllamaException`. Ядро ловит
  только `LlmException`, от провайдера не зависит.
* `max_tokens`, таймаут и `temperature` — секция `[claude]`, читается на старте.
  `temperature` из запроса (её задаёт ядро) имеет приоритет.
* Список моделей — первая страница `/v1/models` (до 100). `autoPager()`
  SDK против стаба крутился бесконечно — поэтому явный `limit`.

Расширенное мышление намеренно не включено: решение — короткий JSON, а
ответ формулируется отдельным обращением; экономим и время, и токены.

#### 3.22.4 Смена провайдера посреди запроса

Решение: **запрос, который уже выполняется, доводится на прежнем провайдере;
новые запросы идут на выбранный.**

Как: `AgentCore` работает через `SwitchableProvider`. На входе каждого
сообщения он делает `pin()` и весь цикл — решение, починки, формулировка,
обращения изнутри инструментов — ходит в закреплённый объект.
`switchTo(id)` подменяет только `current`, закреплённый не трогается.
Единственный поток обработки `agent-worker` делает это тривиальным: поле
`pinned` одно на ядро.

Почему так, а не «переключить сейчас же»: середина цикла — это модель,
которая только что написала скрипт и сейчас должна его чинить. Подменить ей
провайдера — значит отдать починку модели, которая не видела ни кода, ни
промпта той семьи. Ответ вышел бы хуже, а разница в пару секунд того не стоит.

Уточнения:

* **Подтверждение кнопкой — новый сегмент**, он идёт уже на новый провайдер:
  ожидание может длиться до 10 минут, и держать старый провайдер ради него
  бессмысленно. Пользователь при этом видит запрос подтверждения от старого
  и формулировку ответа от нового — это допустимо.
* **Старый провайдер не закрывается** — HTTP-клиенты дёшевы, а на нём мог
  остаться запрос. Проверено тестом `ProviderSwitchTest`: инструмент внутри
  запроса переключает провайдера, а формулировка ответа всё равно идёт
  в закреплённый.
* `setModel` и `setApiKey` из настроек применяются только если правится слот
  **текущего** провайдера (`llm.id().equals(settings.provider())`); правки
  чужого слота дождутся переключения — их подхватит фабрика.

#### 3.22.5 Конфиг и обратная совместимость

```toml
[llm]
provider = "ollama"            # "ollama" | "claude"

[llm.ollama]
api_key = ""
model = "gpt-oss:120b"
endpoint = ""                  # пусто = https://ollama.com

[llm.claude]
api_key = ""
model = "claude-opus-5"
endpoint = ""                  # пусто = https://api.anthropic.com

[claude]                       # генерация, на старте
max_tokens = 4096
timeout_seconds = 120
temperature = 0.7

[ollama]                       # генерация, на старте
timeout_seconds = 120
temperature = 0.7
num_ctx = 8192
```

Старые `ollama.api_key` / `ollama.model` / `ollama.base_url` **продолжают
читаться** как запасное значение для слота Ollama, если `[llm.ollama]` пуст;
при первом сохранении из интерфейса значения лягут уже в новые ключи.
Бэкап без секретов знает про `llm.*.api_key` по маске `api_key`.

## 4. Что дальше

Порядок примерный, от фундамента к фичам.

### 4.1 Ближайшее

1. **Заметки: напоминание из меню.** Привязать пункт к напоминанию можно
   только словами; в карточке списка нет кнопки «⏰».
2. **Слияние и устаревание фактов.** Факты только добавляются; противоречия
   лежат рядом. Нужно хотя бы «этот факт заменяет тот» при извлечении.
3. **Логи: точечные уровни из окна.** Общий уровень переключается с экрана
   «Логи»; `[logging.levels]` для отдельной подсистемы — пока только в файле.
4. **Прополка каталога.** Скрипты только добавляются; нужны удаление, слияние
   дублей, «забыть то, что падает чаще, чем срабатывает».
5. **Восстановление из бэкапа кнопкой.** Сейчас — руками по `README.txt`
   из архива; обратная операция (распаковать, проверить, подменить базы
   при выключенном агенте) не написана. «📊 Статус» в Telegram не планируется
   — см. 3.19.1.

### 4.2 Агентный цикл

6. **Семантический поиск по каталогу.** Сейчас совпадение лексическое:
   «занятое место» и «сколько свободно» не сойдутся. На сотнях записей
   понадобятся эмбеддинги — см. [3.9.2](#392-поиск-почему-по-словам-а-не-запросом-к-модели).
7. **Потолок лога сессии.** Сотни реплик упрутся в контекст модели; нужна
   либо суммаризация *старой* части сессии (не текущей), либо жёсткое окно.
8. **Показывать, что происходит.** Между вопросом и ответом может пройти
   полминуты молча. Нужен хотя бы «выполняю скрипт…» в чат.
9. **Подтверждения вне Telegram.** Голосовой запрос, требующий разрешения,
   уходит кнопками в чат — в GUI такого экрана нет.
10. **Заметки: перенос и переименование.** Пункт между списками, заголовок
    документа — сейчас только через удалить/создать.
11. **Кэш поиска.** Один и тот же вопрос дважды за минуту — два раза в DDG
    и три обращения к модели. Короткий кэш по запросу окупится.
12. **Поиск: ссылки в ответе.** Модель называет источник фразой; иногда
    пользователю нужна сама ссылка. `ToolResult.sources` уже есть, осталось
    показывать.
13. **Напоминания: смена текста и повтора.** Перенос и отмена есть; изменить
    заметку или правило повторения — пока отмена + новое.
14. **Напоминания без Telegram.** Голосовое «напомни» ставит задание
    с разговором `VOICE:-`; ответ на него уйдёт в последний активный чат, как
    и всё голосовое. С `tts-bridge` — озвучивать.

### 4.3 Каналы

10. **Ответ на голос в колонки.** Сейчас голосовое уходит в Telegram; когда
    пользователь у машины, логичнее проиграть локально (`paplay`) — нужен
    признак «пользователь за компьютером».
11. **Голосовые в Telegram** — скачивание `voice` через `getFile` и передача
    в тот же `Transcriber`. Ogg/Opus придётся конвертировать в 16 кГц WAV
    (ffmpeg), whisper.cpp другого не принимает.
12. **Выбор голоса из меню.** Скачанные голоса можно перечислять
    в `voices_dir`; переключение без перезапуска — вопрос одного поля
    в `AppSettings`.
13. **Запись в буфер** (`wl-copy`): «скопируй ответ» — класс тот же,
    метода пока нет.
14. **Индикация записи.** Сейчас о том, что идёт запись, знает только лог.
    Нужен хотя бы индикатор в окне, иначе непонятно, слушает агент или нет.

### 4.4 Надёжность

16. **Watchdog для каналов.** Поток обработки под надзором; поллинг Telegram
    и слушатель клавиши переживают сбои сами, но за их живостью никто не
    следит — им нужен свой heartbeat в `HeartbeatSource`.
18. **`notes` сущностей.** Поле `notes` у сущности есть, но никто его
    не заполняет.
19. **Параллельные воркеры.** Один `agent-worker` — одна очередь; когда
    голосовые и чат начнут мешать друг другу, нужен пул с heartbeat на поток.
17. **Ограничение частоты** — Telegram режет отправку примерно на 30
    сообщениях в секунду; сейчас защиты нет.

### 4.5 Долгосрочный бэклог (после Этапа 1)

Это не «следующая сессия», а направления, в которые упрутся текущие
компромиссы. У каждого записано, какой именно компромисс он снимает и какой
ценой — чтобы не браться раньше времени.

1. **Эмбеддинги для каталога скриптов** вместо совпадения по словам
   ([3.9.2](#392-поиск-почему-по-словам-а-не-запросом-к-модели)). Снимает:
   «занятое место» и «сколько свободно» не сходятся. Цена: модель эмбеддингов
   (локальная через Ollama `/api/embed` или облачная), векторы в SQLite
   (`sqlite-vec`), пересчёт при правке описания. Порог — сотни записей;
   до него лексический поиск дешевле и предсказуемее. Тот же механизм потом
   подойдёт для выбора заметки по смыслу вместо обращения к модели в `find`.
2. **Строгая песочница для скриптов** — `bubblewrap` (или `firejail`)
   с явно выданными путями, без сессии D-Bus и сети по умолчанию, с профилем
   «GUI-скрипт» как исключением ([3.8.5](#385-безопасность-выполнения-осознанный-компромисс)).
   Снимает: код модели с правами пользователя. Цена: часть сценариев
   с управлением окнами перестанет работать; понадобится профиль на скрипт
   (что ему открыть) и UI, чтобы этот профиль подтверждать вместе с кодом.
   Обязательно, если агент когда-либо станет доступен не одному человеку.
3. **Векторный RAG для памяти и поиска.** Снимает три ограничения сразу:
   память узнаёт людей только по именам ([3.11.5](#3115-ограничения--честно)),
   лог сессии не сжимается и упрётся в контекст, веб-поиск читает 1–2 страницы
   целиком вместо релевантных кусков. Устройство: чанки фактов, старых
   сессий и скачанных страниц с эмбеддингами; в контекст — top-k по вопросу,
   а не «всё про упомянутых». Цена: ещё один индекс, который надо
   поддерживать, и заметно более сложная отладка «почему модель это не учла».
4. **Секреты через Secret Service API** (GNOME Keyring, `org.freedesktop.secrets`
   по D-Bus) вместо открытого текста в `config.toml` ([1.7](#17-конфигурация-и-секреты)).
   Снимает: любой процесс пользователя читает ключи. Цена: зависимость
   от разблокированного keyring при автозапуске из systemd (до входа в сессию
   его нет), запасной путь для headless-режима, миграция существующих
   конфигов. `SettingsField.secret` уже отделяет, что туда переедет.
5. **Режимы и профили контекста.** Сейчас в каждый запрос уходит один и тот же
   набор: весь лог сессии, факты упомянутых, процедуры, активные напоминания,
   персона. Профиль — именованный набор «что подмешивать и какие инструменты
   разрешены»: «работа» (заметки проекта, без личных фактов), «дом»,
   «стрим» (процедуры и скрипты OBS, без веб-поиска), «тихий» (без
   проактивности). Переключается как персона — вручную или по времени /
   расписанию. Снимает: рост контекста и лишние инструменты в промпте.
   Цена: ещё одна ось состояния рядом с персоной; нужно решить, что из них
   главнее и как это показать в двух интерфейсах.
6. **Мультипользовательский режим** — авторизация по человеку, раздельная
   память, подтверждения от того, кто просил, бюджет и частота на пользователя.
   См. README, раздел 5.4. Без пунктов 2 и 4 браться нельзя.

## 5. Соглашения

* **Язык комментариев и Javadoc** — русский, как и сообщения в логах и GUI.
* **Имя проекта — Server AI Agent, slug — `server-ai-agent`.** Так называются
  Gradle-проект, нативные пакеты и лаунчеры (`server-ai-agent`,
  `server-ai-agent-server`, `server-ai-agent-client`), юниты systemd,
  ярлык, `--vendor` и репозиторий. **Историческое `bebebe` остаётся намеренно**
  там, где смена сломала бы существующие установки или требует правки Java:
  пакеты `com.bebebe.agent` и группа `com.bebebe`, пути данных
  (`~/.config/bebebe-agent`, `~/.local/share/bebebe-agent`,
  `~/.local/share/bebebe-client`), свойства и переменные
  (`-Dbebebe.config`, `$BEBEBE_CONFIG`, `bebebe.log.*`), сокет
  `bebebe-agent.sock`, CN сертификата, автор коммитов заметок, `User-Agent`.
  Не «дочищать» их без миграции.
* **Пакеты** — `com.bebebe.agent.<модуль>`.
* **Логирование** — только через slf4j; logback подключать нигде, кроме
  модуля `logging`.
* **Секреты** — никогда не логировать и не печатать в `toString()`.
* **Скрипты действий** — только Python 3, контракт: JSON в stdin, JSON в stdout,
  ошибки в stderr, ненулевой код возврата.
* **Тесты** — без сети наружу; внешние HTTP-API мокать локальным
  `com.sun.net.httpserver.HttpServer`. Имена тестов — по-русски, описывают
  поведение, а не метод.
* **`callback_data`** — только идентификаторы, не значения; лимит 64 байта
  проверяется в `CallbackData`, обходить его нельзя.
* **Конфиг** — каждый модуль читает только свою секцию через `config-store`
  и сам задаёт дефолты. Настройки, правимые из интерфейсов, объявляются
  в `SettingsField`: там же записано, секрет ли это и что будет при смене.
* **Секреты не уходят в Telegram** — ни значением, ни в кнопке, ни в логе.
* **Хуки жизненного цикла** — быстрые и синхронные; долгую работу ставить
  в очередь, а не делать внутри хука.
* **Входящее из любого канала** — это `UserMessage`, а не строка: канал
  занимается транспортом, обработка общая.
* **Внешние процессы** (`arecord`, `whisper-cli`, evdev-хелпер, Python) —
  stdout и stderr читать **раздельно**: служебный вывод не должен попадать
  в данные. Команда запуска выносится в отдельный метод, чтобы её проверял тест.
* **Модель — только через `LlmProvider`.** Ядро, инструменты и GUI не знают
  ни `OllamaClient`, ни SDK Anthropic; новый провайдер — это класс в
  `com.bebebe.agent.llm`, ветка в `LlmProviders.create` и строка в `PROVIDERS`.
* **Каждое обращение к модели списывает бюджет.** Новая фича, которая ходит
  в Ollama, обязана брать из `RequestBudget`, а не заводить свой лимит.
* **Ответ модели разбирается терпимо.** Неизвестный тип, отсутствующее поле,
  не-JSON — это `UNKNOWN` и вежливый ответ, а не исключение.
* **Новый скрипт по умолчанию требует подтверждения.** Снимать флаг может
  только пользователь, кнопкой.
* **Всё, что приходит от модели и уходит в имя файла или в аргументы
  процесса, проверяется.** Имя скрипта, имя пакета, идентификаторы.
* **Заметки — файлы, индекс — кэш.** Всё, что пишет `notes-store`, должно
  оставаться читаемым без базы и без агента (Obsidian, `cat`, `git show`);
  служебное — только в HTML-комментариях. Каждая запись — через
  `NotesStore.write`: атомарно, с переиндексацией и коммитом.
* **Буфер обмена читается только по явной просьбе** — через инструмент,
  никакого фонового чтения и `--watch`. Результат идёт в лог сессии
  источником `CLIPBOARD`, а не подмешивается в текст сообщения молча.
* **Живой стиль: тумблер включает механику, персона задаёт манеру.** Новые
  правила разбиения не зашивать в код — они идут в промпт с оговоркой
  о приоритете персоны; каналы получают `parts`, но опираться могут
  на `text`.
* **Персона — это стиль, не права.** Её текст подмешивается в каждый
  системный промпт, но не меняет протокол решения, подтверждения и бюджет.
* **Ожидание с известным потолком — под сигналом `activity.busy`.** Новый
  долгий вызов (сеть, дочерний процесс) обязан поднять сигнал с таймаутом,
  иначе сторож примет его за зависание; а вызов без таймаута — не заводить.
* **Обработка — только в `AgentWorker`.** Новый канал зовёт `handle()`
  и ждёт, а не крутит цикл у себя: иначе его зависание нечем перезапустить.
* **Экран в окне — из кирпичей `Ui`, анимации — из `Transitions`.** Свои
  отступы, размеры шрифтов, hex-цвета и длительности не заводить: новый
  раздел должен быть неотличим от соседних без ручной подгонки.
* **Статус — только в окне.** Всё, что отвечает на вопрос «есть ли сеть»,
  бессмысленно слать по сети; Telegram получает события (зависание,
  обновление), а не панель состояния.
* **В бэкап секреты не попадают.** Любой новый секрет в конфиге называется
  так, чтобы его ловил фильтр `BackupService` (`*_token`, `*api_key`,
  `*secret*`, `*password*`), иначе он уедет в архив открытым текстом.
* **Голосовое — вдобавок к тексту, не вместо.** Текст уходит всегда
  и первым; синтез — в отдельном потоке, его сбой ответ не ломает.
* **Системное событие — тоже `UserMessage`**, с `source = SYSTEM`: планировщик
  не зовёт модель сам, а подаёт промпт в `AgentCore.handle`. Так на него
  распространяются флаг ON/OFF, бюджет, память и лог сессии.
* **Новый канал ввода открывает `TraceContext` на входе**, а `UserMessage`
  подхватывает идентификатор. Переезд в другой поток — только через
  `TraceContext.wrap`. Иначе история запроса рвётся.
* **Значимые шаги логируются событиями**, а не фразами:
  `log.atInfo().addKeyValue("event", "…").addKeyValue(…).log(…)`. По `kv.event`
  и `trace_id` историю собирают инструментами, а по тексту — нет.
* **Инструмент ходит в модель только через `ToolContext.LlmCaller`.** Прямой
  `OllamaClient` в модуле `tools` запрещён: иначе обращение не спишет бюджет.
* **Регулярки с кириллицей — с `Pattern.UNICODE_CHARACTER_CLASS`**, иначе
  `\\b` не работает и триггер молча не срабатывает.
* **Память пишется только консолидацией и руками через меню.** Ядро не
  добавляет факты напрямую по ходу ответа — иначе один и тот же факт ложился бы
  дважды, из ответа и из извлечения.
* **Новая подсистема со своим файлом** — три места сразу: аппендер и `<logger>`
  в `logback.xml`, префикс в `JsonLayout.SUBSYSTEMS`, имя в
  `AppLogging.resolveLoggerName`. Тест `LogbackConfigTest` проверит первые два.

## 7. Сборка и релизы

### 7.1 Как упаковываем: jpackage, а не native-image

Нативные исполняемые файлы делает **`jpackage` из JDK** — официальный инструмент,
который кладёт рядом с приложением урезанную JVM (`jlink`) и нативный лаунчер:
пользователю не нужна установленная Java, запускается `server-ai-agent-server/bin/server-ai-agent-server`.

Почему не GraalVM native-image, хотя он даёт один маленький бинарник и мгновенный
старт:

* **JavaFX.** Native-image с JavaFX работает только через GluonFX и свой набор
  метаданных; автономный агент — JavaFX + AtlantaFX, и это сразу отдельный
  проект по поддержке.
* **Рефлексия и нативные библиотеки.** Jackson (записи протокола, конфиг
  клиентов), `sqlite-jdbc` (грузит `.so` из jar), Java-WebSocket, logback,
  Anthropic SDK — каждому нужны reachability-метаданные; собрать их можно
  агентом-трассировщиком, но любой непройденный путь = падение в проде,
  которого тесты на JVM не покажут.
* **Старт не критичен.** Сервер и клиент — долгоживущие процессы под systemd,
  секунда старта JVM никого не волнует; память тоже не узкое место.
* **Цена ошибки.** jpackage запускает ровно тот же байт-код, что прошёл 721 тест.
  Native-image — другой рантайм (closed-world, свои правила инициализации
  классов), его пришлось бы тестировать отдельно.

Что даёт jpackage и что нет: `--type app-image` — переносимый каталог
(любой glibc-Linux, в том числе Arch: пакетов `pacman` jpackage не делает,
и это осознанно не PKGBUILD, а tar.gz); `--type deb` — пакет для Ubuntu/Debian
(`dpkg-deb` + `fakeroot` на машине сборки; на Arch их нет, `.deb` собирает CI);
`--type exe` — установщик Windows (через WiX; выбран вместо `msi`, потому
что умеет `--win-per-user-install` без прав администратора и диалог выбора
каталога); `--type rpm`, `dmg` — по той же схеме, когда понадобятся.
Windows-сборка идёт на отдельном runner-е: jpackage не кросс-компилирует.

### 7.2 Что и на чём собирается

Всё описано одним скриптом [`gradle/packaging.gradle.kts`](gradle/packaging.gradle.kts),
который подключают три модуля-точки входа через `extra` + `apply(from = …)`.
jpackage **не кросс-компилирует**, поэтому что собирать, решает ОС сборки
(`isWindows` в скрипте), а в CI у каждой ОС свой runner:

| Артефакт | Модуль | Runner | Как |
|---|---|---|---|
| `server.jar` | `server-app` | Linux | толстый JAR, `java -jar server.jar` (`Main-Class`, `Enable-Native-Access` в манифесте) |
| `client.jar` | `client-app` | Linux | то же |
| `standalone-agent.jar` | `supervisor-app` | Linux | то же, JavaFX внутри |
| `server-ai-agent-server-<v>-linux-x64.tar.gz` | `server-app` | Linux | app-image со встроенной JVM — Arch и любой glibc-Linux |
| `server-ai-agent-client-<v>-linux-x64.tar.gz` | `client-app` | Linux | то же |
| `server-ai-agent-<v>-linux-x64.tar.gz` | `supervisor-app` | Linux | то же, автономный агент |
| `server-ai-agent-server_<v>_amd64.deb` | `server-app` | Linux | Ubuntu (`--linux-shortcut`, пакет `server-ai-agent-server`; нужны `dpkg-deb`, `fakeroot`) |
| `server-ai-agent-client_<v>_amd64.deb` | `client-app` | Linux | Ubuntu |
| `server-ai-agent-client-<v>-windows-x64.zip` | `client-app` | **Windows** | app-image: `server-ai-agent-client\server-ai-agent-client.exe` + runtime, переносимый |
| `server-ai-agent-client-<v>-windows-x64.exe` | `client-app` | **Windows** | установщик (`--type exe` через WiX): в каталог пользователя без прав администратора, ярлык в «Пуске» |

Сервер и автономный агент под Windows **не собираются намеренно**: сервер —
headless-процесс под systemd на Linux-машине, автономный агент завязан на
Wayland (evdev, `wl-paste`, `notify-send`). Windows нужен только тонкому
клиенту — «рукам» на машине пользователя.

Таски: `fatJar` → `stageJpackageInput` → `jpackageAppImage` → на Linux
`appImageTar` + `jpackageDeb`, на Windows `appImageZip` + `jpackageWinExe`
(jpackage называет установщик `<name>-<version>.exe`, таск переименовывает
в общую схему `-windows-x64`). Всё вместе — `packageNative` в каждом модуле;
корневые `releaseArtifacts` (три модуля, Linux) и `releaseArtifactsWindows`
(только клиент). Задача пропускается через `onlyIf`, если не та ОС или нет
инструмента (`dpkg-deb`, `candle.exe`/`wix.exe`).

Толстый JAR собирается без shadow-плагина: `Jar` с `zipTree` зависимостей,
дубли отбрасываются, подписи чужих jar (`META-INF/*.SF`) выкидываются —
иначе JVM откажется грузить классы. Версия для jpackage — первые три числа
из `-PreleaseVersion` (`0.2.0` как есть, `0.1.0-stage2-preview` → `0.1.0`);
без свойства — `0.1.0-SNAPSHOT`.

**Клиент на Windows — что работает, а что нет.** Транспорт, трей (AWT),
запись звука (`javax.sound`) и скрипты — кроссплатформенны; для скриптов
`ScriptConfig` на Windows берёт `python` вместо `python3` и `Scripts\python.exe`
внутри venv вместо `bin/python` (без этого `.exe` не выполнил бы ни одного
скрипта). `prlimit` там нет — скрипты идут без лимитов ресурсов, с `WARN`
на старте (таймаут остаётся). **Не портировано**: push-to-talk (evdev-хелпер —
Linux-only, нужен низкоуровневый хук клавиатуры) и буфер обмена (`wl-paste` →
`java.awt.datatransfer`); клиент честно не заявляет `voice` и `clipboard`
в `capabilities`, сервер на просьбу про буфер отвечает «компьютер не на связи».
Это и есть работа «Windows-клиент» из 6.7 — сборка её не заменяет.
Проверено CI: `.exe` и zip собираются; **запуск на Windows вручную не
проверялся** — на этой машине Windows нет.

Пути в упакованном виде: рабочий каталог у лаунчера произвольный, поэтому
конфиги лучше класть по XDG-путям (`~/.config/bebebe-agent/config.toml`,
`client.toml`), а `hotkey_helper`, `[logging] dir`, `whisper_binary` задавать
абсолютными. Автономный агент, установленный из app-image, SingleInstance
и Telegram-кнопку «Показать окно» сохраняет — сокет в `$XDG_RUNTIME_DIR`.
На Windows `~` — это `%USERPROFILE%`, `client.toml` ищется в
`%USERPROFILE%\.config\bebebe-agent\`.

## 6. Этап 2: сервер и тонкие клиенты

Этап 1 — автономная сборка на одной машине — остаётся рабочей как есть
и ничего из написанного ниже пока не использует. Этап 2 разносит систему
на **сервер** (агент: модель, память, Telegram, планировщик) и **тонких
клиентов** на других машинах: выполнить скрипт там, прочитать тамошний буфер,
принять голос с тамошнего микрофона. Сделан **только транспорт**.

### 6.1 Схема

```
   клиент (ноутбук)                                   сервер (агент)
 ┌───────────────────┐   исходящее wss://, TLS       ┌──────────────────────┐
 │ TransportClient   │ ───────────────────────────▶  │ TransportServer      │
 │  пинит отпечаток  │   AUTH{client_id, token}      │  self-signed cert    │
 │  сертификата      │ ◀──── AUTH_RESULT ok ──────── │  PairingTokens (хэши)│
 │                   │   STATUS_PUSH                 │                      │
 │  Handler          │ ◀──── PING / PONG ─────────▶  │  Listener            │
 │   onRequest()     │ ◀──── RUN_SCRIPT_REQUEST ──── │   request() ─► future│
 │                   │ ────── RUN_SCRIPT_RESULT ───▶ │   (reply_to)         │
 │                   │ ◀──── CLIPBOARD_REQUEST ───── │                      │
 │                   │ ────── VOICE_AUDIO_PUSH ────▶ │   onMessage()        │
 └───────────────────┘                               └──────────────────────┘
        обрыв → Backoff 1 с → 2 → 4 … 60 с (±20 %) → снова
        отказ AUTH → REJECTED, стоп: нужен новый паринг
```

Решения, из которых всё следует:

* **Клиент всегда инициирует соединение.** У него нет открытых портов, он за
  NAT, на ноутбуке, который засыпает; серверу достаточно одного адреса.
  Запросы «сервер → клиент» едут по уже открытому сокету.
* **TLS с self-signed сертификатом и пиннингом.** Покупать сертификат
  домашнему серверу не у кого. Сервер при первом старте генерирует ключ
  **`keytool`-ом из JDK** (внешний процесс, аргументы списком — как
  `arecord` и `whisper-cli`; BouncyCastle ради одного сертификата на 10 лет
  не нужен), клиент доверяет **SHA-256 отпечатку**, а не CA. Это строже
  проверки имени хоста: подменить сервер можно, только украв `server.p12`.
  Плата — перевыпуск сертификата требует перепарить клиентов.
* **Библиотека — Java-WebSocket на обеих сторонах**, не JDK-клиент:
  `java.net.http.WebSocket` принудительно проверяет имя хоста и с пиннингом
  не дружит без системного флага. Библиотечные ping-фреймы выключены
  (`setConnectionLostTimeout(0)`): живость — наши `PING`/`PONG`, они видны
  в логах и в тестах.
* **Pairing-токен рождается на сервере**, по действию пользователя,
  а не пишется руками в конфиг: человек придумает короткий и один на все
  машины, `SecureRandom` — 32 байта. Выдаётся из **окна**, не из Telegram:
  это секрет, а секреты в чат не уходят (раздел 5). Telegram потом покажет
  список клиентов и «отозвать» — там секрета нет. На диске лежит **SHA-256
  токена**, не токен: показать повторно нельзя, только выпустить новый,
  зато утечка `clients.json` не даёт подключиться. Сравнение константное
  по времени.
* **Отказ в AUTH — не повод переподключаться.** Неверный токен сам не
  исправится; клиент уходит в `REJECTED` и пишет `ERROR`. Обрыв, таймаут,
  4409 «заменён», 4001 «сервер останавливается» — переподключение.
* **`trace_id` едет в конверте.** Запрос, ушедший клиенту, и его результат
  ложатся в одну историю с сообщением пользователя, из которого родился
  (`Envelope.reply` наследует `trace_id`). Соединение как таковое — своя
  цепочка: connect → auth → disconnect под одним идентификатором.

### 6.2 Протокол

Текстовые WebSocket-фреймы, один JSON-объект на сообщение:

```json
{"type": "RUN_SCRIPT_REQUEST",
 "id": "5f1c9a2b7e3d4c10",          // 8 случайных байт hex, уникален в соединении
 "reply_to": null,                  // у ответов -- id запроса
 "trace_id": "e510c42a22f9",        // как в логах; ответ наследует
 "sent_at": 1789890000000,          // epoch millis отправителя
 "payload": { ... }}                // объект, форма зависит от type
```

| Тип | Направление | payload | Ответ |
|---|---|---|---|
| `AUTH` | клиент → сервер, первое сообщение | `client_id`, `client_name`, `token`, `protocol_version` | `AUTH_RESULT` |
| `AUTH_RESULT` | сервер → клиент | `accepted`, `reason`, `server_name`, `heartbeat_seconds` | — (при отказе сокет закрывается 4401) |
| `PING` / `PONG` | обе стороны | пусто | `PONG` с `reply_to` |
| `STATUS_PUSH` | клиент → сервер, после AUTH и раз в `status_interval` | `hostname`, `os`, `user`, `display`, `capabilities[]`, `version`, `uptime_seconds` | — |
| `RUN_SCRIPT_REQUEST` | сервер → клиент | `code`, `arguments{}` (JSON в stdin скрипта), `timeout_seconds` | `RUN_SCRIPT_RESULT` |
| `RUN_SCRIPT_RESULT` | клиент → сервер | `exit_code`, `stdout`, `stderr`, `duration_ms`, `timeout` | — |
| `CLIPBOARD_REQUEST` | сервер → клиент | `max_chars` | `CLIPBOARD_RESULT` |
| `CLIPBOARD_RESULT` | клиент → сервер | `available`, `text`, `truncated`, `error` | — |
| `VOICE_AUDIO_PUSH` | клиент → сервер | `format` (`wav`), `sample_rate`, `channels`, `audio_base64`, `duration_ms` | — |
| `ERROR` | обе стороны | `code` (`unsupported`, `bad_payload`, `bad_message`, `internal`), `message` | — |

Коды закрытия (`Protocol`): `4401` AUTH отклонён, `4408` AUTH не пришёл или
первым пришло не оно, `4409` заменено новым соединением того же клиента,
`4499` нет ответа на PING два интервала, `4001` сервер останавливается.

Кодек **строгий**: нет типа, чужой тип, `payload` не объект — `ProtocolException`.
Обе стороны — наш код, терпеть, как ответ модели, здесь нечего; чем раньше
вылезет рассинхрон версий, тем лучше. Незнакомые поля конверта игнорируются,
чтобы новая версия могла добавить поле. Голос едет base64 внутри JSON — одно
сообщение на фразу; бинарные фреймы появятся, если станет тесно.

### 6.3 Что готово

Модуль `transport` (`com.bebebe.agent.transport`):

| Класс | Что делает |
|---|---|
| `MessageType`, `Envelope`, `Codec`, `Protocol` | Типы, конверт, JSON туда-обратно, коды закрытия |
| `messages/*` | Записи полезных нагрузок: `AuthRequest`, `AuthResult`, `StatusPush`, `RunScriptRequest/Result`, `ClipboardRequest/Result`, `VoiceAudioPush`, `ErrorPayload` |
| `TransportConfig` | Секция `[transport]`: `bind`, `port`, `data_dir`, `heartbeat_seconds`, `auth_timeout_seconds` |
| `ServerCertificate` | `server.p12` + `server.p12.pass` (600) через `keytool`; `SSLContext`, отпечаток |
| `Fingerprint`, `PinnedTrust` | SHA-256 отпечаток и `SSLContext` клиента, доверяющий только ему |
| `PairingTokens` | `clients.json`: выпуск, проверка, отзыв, `last_seen`; хэши, атомарная запись |
| `TransportServer` | `wss://`-сервер: AUTH с таймаутом, heartbeat, `send()`, `request()` с будущим по `reply_to`, `Listener` |
| `TransportClient` | Исходящее соединение, AUTH, `PONG`, свой `PING` при простое, `STATUS_PUSH`, `Handler.onRequest` в отдельном потоке, автопереподключение |
| `Backoff` | 1 с → 2 → 4 … потолок, ±20 % |
| `remote/ClientSelector` | Кому адресовать: `default_client` из конфига → единственный → подключившийся последним; фильтр по `capabilities` |
| `remote/RemoteActionExecutor` | `ActionExecutor` сервера: `RUN_SCRIPT_REQUEST` → `RUN_SCRIPT_RESULT`; нет клиента — `launchFailed` **сразу**; молчит — `TIMEOUT` через таймаут скрипта + 30 с |
| `remote/RemoteClipboardTool` | `ClipboardTool` сервера: `CLIPBOARD_REQUEST`, 10 с; нет клиента — `isReady() = false` |

`TransportServer` держит список слушателей (`addListener`): удалённые исполнители
ждут ответы по `reply_to`, `VoiceReceiver` сервера забирает `VOICE_AUDIO_PUSH`,
уведомления о подключениях уходят в Telegram — каждому своё. `PairingTokens`
перечитывает `clients.json` по времени файла: токен, выпущенный утилитой
по SSH, действует без перезапуска сервера.

Чего нет: client-модуля (тонкого процесса на машине пользователя), выбора
клиента моделью, раздела «🖥 Клиенты» в Telegram, паринга из окна.

### 6.4 Точки разделения ядра: `ActionExecutor` и `ClipboardTool`

Ядро просит у «машины пользователя» ровно две вещи, и обе теперь идут через
интерфейсы пакета `com.bebebe.agent.transport.actions`:

| Интерфейс | Что | Local-реализация (Этап 1) | Remote (следующая сессия) |
|---|---|---|---|
| `ActionExecutor` | `run(pythonCode) → ActionResult`, `timeout()`, `name()` | `script-runtime/LocalActionExecutor` поверх `ScriptRuntime` | `RemoteActionExecutor` поверх `TransportServer.request(RUN_SCRIPT_REQUEST)` |
| `ClipboardTool` | `read() → Optional<String>`, `isReady()`, `name()` | `clipboard-bridge/LocalClipboardTool` поверх `ClipboardBridge` | `RemoteClipboardTool` поверх `CLIPBOARD_REQUEST` |

`ActionResult` — общая форма результата (код, stdout, stderr, длительность,
доустановленные пакеты, `describeForModel()`); `ScriptResult` конвертируется
в неё `toActionResult()`, а обрезка вывода для модели теперь живёт в одном
месте. `AgentCore` принимает `ActionExecutor`, зовёт `run()` и берёт потолок
ожидания для watchdog из `timeout()` — раньше он сам считал «таймаут скрипта
+ 90 с», теперь это знает локальный исполнитель, а удалённый добавит сеть.
`ReadClipboardTool` получил конструктор от `ClipboardTool`.

Local-реализации лежат **рядом с тем, что оборачивают** (в `script-runtime`
и `clipboard-bridge`), а не в `agent-core`: клиент-модуль Этапа 2 возьмёт
их без ядра — тонкому клиенту нужен `ScriptRuntime` и `wl-paste`, но не
модель. Ради этого `script-runtime`, `clipboard-bridge` и `tools` зависят
от `transport`; Java-WebSocket в `transport` переведён в `implementation`,
чтобы не расползаться по classpath.

Контракт `ActionExecutor`, который Remote обязан выдержать: блокирует
до конца, прерывание потока = «останови скрипт» (локально — SIGTERM, удалённо —
отмена клиенту), исключений наружу нет — только `ActionResult.launchFailed`,
`timeout()` — честный потолок для сигнала «занят легитимно».

**Голос — не интерфейс, и это намеренно.** В автономной сборке источник
голоса остаётся как есть: `stt-bridge` **сам** решает, когда начать
и остановить запись — по нажатию и отпусканию клавиши через evdev — и подаёт
в ядро уже распознанный текст. Это push от источника, ядро голос не
запрашивает. В клиент-серверном режиме то же самое, только запись делает
клиент на своей машине и присылает `VOICE_AUDIO_PUSH`; сервер расшифровывает
и подаёт текст тем же путём. Поэтому «VoiceSource с методом record()» не
появится: есть источник, который зовёт ядро, а не ядро, которое зовёт источник.

Проверка, что автономная сборка не изменилась: полный набор — 683 теста,
включая восемь сквозных сценариев `EndToEndScenariosTest` на реальном
графе `AgentAssembly` — зелёный; `LocalActionExecutorTest` сравнивает
результат через интерфейс с результатом `ScriptRuntime` напрямую.

### 6.6 `server-app`: headless-сервер

#### Что это и чем отличается от автономной сборки

Второй entrypoint — `server-app` (`com.bebebe.agent.server.ServerMain`).
Собирается **без JavaFX вообще** (в `runtimeClasspath` нет ни `javafx`,
ни `atlantafx` — проверено) и поднимает через тот же `AgentAssembly` из
модуля `assembly` всё, что поднимал единый процесс, кроме трёх вещей:

| | Автономная сборка (`supervisor-app`) | Сервер (`server-app`) |
|---|---|---|
| Окно | JavaFX | нет |
| Скрипты | `LocalActionExecutor` → `ScriptRuntime` на этой машине | `RemoteActionExecutor` → `RUN_SCRIPT_REQUEST` тонкому клиенту |
| Буфер обмена | `LocalClipboardTool` → `wl-paste` | `RemoteClipboardTool` → `CLIPBOARD_REQUEST` |
| Голос | `SttBridge`: evdev-клавиша + `arecord` + whisper здесь | клиент пишет и присылает `VOICE_AUDIO_PUSH`; whisper.cpp — **на сервере**, `RemoteVoiceIngest` → тот же `TranscriptionPipeline` и `handleVoice` |
| Настройки | файл + окно + Telegram | **только файл** (см. ниже) |
| Статус, логи | окно | Telegram: «📊 Статус», «📜 Логи» + файлы по SSH |
| Паринг клиентов | (окно — следующая сессия) | CLI: `server-app pair <имя>` |
| Транспорт | не поднимается | поднимается всегда, `[transport]` обязательна |
| Юнит | `server-ai-agent.service` (`graphical-session.target`) | `server-ai-agent-server.service` (`default.target`, нужен `loginctl enable-linger`) |

Общее — всё остальное: провайдер модели, память, каталог скриптов,
планировщик, заметки, персоны, Telegram, TTS, watchdog, проверка обновлений,
бэкап. Разделение прошло по интерфейсам 6.4, поэтому `AgentCore` про режим
не знает: `AgentAssembly.Options.server(executor, clipboard)` подставляет
удалённые реализации и выключает локальный push-to-talk (`localVoice = false`).

`AgentAssembly` и `Wiring` (бывшие статические шаги `SupervisorMain`) переехали
в модуль `assembly` без зависимости от `ui`; `build-info.properties`
генерируется там же, поэтому версию знают оба entrypoint-а.

#### Конфигурация — только файл, и это намеренно

Сервер читает тот же `config.toml` (формат тот, что писало окно: `[llm]`,
`[llm.<id>]`, `[telegram]`, …) **один раз при старте**. Правится он **только
редактированием файла по SSH** с последующим `systemctl --user restart
server-ai-agent-server`. Раздел «⚙️ Настройки» в Telegram в серверном режиме показывает
значения, но кнопок правки в нём нет (`SettingsScreens.root(settings, readOnly
= true)`, нажатие устаревшей кнопки отвечает «правится в config.toml по SSH»).

Почему так для headless: на удалённой машине нет окна, которое показало бы
расхождение файла и памяти; секреты в чат не уходят и раньше, а менять
провайдера или токен вслепую из чата на сервере, до которого идти по SSH, —
способ остаться без связи. Один источник правды, один способ его менять,
изменения видны в `git diff`/бэкапе.

#### Удалённые исполнители: нет клиента — сразу понятно

`RemoteActionExecutor.run()` при отсутствии подключённого клиента с
`capability = scripts` возвращает `launchFailed("нет связи с компьютером: ни
один клиент не подключён к серверу")` **мгновенно** (тест: < 500 мс) — модель
получает это как stderr и объясняет пользователю, ничего не ждёт. При наличии
клиента — запрос и ожидание `timeout()` = таймаут скрипта (`scripts.
timeout_seconds`) + 30 с на сеть; молчание клиента — `TIMEOUT_EXIT_CODE`,
`ERROR` от клиента — `launchFailed` с его кодом. Прерывание потока (мягкая
остановка) отменяет ожидание; отмены клиенту в протоколе пока нет — его скрипт
дойдёт до собственного таймаута. `RemoteClipboardTool` — то же с 10 с;
без клиента `isReady() = false`, и `read_clipboard` честно отвечает, что
компьютер не на связи.

Тумблер `agent.scripts_enabled` на сервере — тот же, что в автономной сборке
(в headless-режиме правится только в `config.toml`, 3.8.7): выключен —
модель не знает о скриптах и `RemoteActionExecutor` не вызывается вовсе, так
что клиент не получает ни одного `RUN_SCRIPT_REQUEST`, даже если модель
прислала скрипт вопреки схеме или кнопку «✅ Выполнить» нажали после выключения.

#### Голос

`VoiceReceiver` (слушатель транспорта) → `RemoteVoiceIngest.accept(bytes,
trace_id, кто)` → временный WAV → `TranscriptionPipeline` (тот же, что
у `SttBridge`; whisper-cli из `[stt]` на сервере) → `UserMessage(VOICE)`
→ `AgentAssembly.handleVoice` → ответ в последний активный чат Telegram,
как и раньше. Порог короткой записи (8000 байт) и проверка ON/OFF — те же.
`SttConfig.whatIsMissingForTranscription()` проверяет модель и бинарник
без evdev-хелпера: серверу клавиша не нужна. `trace_id` — тот, что клиент
завёл при нажатии клавиши; запись, расшифровка и ответ — одна история.

#### «Статус» и «Логи» в Telegram

В автономной сборке статуса в Telegram нет намеренно (3.19.1: «есть ли сеть»
без сети не доставить). У сервера иначе: он не уходит в офлайн сам по себе,
окна нет, и Telegram — единственный интерфейс кроме SSH. `ServerRuntime.status()`
собирает `ServerStatus` (ON/OFF, провайдер и доступность по последнему вызову,
счётчики, **подключённые клиенты** с адресом и `capabilities`, watchdog, диск,
версия, обновления, последняя ошибка, путь к конфигу); «📜 Логи» — хвост
`LogBuffer` с фильтрами ERROR / WARN+ / все, по 12 строк, `<pre>`, с командой
для SSH внизу. Логи как были файлами — так и остаются; в чате только окно
в последние события. Разделы включает `TelegramBridge.attachHeadless(...)`;
в автономной сборке они заглушки, «Логи» в корне не показываются.

#### Как запустить на удалённой Ubuntu для ручной проверки

```bash
# на сервере, от обычного пользователя
sudo apt install -y openjdk-25-jdk git python3-venv ffmpeg     # whisper.cpp -- как в README 1.4
git clone git@github.com:qateralong/server-ai-agent.git ~/server-ai-agent && cd ~/server-ai-agent
./gradlew :server-app:installDist                              # без JavaFX, ~1 мин
cp config/agent.example.toml config/agent.toml && chmod 600 config/agent.toml
$EDITOR config/agent.toml        # [llm.*] ключ и модель, [telegram] токен и allowed_usernames,
                                 # [stt] whisper_binary/model_path, [transport] port и bind

mkdir -p ~/.config/systemd/user && cp systemd/server-ai-agent-server.service ~/.config/systemd/user/
systemctl --user daemon-reload && systemctl --user enable --now server-ai-agent-server
sudo loginctl enable-linger $USER          # иначе юнит умрёт вместе с SSH-сессией

journalctl --user -u server-ai-agent-server -f      # «Серверный режим: конфиг …», «Транспорт слушает wss://…»
./server-app/build/install/server-app/bin/server-app pair "ноутбук"   # client_id, токен, отпечаток -- один раз
./server-app/build/install/server-app/bin/server-app clients
```

Порт `[transport] port` (8765) должен быть открыт для клиента (`ufw allow
8765/tcp` или туннель). Что проверять руками, пока клиента нет: `/menu` →
«📊 Статус» показывает «Клиенты: никого»; сообщение боту, требующее скрипта,
— в ответе «нет связи с компьютером»; «⚙️ Настройки» без кнопок правки;
«📜 Логи» с фильтрами; после `pair` — `clients` показывает запись, а
в `clients.json` лежит хэш. Полная проверка со скриптами и голосом — после
client-модуля (тестовый клиент есть только в `ServerRuntimeTest`).

Логи по SSH:

```bash
tail -f ~/server-ai-agent/logs/agent.log | jq -r '"\(.ts[11:19]) \(.level) \(.subsystem) \(.msg)"'
tail -f ~/server-ai-agent/logs/transport.log | jq -r '.msg'           # подключения, AUTH, heartbeat
grep '"remote.no_client"' ~/server-ai-agent/logs/agent-core.log | tail  # когда компьютера не было на связи
journalctl --user -u server-ai-agent-server --since today                # старт/падения процесса
```

### 6.8 `client-app`: тонкий клиент (Linux)

#### Что это

Второй процесс Этапа 2 — на машине пользователя. **Без окна, без `agent-core`,
без провайдеров модели** (в `runtimeClasspath` их нет — проверено): «мозг»
на сервере, у клиента только руки и уши. Что он умеет:

| Просьба сервера / событие | Что делает клиент |
|---|---|
| `RUN_SCRIPT_REQUEST` | Выполняет код тем же `ScriptRuntime` через `LocalActionExecutor`: свой venv (`~/.local/share/bebebe-client/venv`), `prlimit`, таймаут, **автоустановка пакета при `ImportError`** и повтор, аудит `script.audit` в лог клиента; отвечает `RUN_SCRIPT_RESULT` (код, stdout, stderr раздельно, длительность, таймаут) |
| `CLIPBOARD_REQUEST` | Читает системный буфер тем же `wl-paste` (`LocalClipboardTool`), обрезает по `max_chars`; без `wl-paste` — `available = false` с причиной, и `capability clipboard` не заявляется |
| Клавиша push-to-talk (evdev, DOWN/UP) | На DOWN — запись через `javax.sound.sampled` (`JavaSoundRecorder`, 16 кГц/моно/16 бит, в памяти), на UP — WAV уезжает `VOICE_AUDIO_PUSH`; короче 8000 байт — не отправляется. Расшифровки на клиенте нет |
| `PING`, `STATUS_PUSH` | Как у любого `TransportClient`: `capabilities` = `scripts` + `clipboard`/`voice`, если есть чем |
| Обрыв связи | Автопереподключение с экспоненциальной паузой; отказ AUTH — стоп и красная иконка |

Логика скриптов **не копировалась**: `script-runtime` и `clipboard-bridge`
от `agent-core` не зависят (это и было целью 6.4), клиент подключает те же
модули. Одна реализация — одно поведение на обеих машинах.

`HotkeyListener` переехал из `stt-bridge` в новый модуль **`capture`**
(зависит только от `logging`), там же `JavaSoundRecorder`; `stt-bridge`
использует их через `SttConfig.hotkey()`. Автономная сборка по-прежнему
пишет звук через `arecord` — на PipeWire это проверено, а `javax.sound`
впервые идёт в бой на клиенте; когда обкатается, `stt-bridge` переключится
через свой интерфейс `Recorder`, менять больше ничего не придётся.

**Трей** (`ClientTray`, AWT `SystemTray`): кружок зелёный «подключён»,
серый «нет связи / подключаюсь», красный «сервер отклонил — нужен новый
паринг»; подсказка с состоянием и адресом; пункт «Выход». Окна настроек нет
намеренно: конфиг — файл. На GNOME без AppIndicator трея нет (то же
ограничение, что у окна автономной сборки) — клиент пишет об этом в лог
и работает без иконки; `tray = false` отключает попытку.

#### Конфиг клиента

Отдельный файл `client.toml` — в нём нет ни модели, ни Telegram. Порядок
поиска: `-Dbebebe.client.config` → `$BEBEBE_CLIENT_CONFIG` →
`~/.config/bebebe-agent/client.toml` → `./config/client.toml`. Образец —
[`config/client.example.toml`](config/client.example.toml):

| Секция | Ключи | Откуда |
|---|---|---|
| `[server]` | `url` (`wss://` обязателен), `fingerprint`, `client_id`, `token` | печатает `server-app pair "<имя>"` на сервере, один раз |
| `[client]` | `name`, `tray` | как компьютер зовётся в статусе сервера |
| `[hotkey]` | `helper`, `key`, `device` | тот же evdev-хелпер, что в 3.7 (группа `input`) |
| `[audio]` | `device` (подстрока имени устройства ввода), `max_seconds` | пусто — системное устройство |
| `[scripts]` | `venv_dir`, `scripts_dir`, `timeout_seconds`, `auto_install_deps` | как у автономной сборки, но свой каталог |
| `[logging]` | `dir`, `level` | логи клиента, тот же JSON-формат |

Токен лежит открытым текстом — тот же компромисс 1.7, `chmod 600`. Всё
читается на старте; `toString()` конфига токен не печатает.

#### Как собрать и запустить

```bash
cd ~/server-ai-agent && ./gradlew :client-app:installDist
cd native/evdev-hotkey && make && cd -          # push-to-talk; без хелпера клиент работает без голоса
cp config/client.example.toml config/client.toml && chmod 600 config/client.toml
$EDITOR config/client.toml                      # вставить блок [server] из «server-app pair»
./client-app/build/install/client-app/bin/client-app     # или юнит ниже

cp systemd/server-ai-agent-client.service ~/.config/systemd/user/
systemctl --user daemon-reload && systemctl --user enable --now server-ai-agent-client
journalctl --user -u server-ai-agent-client -f           # «Клиент запущен: … скрипты да, буфер да, голос да»
```

Что проверить: в `/menu` → «📊 Статус» на сервере появился клиент с его
`capabilities`; попросить бота выполнить что-нибудь скриптом — подтверждение,
и в логе клиента `client.script.start` / `script.audit` / `client.script.done`;
«переведи то, что я скопировал» — `client.clipboard`; зажать клавишу, сказать,
отпустить — у клиента `voice.press` / `voice.sent`, у сервера
`voice.received` / `voice.transcribed` под **тем же `trace_id`**.

Ограничения: аргументы `RunScriptRequest.arguments` пока игнорируются
(контракт скриптов Этапа 1 — данные в коде; в логе `WARN`); отмены скрипта
с сервера нет — он дойдёт до своего таймаута; Windows-сборка (`.exe`, zip)
публикуется в релизе (7.2), но push-to-talk и буфер там не работают:
evdev-хелпер и `wl-paste` — Linux-only, порт — 6.7.

### 6.9 Связка «сервер + Linux-клиент»: проверенные сценарии

Каждый — тест в `ClientServerScenariosTest` (`server-app`): настоящий
`ServerRuntime` и настоящий `ClientRuntime` на одном хосте, настоящий Python
на стороне клиента, стабы Telegram и модели (test fixtures модуля `assembly`),
whisper подменён скриптом. Руками на двух машинах проходятся те же шаги.

| Сценарий | Что подтверждено |
|---|---|
| **Голос с клиента → скрипт на клиенте → Telegram, живой стиль.** `PushToTalk.send(WAV)` → `VOICE_AUDIO_PUSH` → whisper на сервере → `run_script` → подтверждение в чате → ✅ | «🎤 текст» в чате; код сохранён и выполнен в `scripts_dir` **клиента**, на сервере скриптов нет; stdout с клиента попал в формулировку; ответ ушёл двумя репликами с `sendChatAction` между ними |
| **Буфер обмена по просьбе в чате.** «переведи то, что я скопировал» → `tool_call(read_clipboard)` → `CLIPBOARD_REQUEST` клиенту | текст буфера клиента в контексте модели |
| **Обрыв клиента во время скрипта.** Сервер закрывает соединение (`TransportServer.disconnect`, код 4002), пока скрипт идёт | ответ «Не удалось выполнить действие: соединение с компьютером оборвалось» **сразу**, не по таймауту; модель второй раз не звали; клиент переподключился сам, `connectedAt` новый |
| **Рискованный скрипт → подтверждение → именно на клиенте.** «удали всё из корзины» | до ✅ ничего не выполнялось; после — файл скрипта у клиента |
| **Переключение провайдера** Ollama → Claude → Ollama при живом клиенте | `connectedAt` не изменился, состояние `CONNECTED`, следующий скрипт снова уходит клиенту |

Стыки, починенные по ходу:

* **Обрыв клиента не завершал ожидающие `request()`** — сервер ждал полный
  таймаут (таймаут скрипта + 30 с). Теперь `TransportServer` помнит, какому
  клиенту адресован каждый запрос, и на закрытии соединения завершает их
  исключением сразу.
* **Ошибка запуска шла в цикл починки.** `launchFailed` (нет связи, нет
  интерпретатора) — не ошибка в коде; ядро просило модель «починить» и жгло
  бюджет. Теперь `LAUNCH_FAILED_EXIT_CODE` → сразу текст пользователю
  (`script.launch_failed`), без обращения к модели.
* `TransportServer.disconnect(clientId, reason)` с кодом `4002 CLOSE_KICKED`
  (клиент переподключается) — пригодится и для отзыва.

Известные шероховатости связки:

* **Отмены скрипта на клиенте нет.** После обрыва или мягкой остановки сервера
  скрипт на клиенте дорабатывает до своего таймаута; результат потом некому
  отдать. Нужен `CANCEL` в протоколе.
* **Ответ после подтверждения приходит правкой сообщения с кнопками**
  (`editMessageText`), а не новым сообщением — так было и в Этапе 1; в чате
  это выглядит нормально, но при разборе логов/стабов искать надо в обоих.
* **`arguments` в `RUN_SCRIPT_REQUEST` игнорируются** клиентом (6.8).
* **Один клиент по умолчанию** — `ClientSelector` берёт последнего
  подключившегося; выбор моделью — 6.7.

### 6.10 Ручной запуск прямо сейчас: сервер на Ubuntu, клиент на Arch

Без релизов и упаковки (это Сессия 27) — Gradle-дистрибутивы и `scp`.

```bash
# --- на машине разработки (Arch) -------------------------------------------
cd ~/server-ai-agent
./gradlew :server-app:build :client-app:build      # тесты + build/distributions/*.tar
scp server-app/build/distributions/server-app.tar user@ubuntu:~/
scp config/agent.example.toml user@ubuntu:~/agent.toml     # или уже заполненный конфиг

# --- на сервере (Ubuntu) ----------------------------------------------------
sudo apt install -y openjdk-25-jre-headless python3-venv ffmpeg   # + whisper.cpp, README 1.4
tar xf server-app.tar && mkdir -p ~/server-ai-agent/config && mv agent.toml ~/server-ai-agent/config/agent.toml
chmod 600 ~/server-ai-agent/config/agent.toml && $EDITOR ~/server-ai-agent/config/agent.toml
cd ~/server-ai-agent && ~/server-app/bin/server-app            # вручную: конфиг ищется от рабочего каталога
#   либо юнит: ExecStart в systemd/server-ai-agent-server.service поправить на ~/server-app/bin/server-app
~/server-app/bin/server-app pair "arch-ноут"          # напечатает блок [server] для клиента
sudo ufw allow 8765/tcp

# --- на клиенте (Arch) ------------------------------------------------------
cd ~/server-ai-agent && tar xf client-app/build/distributions/client-app.tar -C /tmp
cp config/client.example.toml config/client.toml && chmod 600 config/client.toml
$EDITOR config/client.toml                            # вставить блок [server] с сервера
cd native/evdev-hotkey && make && cd -                # push-to-talk (группа input, 3.7)
/tmp/client-app/bin/client-app                        # или ./gradlew :client-app:run
```

`bin/*` — стартовые скрипты Gradle с classpath из `lib/*.jar` (`java -jar`
одного файла нет: зависимости лежат рядом, скрипт их собирает). Относительные
пути (`config/`, `logs/`, `native/`) считаются от **рабочего каталога**,
поэтому запускать из корня репозитория или задать `-Dbebebe.config` /
`-Dbebebe.client.config` абсолютными путями. Проверка: в журнале сервера
`Транспорт слушает wss://…`, у клиента `Клиент запущен: … скрипты да`,
в `/menu` → «📊 Статус» клиент виден с его `capabilities`.

### 6.7 Что дальше

1. **Выбор клиента моделью.** Сейчас `ClientSelector`: `default_client` →
   единственный → последний подключившийся. Дальше — параметр решения
   `target: <client_id>` с подсказкой в промпте о подключённых клиентах
   и их `capabilities`; сюда же `local` для автономной сборки с клиентами.
2. **Windows-клиент: порт возможностей.** Сборка `.exe`/zip уже в релизе
   (7.2), скрипты и трей там работают; остались клавиша (evdev →
   низкоуровневый хук Windows) и буфер (`wl-paste` → `java.awt.datatransfer`
   там работает), после чего клиент заявит `voice` и `clipboard`. Аргументы
   скриптов в stdin. Первый ручной запуск на Windows — тоже сюда: CI проверяет
   только сборку.
3. **Паринг в окне** (автономная сборка с клиентами): «Подключить клиента» →
   `PairingTokens.issue` → показать один раз `wss://host:port`, отпечаток,
   `client_id`, токен (и QR). В Telegram — раздел «🖥 Клиенты»: кто подключён,
   статус, «отозвать» (на сервере это пока `server-app clients / revoke`).
4. **Подтверждение говорит, где выполнится.** Кнопки и `PendingExecution` уже
   общие; осталось подставить `executor.name()` («компьютер «ноут»») в текст.
   И отмена скрипта клиенту (`CANCEL` в протоколе) при мягкой остановке.
5. **Ограничения, которые появятся вместе с интеграцией**: скрипт на клиенте
   работает с правами тамошнего пользователя без песочницы (тот же компромисс
   3.8.5, теперь на двух машинах); секрет клиента — токен в его конфиге
   открытым текстом (тот же компромисс 1.7); голос по сети идёт под TLS,
   но покидает машину клиента — в отличие от Этапа 1, где аудио не уходило
   никуда.
